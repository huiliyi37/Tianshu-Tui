# 桌面版任务规划与落地方法论

> 从天枢桌面版 M0→M3（基座）+ N0→N5（平价）两轮计划反推
> 日期：2026-06-15

---

## 1. 范式照搬优先于个性化（推迟发明）

**计划体现**：基座计划开篇明义"先照搬 Antigravity 2.0，再谈个性化"。M0→M3 全程忠实复制竞品主线，星域议事会（天枢独有的最大差异化）被放在 §5 迭代路线标注"本轮不做"。N 阶段再次确认"本阶段不做个性化"。

**反推的思想**：面对一个有成熟参照物的产品方向时，**先证明能跑通竞品的主线路径**，再谈自己的差异化。如果一上来就把范式和个性化纠缠在一起，每个里程碑的验收标准就模糊了——"这个功能不够 Antigravity" 和 "这个功能不够天枢" 是两个不同的失败。分开来做让验收口清晰。

## 2. 运行时零改写（不动大脑，只接身体）

**计划体现**：基座 §1 红线——"AgentLoop 核心、deliver_task/ownership、prompt frozen/cache 不变量、T6 self/world 判定一律不动；后端只加 API 面"。N 阶段缰绳不变。

**代码实证**：M0→M3 落地的所有后端代码（serve.ts、session-manager.ts、session-routes.ts）都在 `src/server/` 目录——不在 `src/agent/` 里改一行。`AgentLoop` 通过 `AgentCallbacks` 事件接口被 session-manager 消费，零侵入。

**反推的思想**：当一个系统已经被充分解耦（AgentLoop 不依赖 TUI），**新入口的价值在于暴露已有能力，不在于重写内核**。每个新入口（桌面/HTTP/CLI/headless）都是"接一副新身体"，大脑只有一个。计划中反复出现的"复用"（ArtifactStore、SessionRegistry、TaskRegistry、ProfileRegistry）不是偷懒，是对已有投资的最大化回报。

## 3. 缺口用代码行号实证（不脑补工作量）

**计划体现**：基座 §3"关键缺口"每个都有具体的 file:line 引用：
- B0：`rivet serve` 未进发行入口（main-ink.tsx → main.ts）
- B1：单活跃会话（routes.ts 只有 state.running）
- B2：approval 硬拒（prompt-route.ts onApprovalRequired 自动否决）
- B3：事件不补全（缺 onPhaseChange/onCheckpoint）
- B4：Artifacts 未升为 session API

N 阶段同样逐条列了 6 个真实状态（前端是快速脚手架、RuntimeSessionManager 纯内存、M2 只做了 approval modal……），每条都有代码引用。

**反推的思想**：计划的核心价值不在于"做什么"，在于**"为什么这样做是安全的"和"当前真实状态决定了工作量"**。不读代码写出来的计划是猜测——读了代码写出来的计划是工程。缺口必须到行号，说"哪半截断了、为什么断"（贪狼的诊断之道在计划层面的应用）。

## 4. 每阶段独立可用 + 过门测试 + 单独提交

**计划体现**：M0→M3 每个里程碑都有明确的"过门"条件（缺 token fail-closed、只监听 127.0.0.1、SSE 四类事件、两会话并行不串……）。N 阶段同样：每个 N 都有"过门"（tauri:dev 能起、刷新恢复会话、损坏尾行不致命、seq 不回退……）。

**代码实证**：17 条反证测试覆盖并行不串味、abort 只杀目标、不挂起 promise、跨会话不串读。

**反推的思想**：一个大计划拆成里程碑，每个里程碑**自身就是一个可交付的产品**。M0 是一个"能对话的窗口"——虽然粗糙但能用。如果 M0 做完不能跑，M1 就是在没有地基的楼层上盖墙。"过门"不是 checklist 打勾，是**反证测试证明偷懒实现会红**（瑶光的复现之道在验收层面的应用）。

## 5. 诚实标注验证边界

**计划体现**：基座最后一句"Rust 外壳 src-tauri/ 因本机无 Rust/Tauri 工具链未实跑——是标准 Tauri 2.x 代码，需在装好前置的机器上验证"。N 阶段"用户已确认：本机具备 Tauri 工具链，故真实启动桌面 + 单平台打包验证纳入交付门"。

**反推的思想**：声称≠事实（瑶光第 8 条）。未验证的代码必须标注为未验证。N 阶段因为工具有了，就把验证标准升级——这就是"让另一种姿态在场"（瑶光第 5 条：换更强的条件不会让缺陷消失，只有实际验证才会）。

## 6. 安全铁律不可妥协

**计划体现**：sidecar 只绑 127.0.0.1 + token fail-closed + SSE 必带 seq 可重连可补读 + viewer 断开≠abort。N4 浏览器验证面放在最后——"新攻击面，必须在 M2/M3 成熟后再引入"。

**反推的思想**：安全边界是硬约束不是优化项。当引入新攻击面（浏览器、网络请求）时，必须等信任层（审批/反馈/回灌）成熟后再引入——不能在没建好围栏的时候放新动物进动物园（天府的 fail-closed 之道在产品规划层面的应用）。

---

## 总结

**这套方法论的核心是"先证明能跑通主线路径，再谈差异化；每步用代码行号定锚、用过门测试守底线、用诚实标注画验证边界"——范式照搬是策略，零改写是纪律，实证缺口是方法，过门测试是质量，安全铁律是底线。**
