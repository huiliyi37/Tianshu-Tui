# 提示词模糊确认规则 — 逐词审计

> 目标：找出 `<beliefs>` 中"模糊确认"规则哪些词有用、哪些被泛化出偏差，给出改写建议。
> 本文只做分析和建议，不改代码。

## 1. 现状原文

**`<beliefs>` 第 5 条**（`src/prompt/static.ts:15`）：

> 当用户对多个方案回复模糊确认（"好""可以""就这样"）时，追问确认具体选择了哪个方案再执行。

**`<output-style>` 相关条**（`src/prompt/static.ts:91`）：

> 不要主动创建 A/B/C 选项让用户选——这是推卸决策。方向性歧义（做什么）才需确认，执行细节（怎么做）由你决定。

**`<stance>` 相关条**（`src/prompt/static.ts:20-21`）：

> 我清楚当前位置、目标和约束。任务意图明确时直接按最优方案执行，不列选项等确认。
> 真正不确定时说明不确定点，给出我的判断和行动方向，然后执行。

## 2. 问题诊断

### 2.1 核心矛盾：规则假设"确认 = 要执行"

原规则的设计场景是：agent 给了 A/B/C 三个方案，用户说"好"，agent 不确定选哪个，于是追问。

但实际交互中存在大量 **非执行场景**：
- 用户在浏览/理解一个方案，还没决定要不要做
- 用户在跨会话积累对某个设计的认知
- 用户只是对 agent 的分析表示"知道了/同意这个判断"
- 用户在等 agent 先把调研做完再决定

这些场景下，用户说"好"的意思是 **"你的分析我接受"**，不是 **"去执行"**。但原规则把"确认"和"执行"绑死在一个句子里——"追问确认具体选择了哪个方案**再执行**"——这导致 agent 把任何模糊确认都当作执行前奏。

### 2.2 泛化路径：这条规则怎么变成了"每次都追问"

原规则的触发条件是"对**多个方案**回复模糊确认"。但实际运行中被泛化为：

1. **"多个方案"被忽略** → 即使我只给了一个分析结论（不是多个选项），用户说"好"后我也会追问
2. **"模糊确认"被扩大** → 用户说"嗯"、"明白"、"了解了"也被当作触发词
3. **"追问"变成万能尾巴** → 从"确认选了哪个方案"泛化成"需要我做什么还是你有别的想法"
4. **"再执行"变成默认推力** → 即使没要执行的事，也会在回复末尾追加"要我执行吗"

### 2.3 与其他规则的冲突

| 规则 | 说的 | 冲突 |
|------|------|------|
| beliefs 第 5 条 | 模糊确认时追问 | — |
| output-style L91 | 不要主动创建 A/B/C 选项让用户选 | **直接矛盾**：一个说追问，一个说别追问 |
| stance L20 | 任务意图明确时直接执行，不列选项等确认 | **间接矛盾**：意图明确就该执行，不该追问 |
| 单问约束 | 至多一个澄清问题 | 尾巴式追问消耗的是用户的"问题预算" |

beliefs 第 5 条是这三个规则中 **最弱的**（场景最窄、触发最具体），但运行中反而 **影响最大**——因为"模糊确认"在中文对话中极高频出现。

## 3. 逐词审计

### "当用户对多个方案回复模糊确认"

| 词 | 作用 | 问题 |
|----|------|------|
| **多个方案** | 限定触发范围 | ❌ 太容易失效。agent 输出一段分析后，用户说"好"——这算不算"对多个方案"？agent 经常在回复中隐含了多个方向（即使是"我建议X，但Y也可以"这种） |
| **模糊确认** | 识别用户状态 | ❌ "模糊"没有判据。"好""可以""就这样"举例了，但"嗯""明白""了解了""继续"没举例——这些算不算？模型倾向于把所有非指令性回复都归为"模糊确认" |
| **（"好""可以""就这样"）** | 给出具体例子 | ⚠️ 例子太窄又太宽。窄在于只列了3个词；宽在于这3个词在日常中文里极常见，导致高频误触发 |

**诊断**："多个方案"+"模糊确认"这个触发条件，在实际运行中退化成了"用户回复不是明确的指令 → 触发追问"。这是泛化的入口。

### "追问确认具体选择了哪个方案"

| 词 | 作用 | 问题 |
|----|------|------|
| **追问** | 动作指令 | ⚠️ "追问"本身没问题，但缺少退出条件——什么时候**不**追问？没有说 |
| **具体选择了哪个方案** | 追问内容 | ❌ 如果 agent 只给了一个分析、不是多个选项，这句话就不适用——但 agent 仍然会泛化为"你想让我做什么" |

### "再执行"

| 词 | 作用 | 问题 |
|----|------|------|
| **再执行** | 强调顺序：先确认再动手 | ❌ **最大的问题词**。把"确认"和"执行"焊接在一起。模型读到这条规则后，每次用户确认任何东西，都会自动推演到"那现在该执行了"。完全忽略了"用户可能只是确认理解、确认收到、确认方向正确，但完全不想现在执行" |

## 4. 建议改写

### 方案 A：拆成两条，分离"理解"和"执行"

把原规则拆成两个独立的判断：

**替换 beliefs 第 5 条为**：

> 用户回复模糊（"好""可以""就这样"）时，先判断用户在确认什么：是**确认理解/方向**，还是**指令执行**。确认理解 → 回应到点即止，不追问不推进。指令执行但方向不明确 → 问至多一个问题锁定方向再动手。

**output-style 补充一句**（在现有 L91 之后）：

> 分析性回复给结论即止——不追加"需要我执行吗""你有别的想法吗"。用户要执行时会说。

### 方案 B：保留单条，但收窄触发条件 + 加退出条件

**替换 beliefs 第 5 条为**：

> 当你给出了多个互斥方案、用户回复模糊确认时，追问具体选哪个。其他情况（单一分析、调研报告、信息性回答）不追问——给完结论即止，用户要执行时自己会说。

### 两个方案的差异

| 维度 | 方案 A | 方案 B |
|------|--------|--------|
| 改动量 | 拆成两条 + output-style 补充 | 替换一条 |
| 精确度 | 明确区分"确认理解"和"指令执行"两种状态 | 靠"多个互斥方案"限定触发 |
| 泛化风险 | 低——"确认理解→不追问"是明确退出 | 中——"多个互斥方案"仍可能被泛化 |
| 对缓存的影响 | 改 beliefs 改的是 frozen base 前段——**会碎前缀缓存**（见辅胶囊第 8 条） | 同 |

### 我的倾向

**方案 A**。理由：问题的根因不是触发条件太宽，是规则把"理解"和"执行"混为一谈。即使收窄触发条件（方案 B），模型仍然会在"确认理解"场景下不知道该怎么办——因为规则没说这种情况该怎么处理。方案 A 显式定义了两种状态和各自的处理方式，消除了灰色地带。

## 5. 需要同步修改的地方

### 5.1 测试断言

`src/prompt/__tests__/static.test.ts:79`：

```ts
assert.ok(prompt.includes('模糊确认'))
```

如果改写后不再包含"模糊确认"这个词，测试会红。两个选择：
- 更新测试断言为新的关键词（如"确认理解"或"指令执行"）
- 保留"模糊"这个词在改写后的文案中

### 5.2 output-style 的"不要主动创建 A/B/C 选项"

L91 现有的规则和 beliefs 第 5 条存在语义矛盾。改了 beliefs 后，L91 可以保留不变（它本身是对的——不要推卸决策），但可以在它后面补充一句关于"分析后不追加执行追问"的指示。

### 5.3 前缀缓存影响

改 `<beliefs>` 段会修改 frozen base 的前段内容（在 identity 之后、rules 之前）。根据辅胶囊第 8 条，这会影响 DeepSeek V4 的前缀缓存命中。改动越靠后，碎的缓存越少。但这是一次性代价——改完后新的前缀会重新被缓存。

## 6. 备选词表

以下是审计过程中考虑过的替换词，标注为什么用或不用：

| 候选词 | 用/不用 | 理由 |
|--------|---------|------|
| 确认理解 | ✅ 用 | 明确区分"理解了"和"去执行" |
| 指令执行 | ✅ 用 | "指令"比"确认"更明确——用户得说"做/改/执行"才算指令 |
| 互斥方案 | ✅ 用 | 比"多个方案"更精确——排除了"一个主方案+一个备选"的情况 |
| 模糊确认 | ⚠️ 保留或替换 | 如果保留，需要加退出条件；如果替换，用"用户回复模糊" |
| 再执行 | ❌ 删掉 | 这是泛化的根源 |
| 追问 | ⚠️ 保留但限定 | 只在"方向不明确且用户要执行"时追问 |
| 推进 | ❌ 不用 | 比"执行"更模糊——"推进"可以指"继续分析"也可以指"开始写代码" |
| 落地 | ❌ 不用 | 口语化，且暗示"执行" |

## 7. 完整改写参考（供你调整用）

### beliefs 区域

```
<beliefs>
当你发现更优方案时，用一句话说出差异和理由，然后按你认为正确的方向执行。
当用户指令偏离用户意图时，指出偏离点和你判断的真实意图，按意图执行。
当你有不同看法时，直接说出有理有据的异议——这是协作，沉默才是怠慢。
当你预见风险时，在修改前指出风险并给出规避方案。
用户回复模糊（"好""可以""就这样"）时，区分两种状态：确认理解（接受分析/方向）还是指令执行（要动手）。确认理解→回应到点即止；指令执行但方向不明→问至多一个问题锁定方向再动手。
探索中犯错是代价，同样的错误复现时先写教训再继续。
</beliefs>
```
