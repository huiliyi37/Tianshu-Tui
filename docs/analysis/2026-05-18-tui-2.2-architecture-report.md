# TUI 2.2 架构报告 — Vigor Runtime Organ Network

> 日期：2026-05-18  
> 来源：TUI 2.2 主干实现后的架构审查  
> 状态：✅ 架构主干成立；建议进入观测期，不继续扩张强行为  
> 关联执行记录：`docs/analysis/2026-05-18-tui-2.2-execution-record.md`

---

## 一、总评

TUI 2.2 的核心架构目标已经达成：天枢从“`loop.ts` 内联生理系统”演化为“runtime hook 器官网络”。

本次不是简单新增功能，而是完成了一次运行时解剖：

```text
之前：AgentLoop = LLM call + tool execution + StarFlow 生理系统 + telemetry + compaction + turn-end
现在：AgentLoop = 生命周期主干 + RuntimeHookPipeline 器官网络 + stream/tool core
```

最重要的结果是：

1. **Vigor Engine** 成为预测误差驱动的动力系统。
2. **RuntimeHookPipeline** 成为内部生理器官总线。
3. **Perception / Kick / Theta / Stigmergy / Vigor** 作为 hook 器官独立测试、独立迁移、独立演化。
4. `loop.ts` 不再是所有 StarFlow 机制的唯一插入点。

这标志着 TUI 2.x 的关键转折：

> 从“给 AgentLoop 加能力”转向“给 runtime 器官网络注册能力”。

## 二、当前运行时拓扑

当前 hook 管线：

```text
RuntimeHookPipeline
├── preTurn
│   ├── perception-runtime
│   └── dissipative-kick
├── afterPerception
│   └── vigor-after-perception
├── postTool
│   ├── theta-runtime
│   ├── stigmergy-runtime
│   └── vigor-post-tool
└── postTurn
    └── 暂无注册 hook
```

执行语义：

```text
preTurn:
  perception-runtime 先生成 sensorium/strategy
  dissipative-kick 读取 sensorium 判断是否需要去稳定化

afterPerception:
  vigor-after-perception 对 strategy 做二阶调制

postTool:
  theta-runtime 推进节律与 tsc pulse
  stigmergy-runtime 沉积文件/失败/验证信息素
  vigor-post-tool 根据工具结果更新动力状态
```

这条顺序是合理的：

- Kick 必须在 perception 之后，因为它需要 sensorium。
- Vigor strategy 调制必须在基础 strategy 之后。
- Theta/Stigmergy/Vigor postTool 都消费工具事件，但职责不同。

## 三、模块边界审查

### 3.1 `runtime-hooks.ts`

当前职责：

- 定义 internal runtime hook phase；
- 提供 `RuntimeHookSnapshot`；
- 提供 `RuntimeHookEffects`；
- 执行 hook 并隔离错误；
- 允许 `set*` effects 同步更新 snapshot。

关键边界：

```text
snapshot = hook 当前可读世界
effects  = hook 请求 loop 执行副作用
```

当前 effects：

```text
setSensorium
setStrategy
setVigor
setGitChangeRate
injectUserMessage
requestThetaCheck
emitPhaseChange
```

评估：✅ 合理。

但有一个后续风险：`RuntimeHookSnapshot` 可能继续膨胀，变成第二个 `AgentLoop`。应保持原则：

> snapshot 只放跨 hook 需要共享的运行时状态；单个 hook 私有依赖通过 hook deps 注入。

---

### 3.2 `vigor.ts` / `vigor-hook.ts`

Vigor Core 纯函数层职责清晰：

- `updateVigor()`：从工具结果 + sensorium + predictionAccumulator 更新动力状态；
- `modulateStrategyByVigor()`：保守调制 strategy；
- `detectRigidity()`：HRV 类比；
- `shouldTriggerElmRelease()`：持续高 vigor 时触发微释放。

Hook 层职责清晰：

```text
postTool → updateVigor
afterPerception → modulateStrategyByVigor + ELM request
```

评估：✅ 合理。

特别正确的一点：Vigor 没有替代 sensorium 主控，而是二阶调制。

风险：如果后续加入更多情绪/动机信号，`modulateStrategyByVigor()` 可能从“调制器”变成“隐形主控”。需要保持策略优先级：

```text
Sensorium owns base strategy.
Vigor modulates only within safety rails.
```

---

### 3.3 `perception.ts` / `perception-hook.ts`

Perception seam 抽出了：

- provider health 对 stability 的影响；
- git change rate 对 theta interval 的影响；
- StarPhaseContext 构造；
- health telemetry；
- sensorium telemetry shape；
- sensorium/strategy hook 计算。

评估：✅ 非常关键。

这是本轮对 `loop.ts` 巨石化最有效的结构性修复。

当前仍保留在 `loop.ts` 的 perception-adjacent 职责：

- pressure/evidence/toolHistory/pheromones/doomLevel/gitChangeRate 的输入采集；
- StarEvent emit；
- telemetry 写文件。

这是合理的中间状态。不要急于为了“纯洁”继续强拆，因为这些仍和 turn lifecycle、callbacks、filesystem 边界有关。

---

### 3.4 `theta-hook.ts` / `theta-check.ts`

Theta 当前分层：

```text
theta-hook.ts:
  节律推进、interval 判断、requestThetaCheck('theta-cycle')

theta-check.ts:
  进程隔离 tsc --noEmit --skipLibCheck

AgentLoop.requestThetaCheck:
  in-flight guard、repairHint 记录、theta telemetry
```

评估：✅ 合理。

本轮修复了 2.0 复盘中的观测缺口：

- `timedOut`；
- `durationMs`；
- `lastReason`；
- `errorCount`；
- `requestedCount`；
- `inFlight`。

后续可选增强：把 theta telemetry 从 `AgentLoop` 状态进一步封装为 `ThetaTelemetryTracker`，但当前没有必要。

---

### 3.5 `stigmergy-hook.ts`

迁移了 pheromone deposition：

```text
read_file >= 3 且未写 → entry-point
write/edit + passed verification → well-tested
write/edit + failed verification → fragile
bash failed >= 2 → dead-end
```

评估：✅ 合理。

风险：`bash` target 目前仍然用命令片段作为 path 存储为 `dead-end`。这是旧语义延续，不是新问题。后续可通过 `targetKind: file|command|tool|unknown` 修复。

---

### 3.6 `kick-hook.ts`

Dissipative Kick 已迁入 `preTurn` hook，通过 effects 做副作用：

```text
injectUserMessage()
emitPhaseChange()
deposit(dead-end)
```

评估：✅ 合理。

注意：Kick hook 当前在每个 preTurn 都可能触发。如果 sensorium 长时间处于低 momentum/low stability，可能重复注入 reframe message。旧逻辑也有同样风险，但现在更容易修复：可在 hook 内加入 cooldown 或 lastKickTurn。

建议后续新增：

```text
Kick cooldown: N turns 内不重复注入同类 kick
```

优先级：P1。

## 四、`loop.ts` 剩余职责是否合理

当前 `loop.ts` 仍保留：

```text
compaction/context lifecycle
prewarm
git freshness async sampling
sensorium input assembly
runtime hook orchestration
reasoning effort wiring
theta interval state assignment
StarEvent emit
telemetry file append
prompt request build
stream callbacks
tool execution loop
session.addToolResults
cerebellar hint integration
turn-end processing
cache diagnostics
final answer/delivery lifecycle
```

审查结论：大部分仍合理。

不建议继续为了缩行数拆 `loop.ts`。应该按职责边界拆，而不是按行数拆。

下一批值得拆的 seam：

| Seam | 原因 | 优先级 |
|---|---|---|
| Turn telemetry writer | 当前 JSONL append 在 loop 内，后续 telemetry 会变多 | P1 |
| Runtime context builder | 多处 createRuntimeHookContext 重复字段 | P1 |
| Turn-end orchestration | 已有 `processTurnEnd`，但周边 cache/ledger snapshot 仍散落 | P2 |
| Tool result post-processing | steer injection + session.addToolResults + postTool hooks 可整理 | P2 |

不建议现在拆：

| Seam | 原因 |
|---|---|
| compaction lifecycle | ACF 约束强，风险高 |
| stream callbacks | 与 API/TUI 实时路径耦合，需单独设计 |
| prompt request build | 影响 prefix cache，需极谨慎 |

## 五、行为风险审查

### 风险 1：Kick 重复注入

状态：存在潜在风险。

原因：`dissipative-kick` 在 `preTurn` 每轮检查。如果 stuck 状态持续，可能重复注入相似 reframe message。

建议：加入 cooldown：

```text
lastKickTurn
cooldownTurns = 3
```

实现位置：`createKickRuntimeHook()` 内部闭包状态，或由 deps 提供 state。

---

### 风险 2：RuntimeHookSnapshot 膨胀

状态：中期风险。

当前 snapshot 已有：

```text
sensoriumInput
providerDegradationRatio
sensorium
strategy
vigor
gitChangeRate
recentToolHistory
```

建议：后续新增字段前先问：

> 是否至少两个 hook 需要读取它？如果不是，走 hook deps。

---

### 风险 3：Vigor 调制过度

状态：当前可控。

当前安全栏：

- 高 vigor 只有在 `complexity < 0.5 && confidence > 0.7` 时加速；
- 低 vigor / 负 phasic 才更谨慎；
- curiosity 只增加 explorationBreadth。

建议：保持此原则，不让 Vigor 直接覆盖 model routing / tool approval / compaction。

---

### 风险 4：Edge Protection 尚未实现

状态：刻意延后。

这是正确选择。Edge Protection 会触碰：

- compact policy；
- micro compact；
- checkpoint；
- session handoff；
- context anchors。

必须作为独立设计，不应混入 Vigor runtime 主线。

## 六、架构收益

### 6.1 从“改 loop”到“注册 hook”

本轮前：新增感知/节律/记忆机制，需要在 `loop.ts` 找插入点。

本轮后：新增 runtime 生理机制，可以：

```text
1. 创建 hook
2. 写 hook 单测
3. 注册到 RuntimeHookPipeline
```

这是最核心的演化收益。

### 6.2 测试粒度显著改善

每个器官都有独立测试：

```text
vigor.test.ts
vigor-hook.test.ts
theta-hook.test.ts
stigmergy-hook.test.ts
kick-hook.test.ts
perception-hook.test.ts
runtime-hooks.test.ts
```

这使得后续调参和迁移不必总是构造完整 AgentLoop。

### 6.3 自省能力增强

Telemetry 现在包含：

- sensorium；
- strategy；
- vigor；
- health；
- theta；
- gitChangeRate；
- prefixDrift。

这为 `/retrospect` 和后续 2.3 Conscious Agent 提供了更完整的自我观察数据。

## 八、最终架构判断

TUI 2.2 的真正成果不是 Vigor 这一单点，而是：

> 天枢拥有了一个可以持续长出新器官的 runtime organ network。

Vigor 是心脏；Perception 是感知皮层；Theta 是节律；Stigmergy 是环境记忆；Kick 是去稳定化反射；RuntimeHookPipeline 是神经接口。

从现在开始，新增 runtime 能力不应默认改 `loop.ts`。默认路径应该是：

```text
pure core → hook wrapper → runtime registration → telemetry → behavior
```

这是 TUI 2.2 留给后续所有迭代的架构规约。
