## 核心发现：98.3% 天花板分析

### 98.3% 到 99% 的差距

当前最佳：98.3%（input=92,599, create=1,591）
99% 目标需要：create ≤ 926
差距：**需削减 665 tokens/轮**

### 持久性超额分析

每个稳态轮次都存在 **~1000–1200 tokens 的 prefix 超额**（cacheCreate - inputDelta）：

| 过渡 | inputDelta | cacheCreate | 超额 | 含义 |
|------|-----------|-------------|------|------|
| T6→T7 | 589 | 1,733 | 1,144 | prefix 丢失 1,144 tokens |
| T8→T9 | 602 | 1,591 | 989 | prefix 丢失 989 tokens |
| T9→T10 | 367 | 1,591 | 1,224 | prefix 丢失 1,224 tokens |

### 根因：Standalone Appendix 位置偏移

```
Turn N 请求:   [sys, ..., lastUserMsg, appendix]
Turn N+1 请求: [sys, ..., lastUserMsg, asstN, toolN, resultN, lastUserN+1, appendix]
                      ↑ prefix 命中到这里 ↑              ↑ appendix 位置变了 ↑
```

DeepSeek exact-prefix cache 是 **位置敏感的**。appendix 虽然内容相同，但在 Turn N+1 中位于不同的字节偏移位置（因为中间插入了新的 assistant/tool 消息），所以 appendix 的字节无法从缓存中命中。

**每次轮转，appendix 的内容（~500–1000 tokens）都需要重新 cacheCreate。**

这是 standalone appendix 架构的**固有物理限制**——不是 bug，是 exact-prefix cache 的工作方式决定的。

## 结论

1. **P1b 优化改善明显**：稳态峰值从 97.0% 提升到 **98.3%**（+1.3pp）
2. **99% 在当前架构下不可达**：standalone appendix 的位置偏移导致 ~1000 tokens/轮 的固有开销
3. **大工具输出仍是主要 drop 原因**（非 prefix 断裂）
4. **与 Pre-P1 的 99.3% 对比不公平**：Pre-P1 的 "高命中" 是以 "断裂到 56%" 为代价的

### 可能的改进方向

要突破 99%，需要改变 appendix 的位置策略：
- **Option A**: 将 appendix 放在 lastUser 消息之前（改变消息排序）
- **Option B**: 将动态内容合并回 lastUser 的 trailer，但用固定大小占位符
- **Option C**: 接受 ~98% 作为 standalone appendix 架构的固有上限
