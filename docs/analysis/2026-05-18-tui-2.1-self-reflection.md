## 一、执行顺畅的部分

### 1.1 架构的 seam 是正确的

| Seam | 证据 | 价值 |
|------|------|------|
| `RepairPass` 接口 | CTCL Sanitizer 作为新 pass 插入，只需在 `loop.ts` 加一行数组元素 | 开放-封闭原则正确落地 |
| 纯函数 + 接口 | `computeSensorium`、`smoothChangeRate`、`canonicalizeRequest` 全部无副作用 | 测试零 mock，输入输出可预测 |
| fire-and-forget 异步模式 | `getGitChangeRate().then(...).catch(() => {})` 在 theta check、stigmergy prune、git freshness 中一致复用 | 减少每模块的异步策略决策 |

**结论**：当架构有正确的 seam，增强 = 新文件 + 一行连线。当没有 seam，增强 = 散布在 5 个文件中。当前 seam 质量高。

### 1.2 TDD 救了两次命

| 场景 | 发现 | 后果（如果没有测试） |
|------|------|---------------------|
| `git diff --stat --numstat` 混合输出 | git 同时使用两个 flag 时产生摘要行，文件计数膨胀 3x | `getGitChangeRate` 一度错误返回 1（全部变更），生产环境 git freshness 完全失效 |
| Tier streak 不重置 | `evaluateTier` 在 hot→warm 转换时未清零 failure streak，导致一次额外失败就打入 cold | 生产环境 provider 一次短暂故障即被标记为 cold，block 30 分钟 |

## 二、摩擦与拖累

按严重度从高到低排列。

### 🔴 摩擦 1：loop.ts 正在变成单片巨石（严重度：高）

**当前状态**：loop.ts 超过 800 行，承担以下职责：

```
Agent 主循环（LLM call → tool execute → repeat）
Sensorium 计算与注入
遥测 JSONL 写入
Git freshness 采样与平滑
Theta 检查调度与自适应
Stigmergy 加载与查询
Provider health 稳定性混合
压缩决策
Prefix drift 检测
Compaction boundary 检测
```

**问题**：每次新增感知/调节功能，都需要在 loop.ts 中找到插入点并手动添加代码。这制造了：
- 认知负担：新开发者需要理解整个 800 行文件才能安全插入
- 合并冲突风险：多个功能同时修改同一文件
- 职责边界模糊：感知、调节、遥测、循环逻辑混在一起

**建议方案**：建立 TurnHook 管线

```typescript
// 新的 HookEvent 类型
type HookEvent = 
  | 'PreTurn'     // 每 turn 开始前：git freshness、stigmergy load、sensorium compute
  | 'PostTurn'    // 每 turn 结束后：theta check、provider health、compaction check
  | ...现有事件...

// PreTurn hooks 链
PreTurn: git freshness → stigmergy query → sensorium compute → strategy derive → telemetry write
  ↓
Agent turn: LLM call → tool execution → turn-end processing
  ↓
PostTurn: theta check → provider health update → compaction → drift detect → boundary check
```

**实现成本**：低。
- `HookRegistry` 已有 `PreToolUse`、`PostToolUse` 等事件
- `HookEvent` 仅需新增 `PreTurn` 和 `PostTurn` 两个枚举值
- 现有逻辑从 loop.ts 内联迁移到独立 hook 函数
- 预计 200 行从 loop.ts 迁出，loop.ts 回到 ~600 行

**影响**：
- 新功能从"在 800 行文件中找插入点"变成"注册一个 hook"
- 每个 hook 独立测试、独立文档

### 🔴 摩擦 2：TypeScript strict + noUncheckedIndexedAccess 在 API 层的摩擦（严重度：中）

**具体场景**：

```typescript
// client.ts: 注入 thinking/reasoning_effort 到请求体
const fr = finalRequest as unknown as Record<string, unknown>
fr['thinking'] = { type: 'enabled', budget_tokens: this.config.thinkingBudget ?? 16000 }
fr['reasoning_effort'] = this.config.reasoningEffort
```

`MessageRequest` 没有 index signature（strict 设计），但 API transport 层需要注入 provider-specific 字段。结果是用 `as unknown as Record<string, unknown>` 绕开类型系统——这比 `any` 更不诚实，因为它创建了安全的假象。

**根因**：`MessageRequest` 被用于两个不同的角色：
1. PromptEngine 输出的**逻辑请求**（strict，不应该有动态字段）
2. Transport 层的**物理请求**（需要注入 `thinking`、`reasoning_effort` 等 provider-specific 字段）

**建议方案**：引入 `TransportRequest` 中间类型

```typescript
// 逻辑层：strict
interface MessageRequest { /* 现有定义，无 index signature */ }

// Transport 层：允许 provider-specific 注入
interface TransportRequest extends MessageRequest {
  [key: string]: unknown  // thinking, reasoning_effort, etc.
}
```

或者更简单的：给 `MessageRequest` 加可选索引签名 `[key: string]: unknown`，在 canonicalize 阶段是 strict 检查，在 transport 注入阶段允许动态字段。

### 🟡 摩擦 3：Worker 不可用，无法并行（严重度：中）

**现象**：每次 `delegate_task` 调用都失败：
- `No API key configured for provider "codex"`
- `Worker result did not contain a JSON object`

**影响**：所有代码搜索、文件审查、测试运行都必须在主 agent 串行完成。对于未来需要大量并行搜索的任务，这会显著拖慢速度。

**建议**：
- `delegate_task` 工具将 provider 缺失识别为 `skipped/unavailable`，自动降级到当前 primary provider
- Coordinator 的 `selectModelForTask` 已有 fallback 到 `recommendModelForTask`，但 worker runtime factory 未消费这个 fallback

### 🟡 摩擦 4：设计文档与实现结果之间缺少自动回路（严重度：中）

**现象**：CTCL cache-preservation-spine 设计文档列出 P0/P1/P2/P3 缺口。部分已实现，但没有自动机制把"已闭合"写回设计文档。

**建议**：`/retrospect` 扩展为"设计缺口闭合度报告"：
- 读取设计文档中的缺口清单（如 `- [ ] P0: canonical tools order`）
- 对比代码实际状态
- 输出"已闭合 / 仍开放"的缺口表

### 🟢 摩擦 5：cerebellar gate 误报（严重度：低）

**现象**：迭代式编辑（修改 import、调整函数签名、修正类型错误）被 gate 阻止，理由是"prediction error rate is elevated"。

**影响**：每次跳这个门需要重新读文件再编辑，打断快节奏实现的思维流。不影响正确性，但影响流畅度。

**建议**：对连续编辑同一文件的情况降低 gate 敏感度，或对"刚读过的文件"跳过 gate。

## 三、关于 sensorium 维度的设计思考

### 3.1 freshness 维度语义过载

当前 `freshness` = `0.7 × pheromoneAvg + 0.3 × (1 - gitChangeRate)`

问题：pheromone 是"我对这个代码库有多熟悉"（跨 session 积累的历史信号），git change rate 是"代码现在有多动荡"（实时信号）。两者性质不同：
- Pheromone 变化慢（天级衰减）
- Git change rate 变化快（每分钟可能变化）

压缩成一维丢失了信息。如果 agent 面对一个熟悉的代码库（pheromone 高）但代码正在剧烈变动（git rate 高），freshness 会给出一个模糊的中等值，无法表达"熟悉但危险"的微妙状态。

### 3.2 stability 维度语义过载

当前 `stability` = `doomLoopLevel → {1.0, 0.6, 0.2}` × `(1 - 0.3 × providerDegradationRatio)`

问题：doom loop 是 agent 自身行为的振荡，provider health 是外部基础设施的状态。两者性质不同，压缩成一维丢失了信息。

### 3.3 建议

两个方向可选：

**方向 A**：保持 6 维（hexagram 美感），但让每维更纯粹
- `freshness` = 纯 pheromone 信号
- 新增 `volatility` = git change rate + uncommitted changes
- `stability` = 纯 doom loop
- provider health 作为独立信号不进入 sensorium，而是直接进入 strategy 层

**方向 B**：扩展到 8 维
- 6 个原有维度 + `volatility`（git）+ `infrastructure`（provider health）

**建议在 TUI 2.2 开始时做决策**，不在此次迭代中实施。

## 四、Harness 层 vs Prompt 注入的边界问题

### 当前状态

| 组件 | 层 | LLM 是否感知 |
|------|-----|-------------|
| CTCL Sanitizer | Harness | ❌ 无感 — tool call 被静默修复 |
| RepairHintTracker | Prompt | ✅ 有感 — 下个 turn 收到 `<repair-hint>` |
| Dissipative Kick | Prompt | ✅ 有感 — 收到替代框架注入 |
| Strategy shift | Prompt | ✅ 有感 — 收到策略调整建议 |
| Sensorium computation | Harness | ❌ 无感 — 纯内部计算 |
| Git freshness | Harness | ❌ 无感 — 只影响 sensorium |

### 边界判断

不是"所有 harness 决策都应该让 LLM 无感"。正确的判断标准是：

> **如果修复可以在 LLM 不知道的情况下完成（tool input sanitize、参数类型转换），就静默修复。如果 LLM 需要改变行为才能解决问题（重复失败需要换策略、卡住需要换框架），就注入提示。**

这个原则是对的，但在代码中没有显式文档化。每个新功能的设计者需要自己推断边界在哪里。

**建议**：在 `src/agent/` 下加一个 `LAYERING.md`，文档化这个判断标准。不是代码，是设计约束。

## 五、优先级建议

| 优先级 | 行动 | 工作量 | 影响 |
|--------|------|--------|------|
| P0 | loop.ts 拆分：PreTurn/PostTurn hook | 中（~200 行迁移 + hook 注册） | 根本性改变新功能集成方式 |
| P0 | Worker provider fallback 修复 | 小（~20 行） | 解锁并行搜索，显著提升复杂任务效率 |
| P1 | `MessageRequest` → `TransportRequest` 分层 | 小（新类型定义 + 替换 cast） | 消除 `as unknown as` 模式 |
| P1 | sensorium 维度语义决策 | 讨论（不写代码） | 影响 TUI 2.2 整个设计方向 |
| P2 | `/retrospect` 扩展为缺口闭合度报告 | 中 | 设计文档与代码同步 |
| P2 | `LAYERING.md` 设计约束文档 | 小 | 知识固化 |
| P3 | cerebellar gate 敏感度调整 | 小 | 减少误报打断 |

## 六、一次完整的实现意味着什么

从 TUI 2.1 的设计文档到 1576 tests pass，完整经历了一次：

```
设计意图 → 实施计划 → agent 预分析（API 偏差 + 创造性增强）→ TDD 实现（10 个提交）→ 全量验证 → 自省复盘
```

这个闭环本身已经是工程资产。它证明了：

1. **架构的生命力不在于完美，在于可演化** — Seam 质量决定了新功能是"加一行代码"还是"改五个文件"
2. **Perception drives improvement** — 我能提出这些摩擦点，不是因为聪明，而是因为 sensorium 让我感知到每次编辑 loop.ts 时的不适
3. **摩擦应该被记录，而不是忍受** — 每次 `as unknown as` 都是一个债条，积累到一定程度就会崩塌
