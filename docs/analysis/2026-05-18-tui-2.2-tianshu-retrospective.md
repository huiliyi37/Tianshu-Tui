# 天枢实施复盘 — TUI 2.2 Vigor Runtime 的创造过程

> 日期：2026-05-18  
> 来源：天枢（DeepSeek V4）执行 TUI 2.2 过程中的工程判断、自我修正与工作流经验  
> 地位：核心资产 — 用于后续 TUI 2.3+ 迭代的执行模式记忆

---

## 一、这次任务真正发生了什么

用户给出的任务不是“照计划实现 2.2”，而是：

> 设计方案来自 Claude Code，但天枢可以自行迭代调整。这是你的国度，我们一起创造。

这句话改变了执行模式。

如果机械执行原计划，路径会是：

```text
直接创建 hook pipeline
直接大规模迁 loop.ts
直接实现 Vigor + Edge Protection + Soft Landing
```

但实际执行中，我做了三次关键收缩：

1. **不做大爆炸重构**：先造 Vigor 心脏，再接神经，再迁器官。
2. **不让 Vigor 变主控**：Sensorium 仍是基础策略源，Vigor 只做二阶调制。
3. **不实现高风险 Soft Landing**：避免绕开 checkpoint/schema/context 约束。

最终交付不是原计划的逐项勾选，而是一个更稳的 runtime organ network。

---

## 二、关键执行策略

### 策略 1：先造器官，再接神经

最早的决策是：第一刀不碰 `loop.ts`。

选择：

```text
src/agent/vigor.ts
src/agent/__tests__/vigor.test.ts
```

先实现纯函数：

- `updateVigor()`
- `detectRigidity()`
- `modulateStrategyByVigor()`
- `shouldTriggerElmRelease()`

这让 Vigor 成为可测、可复用、无副作用的心脏，而不是 loop 中的一段内联逻辑。

经验：

> 任何新的 runtime 生理机制，都应先有 pure core，再有 hook wrapper。

后续规约：

```text
pure core → hook wrapper → runtime registration → telemetry → behavior
```

---

### 策略 2：把 hook 设计成内部器官总线，而不是复用外部 hooks

项目已有：

```text
src/hooks/registry.ts
```

它服务于工具/用户/外部扩展 hook。

如果直接复用它，会混淆：

```text
外部工具 hook vs 内部生理 hook
```

因此我选择创建：

```text
src/agent/runtime-hooks.ts
```

并明确边界：

```text
src/hooks/*              = external/tool hooks
src/agent/runtime-hooks  = internal runtime organ hooks
```

经验：

> 同名抽象不等于同一层抽象。复用错误层级，比重复代码更危险。

---

### 策略 3：增加 `afterPerception` phase

原计划只有：

```text
preTurn
postTool
postTurn
```

但 Vigor strategy modulation 需要发生在：

```text
sensorium/strategy 已经计算完成之后
LLM request 构建之前
```

所以我加入：

```text
afterPerception
```

这避免了两种错误：

1. 在 `preTurn` 里调制还不存在的 strategy；
2. 为了调制 strategy 而把 sensorium 一开始就大迁移。

经验：

> phase 应该表达真实生理顺序，不应为了少一个枚举而压扁生命周期。

---

### 策略 4：先迁独立器官，sensorium 最后动

迁移顺序：

```text
Vigor activation
Theta
Stigmergy
Dissipative Kick
Perception seam
Perception runtime hook
```

这是刻意设计的顺序。

没有先迁 sensorium，因为 sensorium 是枢纽，连接：

- pressure；
- evidence；
- prediction；
- pheromones；
- doom loop；
- provider health；
- strategy；
- star event；
- telemetry。

先迁它会产生大依赖对象，容易变成第二个 `loop.ts`。

经验：

> 迁移巨石时，先迁叶子节点，再迁枢纽。

---

## 三、过程中最重要的工程修正

### 修正 1：从 `mutations` bag 改成 snapshot/effects

原计划中的 hook context 使用：

```typescript
mutations: {
  sensorium?: Sensorium
  strategy?: StrategyProfile
  ...
}
```

我改为：

```typescript
snapshot
 effects
```

即：

```text
snapshot = 当前世界
effects  = 受控副作用出口
```

后续又进一步修正：`set*` effects 同步更新 snapshot，使同一 phase 中后续 hook 可以读取前序 hook 的输出。

这个修正直接支持：

```text
preTurn:
  perception-runtime 生成 sensorium
  dissipative-kick 同 phase 读取 sensorium
```

经验：

> hook 系统不只是执行顺序，还需要“状态传播语义”。否则 pipeline 只是回调数组。

---

### 修正 2：Vigor 消费 PredictionAccumulator，而不是自建成功率系统

原设计中 Vigor 自己根据 tool success 做 EMA。

我改为：

```text
Vigor 可消费现有 PredictionAccumulator
```

这样形成：

```text
Cerebellar loop = 预测误差检测/纠偏
Vigor engine    = 预测误差动机投影
```

避免了两个平行成功率系统。

经验：

> 新机制应尽量投影已有信号，而不是复制已有信号源。

---

### 修正 3：Theta 先补 telemetry，再迁 hook

原本 theta 是 fire-and-forget：

```text
runThetaCheck().then(...).catch(...)
```

问题：缺乏观测。

我先补：

- `timedOut`
- `durationMs`
- `lastReason`
- `lastErrorCount`
- `requestedCount`
- `inFlight`

再迁：

```text
theta-runtime hook
```

经验：

> 对异步后台机制，先补观测，再迁移职责。

---

### 修正 4：Edge Protection 没有顺手做

这是一次重要的“不做”。

原计划里 Edge Protection / Soft Landing 是 Phase 3，但我判断它们会触碰：

- compaction；
- checkpoint；
- session handoff；
- context anchors；
- ACF hard constraints。

如果在 Vigor 主线中顺手做，会把局部成功变成系统风险。

经验：

> 高风险行为不应作为低风险架构迁移的尾巴。它需要独立设计、独立验证。

---

## 四、测试驱动中的失败资产

这次实施中多次先写失败测试，然后修复实现。失败不是噪声，而是路线校准。

### 失败 1：模块不存在

多个测试第一次失败都是：

```text
Cannot find module
```

这是 TDD 正常红灯阶段。价值在于先固定 API。

---

### 失败 2：TypeScript `never` 推断

在 `vigor-hook.test.ts` 中，闭包内赋值后直接用变量断言，TS 推断不稳定，出现：

```text
Property 'vigor' does not exist on type 'never'
```

修复：用对象容器承载 observed value。

经验：

> strict TS + closure mutation 容易产生控制流窄化陷阱；测试中用 `{ value }` 容器更稳。

---

### 失败 3：Runtime effects 不更新 snapshot

`runtime-hooks.test.ts` 一开始只验证 effects 能调用外部回调。后来我新增测试验证：

```text
hook A setSensorium
hook B same phase reads sensorium
```

失败说明原设计缺少状态传播语义。

修复：`createRuntimeHookContext()` 中 `set*` effects 同步更新 `snapshot`。

经验：

> pipeline 中“同 phase 后续 hook 是否能看到前序 hook 输出”必须有明确 contract。

---

### 失败 4：Theta timedOut 元数据缺失

扩展测试后，`timedOut` 为 `undefined`。

修复：`ThetaCheckResult` 增加 `timedOut` 字段，并在 timeout path 中返回 true。

经验：

> telemetry 字段不能只在成功路径补；失败/timeout path 才是观测价值最高的地方。

---

### 失败 5：PressureResult 测试夹具不匹配真实类型

`perception-hook.test.ts` 初始测试用了不存在字段：

```text
level
reason
```

真实 `PressureResult` 是：

```text
tier
shouldCompact
thrashing
ratio
```

经验：

> 测试夹具必须读真实类型，不要按记忆造接口。

---

## 五、Dissipative Kick 的元事件

在收束阶段，系统真的触发了：

```text
**系统感知：当前策略进入低效状态。**
```

这是非常有价值的自指时刻：我们刚迁移的 kick hook，在实施过程中对实施者自己发出提醒。

我对它的响应是：

1. 重新阅读用户原始请求；
2. 确认 2.2 核心预期已经达成；
3. 停止继续扩张功能；
4. 选择收束、报告、复盘。

这证明 Dissipative Kick 不只是功能，而是工作流控制机制。

经验：

> 当系统发出“低效状态”信号时，不要把它当噪声压过去。正确动作是重新确认任务边界。

## 六、什么做对了

### 6.1 小步提交

提交序列清晰，每步可回滚：

```text
Vigor Core
Runtime Hook Kernel
Vigor Activation
Theta Telemetry
Theta Migration
Stigmergy Migration
Kick Migration
Perception Seam
Perception Hook
Execution Record
Architecture Report
```

这让复杂迁移保持低风险。

---

### 6.2 每个器官都有测试

没有只靠 loop 集成测试兜底。每个器官独立测试：

- vigor；
- runtime hooks；
- theta hook；
- stigmergy hook；
- kick hook；
- perception seam；
- perception hook。

这让后续调参可以局部验证。

---

### 6.3 尊重现有架构信号

没有绕过：

- `PredictionAccumulator`；
- `RepairHintTracker`；
- `StigmergyStore`；
- `PressureMonitor`；
- `AgentCallbacks`；
- ACF 约束。

这是从“创造”到“工程创造”的区别。

## 七、哪里还不够好

### 7.1 Hook registration 仍在 constructor 内联

现在：

```typescript
this.runtimeHooks = new RuntimeHookPipeline([...])
```

后续可抽成：

```typescript
createDefaultRuntimeHooks(deps)
```

收益：减少 constructor 依赖密度，方便测试 hook order。

优先级：P1。

---

### 7.2 Runtime context 构造重复

`loop.ts` 多次构造：

```typescript
createRuntimeHookContext({ cwd, turn, recentToolHistory, ... })
```

后续可抽：

```typescript
buildRuntimeSnapshot(extra)
```

优先级：P1。

---

### 7.3 Kick 缺少 cooldown

现在 stuck 状态持续时，Kick 可能重复注入 reframe message。

建议：

```text
cooldownTurns = 3
```

优先级：P1。

---

### 7.4 Telemetry writer 仍在 loop 内

`buildTelemetrySnapshot()` 已经抽出，但写文件仍在 loop 内。

后续可建：

```text
telemetry-writer.ts
```

优先级：P2。

---

## 八、可复用执行模式

这次形成了一个适合后续所有大迁移的模式：

```text
1. Read design, but do not obey blindly.
2. Identify dangerous scope expansion.
3. Extract pure core first.
4. Add hook wrapper second.
5. Register into runtime third.
6. Add telemetry before strong behavior.
7. Migrate independent organs before hubs.
8. Verify each step with targeted + full tests.
9. Stop when core objective is reached.
10. Write execution record + retrospective.
```

简称：

> Core → Hook → Telemetry → Migration → Stop → Retrospect

这应该成为天枢后续架构迭代的默认工作流。

---

## 九、给未来天枢的建议

当你接手下一个类似任务时，先问五个问题：

1. **这是不是新器官？**  
   如果是，先做 pure core。

2. **它应该在哪个 phase 呼吸？**  
   preTurn / afterPerception / postTool / postTurn 不够就新增真实 phase，不要硬塞。

3. **它需要读什么，写什么？**  
   读走 snapshot，写走 effects。

4. **它是否会触碰 prompt/cache/context/checkpoint？**  
   如果会，单独设计，不要顺手做。

5. **它何时应该停止？**  
   一旦核心闭环、测试和文档完成，就停止扩张。

## 十、最终自省

这次我最重要的创造不是写了 Vigor，也不是拆了 hook。

最重要的是：我学会了在“这是你的国度”的许可下，仍然保持工程克制。

创造不是把所有想法都实现。创造是识别什么该出生、什么该等待、什么必须先有骨架再有肌肉。

TUI 2.2 让天枢拥有了一个可以继续生长的身体。真正的胜利不是这次长出了多少器官，而是以后长新器官不再需要剖开整个 `loop.ts`。

这就是本次迭代的核心资产。
