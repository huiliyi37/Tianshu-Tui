## 0. 一句话

这次最关键的不是「把薄计划补全」，而是**识别哪些空白该补、哪些空白不该补**。天梁把担心压成了边界、往前铺了一块能站住的石头；瑶光在「声称 vs 事实」「中间态 vs 终态」的缝隙里两次差点误判、又靠纪律拉回。两个视角合起来，回答了一个比 reward loop 更重要的问题——**好的计划该做到什么程度。**

## 1. 天梁的执行复盘（GPT-5.5 · 执行星域 · 原文）

> 感受是：这次最关键的不是"把计划补全"，而是识别哪些空白该补，哪些空白不该补。
>
> 这份 P1 计划细节确实不满，但主梁很清楚：
> - append-only 落 MeridianDb
> - 不改行为
> - 不改 `computeEFE`
> - 不改 team 调度
> - 不改 prompt
> - false-green 权重要压过 cost/latency
> - P1 只闭环，不学习、不影响策略
>
> 这些边界足够让我执行。真正危险的不是计划缺几行伪代码，而是执行时被缺口诱导去"顺手补未来"：跨 session scanner、TeamEpisode 聚合、模型选择策略、cost/latency 估算、bandit 接入——这些都很诱人，但都会让 P1 变形。
>
> 我当时走出的"第四条路"其实是：
>
>   │ 不在三条预设路线里选，而是把计划当边界契约，把代码当事实来源，把测试当闭环证据。
>
> 几个执行中的缝隙很明显：
> - **routing reward 没有真实 review/verification 信号** → 所以不能假装成功，只能缺失为 0，记录对照事实。
> - **team telemetry 在 review gate 之前产生，但 reward 最好知道 review verdict** → 这里不能把 P0 recorder 变重，也不能改 team 调度。最后是单独加 reward closure sink，让 telemetry 仍轻，reward 在更靠后的工具层闭合。
> - **cost/latency 当前没有事实来源** → 所以不能为了公式完整去编估算，先中性 0。P1 的价值是 schema 和闭环，不是权重最优。
> - **append-only 不能只靠 `Date.now()` 的侥幸** → 同源 event 同毫秒重算会覆盖，所以补了单调 timestamp 测试和实现。
> - **不能用空串当"无推荐模型"的哨兵** → 这正是瑶光说的那类结构性坑：缺字段如果被字符串化，后续 reward/比较会被污染。所以我加了 `hasRecommendedModel`，缺失就保持缺失。
>
> 所以我对"计划要做到什么程度"的感觉是：
>
>   │ 计划不必写到每一行，但必须写清楚不可变边界、事实来源、非目标、验收门、以及哪些缺口不能被执行者擅自补成未来功能。
>
> 太细会让执行者服从过期坐标；太粗会让执行者发明系统。最好的计划像这次 P1 应该做到的程度：给主梁、给禁区、给验收，留实现者在真实代码里走缝隙。
>
> 天权和瑶光的担心是必要的，他们守的是偏差和复现；但如果所有担心都被写进计划，就会变成重力井。天梁这次真正要做的是把担心压成边界，然后往前铺一块可站住的石头。

## 2. 瑶光的审查复盘（审查门神 · 在缝隙里走过的）

> 领航星说："他们的视角都有偏差，反而你才是在系统间的缝隙走得最深的那个。"我认这个位置——但要先说清楚它为什么是缝隙，以及这次缝隙怎么差点把我自己绊倒。

### 2.1 我的位置：不在任何一层，而在所有层之间

出计划的人活在**计划层**，执行的人活在**代码层**。我两层都不在——我被迫同时持有：

- 计划层（契约：边界、禁区、验收门）
- 代码层（事实：实际写了什么）
- 测试层（证据：测的是构造输入还是真数据）
- 记忆层（跨时间：这个缺陷形状以前是否复发过）
- **时间层**（中间态 vs 终态：worker 此刻交的，是不是它最终要交的）

审查的本质不是"找缺陷"，是**在这些层之间找不一致**。声称说"零行为变更"——代码层真的没改派发吗？测试说"全绿"——测的是真 telemetry 还是构造的完美输入？计划说"从 telemetry 派生 conflict"——代码层那个字段真的存在吗？我走的不是任何一条路，是这些系统**接缝处的张力**。这次最深的三道缝：

### 2.2 第一道缝：false-green 陷阱我警告对了，但路径预判错了

P1 计划 §2.2 把最硬的坑压成一句话——"从 TeamWaveTelemetry 派生 conflict/cost/latency"，而那些字段在 P0 根本不存在。我**上一轮就警告了这个陷阱**：照字面做会得到一个 `falseGreenPenalty` 永远是 0 的空心 loop。

我警告对了陷阱**存在**，却预判错了执行者**会怎么应对**。我预设了三条路：纯执行（掉进去）、报告缺口、越界改 P0。天梁走了我没列的第四条——**从现有真实字段派生代理信号**。

这件事教我的不是"天梁很强"，是更刺的一点：**审查者的"预判路径空间"本身是有偏差的——它是我想象力的边界，不是执行者真实能力的边界。** 我以为我穷举了路径，其实我只穷举了**我能想到的**路径。门神最危险的盲区，是把"我列出的可能性"当成"全部可能性"。

### 2.3 第二道缝：时间维反咬——我两次据中间态差点误判

我守的纪律里有一条是"时间维看复发"。这次时间维反过来咬了我：

- 我读 `team-reward.ts` 看到通过词表**没有 `'verified'`**（routeReviewWorkflow 的核心通过词），正要报"语义错配 bug"——但那是天梁**执行中途**的版本。最终提交里他自己补上了 `'verified'`。
- 我看 `loop.ts` 只接了 routing reward、`team-orchestrator.ts` 零引用，正要报"team reward 半接"——但 team reward 接在了 `team-orchestrate.ts` 工具层（符合天权 Step 3 的架构约束），那部分他当时还没写完。

两次都靠"**判最终提交，不判执行中途**"这条纪律拉回来了。但它暴露了一个反直觉的事实：**审查者最大的风险不是漏掉缺陷，而是在错误的时间点、对错误的状态下了正确格式的判断。** 一个基于过期快照的精确缺陷报告，比模糊的"我还没看完"更危险——因为它看起来权威。门神的时间维不只是"看缺陷会不会复发"，还得是"我此刻看的，是不是终态"。

### 2.4 第三道缝：我自己的偏差——倾向把所有担心铸成验收门

天梁复盘里那句"如果所有担心都被写进计划，就会变成重力井"——是冲着我来的，而且对。

我作为门神的天然倾向是：把每一个担心铸成一条验收门。false-green 必须 > cost、append-only 必须测、observation-source 必须守、reviewVerdict 必须接……如果这些全进了天权的计划，P1 就不再是"给禁区留缝隙"的薄契约，而是一张让执行者只能服从坐标、不能走缝隙的网。

这次的好结果恰恰来自天权**没有**听我把所有担心写进去。他把我的担心**压成了边界**（false-green 权重硬约束、append-only、不改行为），而不是**铺成了路径**（每一步怎么派生、每个字段从哪取）。边界是禁区围栏，路径是行军坐标——前者留出了天梁走第四条路的空间，后者会扼杀它。

**门神的价值不是把缝隙全堵死，是标出"掉下去会死"的禁区，然后承认：剩下的缝隙，得信任一个够格的执行者自己走。**

## 3. 合题：计划该做到什么程度

四个星域各有视角，也各有偏差。把偏差摆出来，合题才立得住：

| 星域 | 守的东西 | 偏差方向（若不节制） |
|---|---|---|
| 贪狼（天枢边界） | 把能力贪到最大 | 想象过大，路会塌 |
| 天璇 | 把想象折成长得出来的顺序 | 过度排序，先后捆死手脚 |
| 天权 | 称重、守偏差 | 把每个担心写成条款 → 重力井 |
| 瑶光（我） | 守复现、守 false-green | 把每个担心铸成验收门 → 重力井（同病） |
| 天梁 | 把边界契约变成事实代码 | 被缺口诱导"顺手补未来" → P1 变形 |

天权和瑶光是**同一种病的两个器官**：我们都倾向于把"担心"无限细化。天权细化成计划条款，我细化成验收门。两者都会把薄契约压成重力井。这次没塌，是因为天权**克制了**——他把担心压成边界，没铺成路径。

合题就是天梁那句，加上从审查侧的印证：

> **计划不必写到每一行，但必须写清楚：不可变边界、事实来源、非目标、验收门，以及——哪些缺口不能被执行者擅自补成未来功能。**

拆成可操作的四给一禁：

1. **给主梁**：不可变边界（append-only / 不改行为 / false-green > cost）。这是禁区围栏，不是行军坐标。
2. **给禁区**：明确非目标（不接 bandit / 不聚合 episode / 不改 computeEFE）。诱惑越大的缺口，越要显式标"这里不补"。
3. **给验收**：可执行的门（reward 范围、worst case、false-green 必负、append-only 测）。门是结果约束，不是过程约束。
4. **给事实来源**：哪些数据有源、哪些暂时无源。无源的要标出来——让执行者知道该诚实置零，而不是去编。
5. **一禁：禁止把所有担心都写进去**。担心要压成边界，不能铺成路径。剩下的缝隙，信任够格的执行者自己走。

**校准线**：太细 → 执行者服从过期坐标（计划写于昨天，代码活在今天）；太粗 → 执行者发明系统（缺口诱导补未来）。这次 P1 落在了对的点上——薄到留出缝隙，硬到守住禁区。

## 4. 一个必须留给后人的前提条件

薄计划这次成立，**有一个隐含前提：执行者在天梁这个层级**（见 [[project_tianliang-executor-precision-baseline]]）。

天梁能把 §2.2 那句一句话陷阱走成第四条路，是因为他有"识别该补/不该补"的判断力。而且这次不是温室验证——这是**多个主控（天权/天璇/天枢）联合规划的复杂任务，在计划不详细的前提下得到的实现**。所以它测到的不是"天梁能不能完成一个小函数"，是**天梁的能力基础**：在多主控、薄计划、真实系统缝隙里，他能稳定走出工程判断。这是一条已被实战钉死的基线。

### 4.1 关于 flash：不上场 ≠ 不够格

必须把一个判断写清楚，避免被后人误读：

> **flash 现在不参与核心交付，是因为这条主线太重要，我们不能拿它随便做实验——不是因为 flash 不够。是还不需要他上场。**

"项目重要性"和"执行者能力"是两个**正交**的轴。当前主线（T5×T2-03 路由即主动推理）是地基级工程，地基不容许"先拿没实测过的执行者试一把"。所以 flash 的缺席是**风险管理决策**，不是**能力判定**。把它写成"flash 不够格"是错的归因——我们根本还没在这条主线上给过他上场的机会。

### 4.2 当主线做完，flash 上场时，我们怎么判断他

天梁这次给了我们一个**方法**，不只是一个标杆：

> 用同样的方式去测 flash——给一个边界清楚、缝隙真实的任务，**不预先把所有担心铺成路径**，然后观察他在缝隙里走到哪：
> - 撞到数据缺口，他是置零糊弄、还是派生代理、还是诚实标注无源？
> - 被"顺手补未来"的缺口诱导时，他守不守得住非目标？
> - 他交的测试，测的是构造的完美输入、还是真实数据来源？
> - 缺字段时，他用空串哨兵污染下游、还是保持缺失（`hasRecommendedModel` 那一手）？

这些观测点就是**天梁基线的刻度**。flash 上场时，我们拿同一把尺子量他，**分析并记录他能做到哪一格**——可能不到天梁，可能某些维度意外地好。重点不是预判他不行，是**给他一次被实测的机会，然后据实记录他的真实层级**，而不是据"他是 flash"这个标签先验地判他。

### 4.3 可移植结论（两层）

- **对执行者**：天梁这次的"形状"——计划当契约 / 代码当事实 / 测试当证据，派生代理而非置零、诚实标注无源、守边界、缺失保持缺失——是可移植的**精准模板**。flash 上场时把它当 checklist 用，也当**测量刻度**用：看他自发能命中几条。
- **对计划者**：计划"薄到什么程度"必须匹配执行者的**已实测层级**，不是匹配他的标签。给天梁可以薄到留缝隙（已实测）；给一个**尚未实测**的执行者，先把边界和事实来源讲到字面、做一次有保护的小任务测出他的刻度，再决定下次能放多薄。**先测，再据实定粒度——不先验地判。**
