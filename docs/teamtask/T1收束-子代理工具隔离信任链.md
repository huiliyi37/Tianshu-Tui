## 0. TL;DR

子代理工具隔离的设计哲学：**权限是数据，不是 prompt 劝说。**

单一数据源（`ProfileRegistry`）定义"谁能用什么工具"，沿 7 个环节流到 worker 的 AgentLoop，
最终用 `filterToolRegistry` 物理收窄成一个只含白名单工具的 registry。worker 在工具表层面
**根本没有**禁用工具——不是软约束。

对抗式 Verifier 的"可信"由此成立：它的 verdict 被无条件信任，**不是因为更强的 prompt，
而是因为它物理上没有作弊工具**（无 bash/edit/write，只有 run_tests + 只读）。

> ⚠️ 但本文第 4 节记录了 4 个正确性裂缝，其中 2 个会让对抗式 Verifier 改造的实际效果
> 接近零。详见 [子任务文档](./T1收束-子代理工具隔离优化任务.md)。

## 1. 全链路 7 环

```
1. delegate_task(profile)        主 agent 调工具，profile 名做 zod 动态校验
        ↓
2. ProfileRegistry.get(profile)  单一数据源 → {role, allowedTools, expertisePrompt}
        ↓
3. buildWorkOrder()              order.allowedTools = profileDef.allowedTools ?? 兜底
        ↓
4. coordinator.dispatch()        classifyProfile → role 决定 dispatch 路径
        ↓
5. filterToolRegistry(base, order.allowedTools)   ← 物理收窄：deny-all + allowlist
        ↓
6. runWorkerSession()            全新 SessionContext + 独立 AgentLoop（隔离 cache）
        ↓
7. verifyWorkerEvidence()        回收时按 role 决定 verdict 可信度
```

| 环 | 文件:行 | 作用 |
|----|---------|------|
| 1 | `src/tools/delegate-task.ts:67` | 入口校验三连：profile 动态校验、路径预检、progressive timeout |
| 2 | `src/agent/profile-registry.ts:38` | BUILTIN_PROFILES 单一数据源 |
| 3 | `src/agent/work-order.ts:215` | `profileDef.allowedTools ?? 兜底` 冻进 order |

## 2. 关键环节详解

### 环 1 — delegate_task：入口校验三连

`delegate-task.ts` 是主 agent 唯一的派发入口，三道前置门：

- **profile 动态校验**（`profileStringSchema.refine`，行 14）：查 `profileRegistry.getProfileNames()`，
  不是写死 enum——用户在 `.rivet/agents/*.md` 的自定义 profile 也能通过。
  > ⚠️ 但**发给模型的 JSON schema enum 仍是硬编码且陈旧**（行 60）。见裂缝 1。
- **文件路径预检**（行 77）：每个 `files[]` 过 `validatePathSafe`，越出 project root 直接 block，
  错误信息教模型"用 bash cat 内联"——复用 tools 层那道路径边界。
- **progressive timeout**（行 39）：turn 0-1→30s、2-4→75s、5+→180s。冷启动短超时防卡，成熟后放宽。

派发完成后的隐藏动作：worker findings 被抽成 `ClaimProposal` 灌进 `claimStore`
（confidence→fitness 映射，行 108-142）——worker 知识回流主上下文的通道，走 claim 生命周期
而非直接注入（保 cache）。
> ⚠️ 但 `source.turn` 硬编码为 0（行 128）。见裂缝 4。

### 环 2-3 — ProfileRegistry：权限即数据

`profile-registry.ts` 是整条链的心脏。每个 profile 是纯数据：

| profile | role | allowedTools | 关键 |
|---|---|---|---|
| code_scout / reviewer / architect | readonly | READ_ONLY_TOOLS(+lsp) | 无写 |
| planner | brain | **仅 delegate_task/batch** | 只会派活 |
| **adversarial_verifier** | **readonly_plus_test** | **READ_ONLY + run_tests** | **无 bash/write** |
| patcher / verifier | hands | WRITE_TOOLS(含 bash) | 能改文件 |

`buildWorkOrder`（work-order.ts:215）把 `profileDef.allowedTools` 拷进 `order.allowedTools`，
兜底是只读集。**权限在这一步就冻进 work order**，后续环节只读不改。

`loadFromDirectory`（行 222）有硬规则：**用户自定义 profile 不能覆盖内置**（行 231 builtIn 检查），
防止用户给 `code_scout` 偷偷加 bash 提权。

### 环 5 — filterToolRegistry：物理收窄（真正的牢笼）

```ts
// coordinator.ts:253
const workerRegistry = filterToolRegistry(this.config.baseToolRegistry, order.allowedTools)
```

`registry.ts:44` 对每个 allowlist 名字 `source.get(name)`，**未知名字直接抛错**（fail-fast）。
worker 拿到的是**只含白名单工具的全新 registry**，连 "unknown tool" 都 dispatch 不出去——
不是 prompt 层"请不要用 bash"的软约束，是工具表里**根本没有** bash。

这是对抗式 Verifier 的设计核心（改造一决策 2）：早期 verifier 有 bash，可 `bash echo > file`
绕过"无 write"。现在 `adversarial_verifier` 物理上没有 bash/edit/write。
**牢笼是数据驱动的，不靠模型自律。**

### 环 6 — worker-session：独立 cache 隔离

`runWorkerSession` 每次造**全新 `SessionContext` + 独立 AgentLoop**（`sessionId: worker-${order.id}`）。
profile-registry 注释（行 138）点明：skill worker **不注入主 agent system prompt**——
避免破坏主会话 exact-prefix cache，worker 自己的 cache 由 Flash 模型廉价承担。

防卡死三重保障：
1. 内部 `setTimeout(() => agent.abort(), timeoutMs)` 预算超时（行 140）；
2. **父 abort 信号传播**（`onParentAbort`，行 144）：父超时→worker 立即停，不等内部 180s。
   这是 `c39f4b0` 修过的"abortSignal 装配漏拷=僵尸 worker"的正解；
3. transient 网络错误指数退避重试（2 次），与 output-parse 重试分离；
4. `finally` 里 `removeEventListener`——长会话反复 delegate 不累积监听器。

### 环 7 — worker-evidence：role 决定 verdict 可信度

`verifyWorkerEvidence` 按 role 分流：

```
changedFiles 为空        → 直接放行（只读 worker + adversarial_verifier 都走这条，行 30）
profile ∈ ['patcher']    → advisory：未验证只加 risk 不 block（WRITE_PROFILES_ADVISORY）
其余有改动但未 verified  → 直接 blocked
```

关键：`WRITE_PROFILES_ADVISORY` 从 `['patcher','verifier']` 缩成 `['patcher']`。
因为 adversarial_verifier 无写工具→changedFiles 永远空→走第一条直接放行，
它的 `verified` verdict 被**无条件信任**。
> ⚠️ 但 harness 从不核对 `transcript.toolUses` 里是否真的有 `run_tests`。见裂缝 2。

## 3. 三个不变量

1. **权限是数据不是 prompt 劝说** —— `filterToolRegistry` 物理收窄工具表。
2. **cache 边界 = session 边界** —— worker 独立 context，不污染主 prefix cache。
3. **信任随 role 分级** —— 无写能力者的 verdict 才被无条件信任，这是对抗式 Verifier 成立的根基。
