# 噪音治理与委派运行质量改造

范围共识：不碰主题一（断线功能）与主题三（交付门禁）——那些功能关闭有其原因，重新启用不是优化。本计划只做减法与收敛。

## Phase A — 注入噪音治理（防 trained-mode）

### A1. 统一劝导总线 harness-advisory（核心减法）
现状：同类"纠偏"信息走 5 条独立通道，单轮最坏 ~25 个模型可见区块：
- immune 上下文（`loop.ts:1554-1557` 注入 projection）
- repair-hint appendix（[src/prompt/volatile.ts](src/prompt/volatile.ts)）
- MistakeNotebook 错误提示拼在失败工具结果后（`tool-pipeline.ts:700-704`）
- dedup-guard 下一轮 system-reminder（`dedup-guard-hook.ts:71-75`）
- stigmergy dead-end 规则 via signal-consumer（`signal-consumer-hook.ts:47-63`）

改造：新建单一 `<harness-advisory>` 汇聚器（建议放 [src/agent/advisory-bus.ts](src/agent/advisory-bus.ts)），五个来源改为投递 advisory 条目（带优先级+去重 key），每轮**最多渲染 3 条**，由 GWT 现有 salience 机制走 dynamic appendix 单一出口。原五条通道的直接注入路径删除。净效果：模型可见区块数下降，劝导不再互相冲突。

### A2. intentRetrievalRouter 默认改 heuristic
现状：默认开 LLM 分类器（[src/config/default.ts](src/config/default.ts) L106-112），每个可操作轮多一次 LLM 调用 + 一个 route 区块。
改造：默认 `mode: 'heuristic'`，LLM 分类器改 opt-in。删除路由区块在低置信时的注入（只在高置信命中时渲染）。

### A3. 冷冻前缀按需分级
现状：`volatile-snapshot.ts:26-76` 无条件全量注入 AGENTS.md + .rivet.md + 代码库索引 + 星座胶囊 + project-memory + session-memory——这是"外部文件污染"的最大来源。
改造（保持会话内字节稳定，分级在会话创建时一次性决定，不破缓存）：
- AGENTS.md / .rivet.md：保留（项目指令是行业标准）
- 代码库索引 `projectIndexBlock`：加字符预算上限（如 4K），超出折叠为"用 repo 工具按需获取"一行
- 星座胶囊 / project-memory：各加渲染预算上限，超出截断
- 新增配置 `agent.prefixBudget`（默认收紧），不加任何新区块

### A4. 跨会话污染门控
现状：
- resume 时 durable claims 取**字典序最后一个**其他会话（`session-persist.ts:434-448`），与当前任务无关也注入
- pheromone dead-end 信号跨会话跨任务全量参与 preTurn 注入（[src/agent/stigmergy.ts](src/agent/stigmergy.ts)）

改造：durable claims 注入加门控——仅当 claim 涉及文件与当前 cwd/近期触碰文件有交集，且未过 TTL（如 7 天）；pheromone 出口经 A1 总线统一限流（命中当前任务文件才出）。

### A5. 自动委派显式配置、默认关
现状：dispatcher-hook 注释引用 `config.agent.autoDelegateEnabled` 但 schema 里**不存在该字段**（`dispatcher-hook.ts:34-35`），凡是 coordinatorRef 存在就默认开，且 fire-and-forget 结果不回注——纯后台噪音。
改造：在 [src/config/schema.ts](src/config/schema.ts) / [src/config/default.ts](src/config/default.ts) 增加 `autoDelegateEnabled: false`，接入 `create-runtime-hooks.ts:228-229` 的注册条件。不做结果回注（保持关闭语义干净）。

### A6. 死计算清理
`cerebellarHint`（`tool-execution.ts:445-446`）与 `routingReason`（`turn-end.ts:59`）计算后从不渲染。处理：cerebellarHint 改投 A1 总线（它本来就是纠偏信号）；routingReason 计算直接删除。

## Phase B — 委派运行质量（对标 Claude Code 子代理）

### B1. delegate_task 失败收敛为结构化 packet
现状：worker 运行时错误/stall sweep 在 `coordinator.ts:887-893` 直接 rethrow，`delegate-task.ts:88-101` 无 catch → 主轮拿到裸 tool error、零 packet、可能盲目重试；而 `delegate_batch` 已有 `workerFailureResult` 降级（`coordinator.ts:1057-1059`）。
改造：`delegate_task` 路径对齐 batch——catch 后产出 `workerFailureResult` 并走 `buildPrimaryWorkerPacket`，主代理始终拿到结构化降级结果。

### B2. 三层超时对齐
现状：timeout ladder（60/120/180s）只挂工具壳（`delegate-task.ts:150`）；`work-order.ts:256` 的 worker 预算硬编码 180s；`profileRegistry.defaultMaxTokens` 被 work-order 忽略；`order.budget.maxTokens` 是死字段。
改造：
- work-order 创建时 `budget.timeoutMs = progressiveTimeout(turn)`，保证工具壳超时 ≥ worker 预算（消除"工具 60s 死了 worker 还在烧 API"）
- `createReadOnly/WriteWorkOrder` 读取 profile 注册表的预算
- `runWorkerSession` 累计 usage 超 `maxTokens` 时主动 abort → `buildBlockedWorkerResult`（带 transcript）

### B3. worker 活动流与团队面板实时化
现状：活动流 400-delta 才出一条心跳、tool_result 完全静默（`worker-activity-stream.ts:15-36`）；team panel 只在终态刷新（`team-panel-model.ts:74-81`）——长任务期间用户只看到"输出中…"，体验与 Claude Code 子代理流式差距最大。
改造：
- 活动流增加 tool 开始/结束行（工具名 + 截断目标，单行），text 心跳阈值降到 ~150 delta
- team-panel-model 支持从 `onActivity` 增量更新状态（waiting→running→done），T9 `app.ts` 接增量刷新

### Backlog（本轮不做）
- worker 断点续做（resumeWorker）、TaskBoard 绑定、/compact 用户指令、resume 缓存快照持久化
