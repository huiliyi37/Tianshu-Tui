## 0. 一句话

P3 子系统（`p3-integration.ts`，8 组件门面）接进了 loop，但内部裂成两半：投机预读 + 错题本是活的，而 **LinUCB bandit、PlanCache、AgentJIT、Nightcrawler 四个完整造好的学习/复用组件全部空转**——它们都接通了「记录/构造」那一头，没接「咨询/复用」那一头。本任务把它们接到已经活着的决策点。

---

## 1. 能力定位

这四个空转组件各自代表 harness 的一个真实能力维度，且每个都已经实现完整、只差最后一根接线：

| 组件 | 代表能力 | 本该接到的活决策点 |
|---|---|---|
| **LinUCB bandit** | 在线 RL 选 reasoning effort / verbosity（从结果学习，而非硬规则） | `auto-reasoning` 的 effort 决策 |
| **PlanCache + AgentJIT** | 计划记忆 → 相似任务 JIT 复用（省一轮规划） | `plan_submit` / 任务启动 |
| **Nightcrawler** | 后台 agent 并行执行 | delegate-task 的后台执行器 |

它们不是「设计得奇怪所以没做完」，是「做完了但最后一根线没接」。能力真实，无第二来源。

## 2. 证据（grep 锚点）

**P3 门面接进 loop，execute 传了、其余执行器没传**
- `src/agent/loop.ts:278-292` `createP3Integration({ execute: ... })` —— 只传了投机预读用的 `execute`（限 SAFE_TOOLS）。
- `src/agent/p3-integration.ts:36/43/53` —— `backgroundExecute`、`jitExecute` 未传，fallback 到 `async () => ''` 空执行器。

**LinUCB bandit 完整造好、零咨询**
- `src/agent/p3-integration.ts:46-50` 构造：6 维上下文、四臂（flash/pro/concise/verbose）。
- `src/agent/p3-integration.ts:120-127` `recommendAction` / `rewardAction` —— **零调用者**（全仓 grep `recommendAction`/`rewardAction` 仅出现在定义处）。
- 实际 effort 决策由**固定启发式**接管：`src/agent/auto-reasoning.ts:10` `selectReasoningEffort(input)` 看输入文本；`src/agent/tool-execution.ts:387` `adjustReasoningEffort(effort, level)` 看错误率。RL 学习器从不被问、从不被奖励。

**PlanCache + AgentJIT 死链**
- `src/agent/p3-integration.ts:94-100` `recordPlan` / `lookupPlan` —— 零调用者 → cache 永远空。
- `src/agent/p3-integration.ts:130-134` `tryJIT` 依赖 `planCache.lookup` → cache 空 → **永远返回 null**。`tryJIT` 虽有 1 个调用点，但因 cache 空而恒为空操作。

**Nightcrawler 空转**
- `src/agent/p3-integration.ts:42-44` 构造时 `backgroundExecute` 未传 → 空执行器。
- `submitBackground` —— 零调用者。

## 3. 联合方案：把空转学习器接到活决策点

### 接线 1 — LinUCB 接管 effort 决策（用 RL 替硬规则）

当前 `tool-execution.ts:387` 的 `adjustReasoningEffort` 是「看错误率的固定规则」。改为：
- 决策时先构造 6 维上下文 `[taskComplexity, errorRate, turnDepth, fileCount, isRepeat, timeOfDay]`，调 `p3.recommendAction(context)` 拿建议。
- 把现有启发式降级为 bandit 的**先验/兜底**（bandit 冷启动或低置信时用规则）。
- 回合结束/任务结果出来时，用实际效果调 `p3.rewardAction(arm, context, accepted)`。
- bandit 权重落 MeridianDb，跨 session 学习「这个项目什么任务该用什么 effort」。

### 接线 2 — PlanCache 接活（补死链中段）

两端都有，中间没接：plan-mode / MCTS 在产计划，PlanCache 空着等。
- `plan_submit` 工具成功时 → `p3.recordPlan(taskDescription, steps)`。
- 任务启动时 → `p3.lookupPlan` / `p3.tryJIT(taskDescription)`，命中则复用计划骨架，省一轮规划。
- PlanCache 落 MeridianDb，计划记忆跨 session。

### 接线 3 — Nightcrawler 接 delegate 执行器（或判定被取代）

Rivet 已有 delegate-task 的真实后台执行能力。两条路二选一（**这条需要先判定，不像 1/2 是确定接线**）：
- **若 Nightcrawler 的「后台 agent」语义与 delegate-task 不同**（如：不占主 agent 回合、真并行）→ 把 delegate 的执行器接进 `backgroundExecute`，接通 `submitBackground`。
- **若 delegate-task 已完整覆盖其能力** → Nightcrawler 属「被取代的旧能力」，丢着不管（参考三死文件的处理）。
- 判定方法：对比 `nightcrawler.ts` 与 `tools/delegate-task.ts` 的执行模型（是否并行、是否独立 session、是否占回合）。

## 4. 影响面与边界

- **接线 1/2 是确定动作**（能力真实、决策点已活、只差接线）；**接线 3 需先判定**（可能被 delegate 取代）。
- LinUCB / PlanCache 权重与计划落 MeridianDb，不新建 store。
- 通道：effort 决策走 API 参数（B 臂，零 cache 代价）；计划复用走 prompt 构造前的骨架注入——**注意**：plan 注入若进 prompt 需走 cache-safe 通道，避免破前缀（查 [[prefix-cache-invariant-registry-ref]]）。
- 与 T2-01 同源：两个任务都是「把空转的学习能力接到活的执行点 + 落 MeridianDb 跨 session」。可并行，无硬依赖。

## 5. 验收

- `recommendAction`/`rewardAction` 有真实调用，bandit 统计显示 arm 被选择与奖励。
- effort 决策可见 RL 影响（非纯启发式），且有规则兜底。
- `plan_submit` 后 PlanCache 非空；相似任务 `tryJIT` 命中复用。
- bandit/planCache 重启后从 MeridianDb 恢复（跨 session）。
- Nightcrawler：给出「接通」或「判定被 delegate 取代、封存」的明确结论。
- effort/计划改动不破 prefix cache（需复现验证）。
