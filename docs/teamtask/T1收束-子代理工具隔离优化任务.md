## 🔴 P0 — 裂缝 1：陈旧 enum 让 adversarial_verifier 调不出来

**取证**：`delegate-task.ts:60`、`delegate-batch.ts:117` 的 JSON schema profile 硬编码：

```ts
enum: ['code_scout', 'doc_scout', 'planner', 'reviewer', 'verifier', 'patcher']
```

缺 `adversarial_verifier`、`architect`、`troubleshooter`。zod 层（`profileStringSchema.refine`）
查 `getProfileNames()`（动态、正确），但**发给模型的 schema 是这份写死 enum**。

**后果**：模型看到的可选项里没有对抗 verifier，会去选旧 `verifier`（有 bash 的）。改造一核心 profile 形同虚设。

**修法**：schema 的 `enum` 改成 `profileRegistry.getProfileNames()` 动态生成（与 refine 同源）。
消除 schema↔validation 双源漂移。本链路 ROI 最高一处。

## 🔴 P0 — 裂缝 2：`verified` 是模型自报，harness 不查 run_tests 是否真跑过

**取证**：`evidenceStatus`（`work-order.ts:143`）是 zod 从 worker 文本 parse 出来的，default `unverified`。
`verifyWorkerEvidence` 只看这个**值** + `changedFiles` 是否空，**从不核对 `transcript.toolUses` 有无 `run_tests`**。
对抗 verifier 因 `changedFiles` 恒空，走 `worker-evidence.ts:30` 直接放行。

**后果**：对抗 verifier 可读完代码、不跑任何测试、直接输出 `{"verdict":"verified"}`，harness 全盘接受。
这正是它 prompt 里列的 #1 失败模式 "verification avoidance"——目前**只有 prompt 在劝，没有 harness 在拦**。

`transcript.toolUses`（worker-session 已记）和 `WorkerSessionRun` 都能拿到信号，只是 coordinator 没消费。

**修法**：对抗 verifier 回收时，verdict=`verified` 但 `transcript.toolUses` 不含 `run_tests`
→ 强制降级 `unverified` + 加 risk。把"无作弊工具"的物理隔离，补上"必须真验证"的行为闸门。

## 🟡 P1 — 裂缝 3：bash rtkRewrite 全局缓存在并发 worker 下失效

**取证**：`bash.ts:62` 的 `_cachedCommand/_cachedResult` 是模块级全局单变量。注释称它关闭
`requiresApproval()`→`execute()` 的 TOCTOU 窗口——但该保证**只在单线程串行下成立**。
`delegate_task.isConcurrencySafe()===true`，多 hands worker 可并发跑 bash：A 缓存命令 X 的 rewrite，
B 用命令 Y 覆盖，A 进 execute 读到 Y 的 rewrite——**TOCTOU 窗口被重新打开**。

实际触发概率低（gate→execute 毫秒级），但声称的安全保证在并发下为假。

**修法**：缓存 key 带 `toolUseId`，或退化成 per-call 计算（rewrite 本身 500ms timeout，缓存收益有限）。

## 🟡 P1 — 裂缝 4：worker finding 的 claim 时间线全部钉死 turn 0

**取证**：`delegate-task.ts:128` — `source: { ..., turn: 0, ... }`。所有 worker finding 进 claimStore turn 恒 0。

**后果**：claim 生命周期（active→durable_candidate→durable）和去重若依赖时间线/turn 排序，
全钉 0 会让同会话多轮 delegate 的 finding 时间线塌缩，影响 promotion 和 conflict-detect。

**修法**：透传当前 `sessionTurnCount` 填真实 turn。`ToolCallParams` 已有 `sessionTurnCount` 字段，现成。

## 🟢 P2 — 健壮性 / 性能

### 5. filterToolRegistry fail-fast 时机太晚
未知工具名抛错发生在**派发时**（`coordinator.ts:253`），而非 `.rivet/agents/*.md` **加载时**。
用户自定义 profile 写错工具名，要等真正 delegate 到它才崩。
**修法**：`loadFromDirectory` 时用 base registry 校验 allowedTools，加载期报错。

### 6. worker 无 PromptEngine/Session 池化
每个 worker 全新 `SessionContext` + AgentLoop。`delegate_batch` 派一堆小 worker 时纯冷启动开销。
profile-registry 注释（行 138）已承认这是已知取舍（隔离 cache 优先）。
**若 batch 场景变热**：考虑 PromptEngine 复用（system prompt 本就该 worker 间共享，不破各自 cache）。

### 7. 超时双轨未对账
tool 层 progressive timeout（30/75/180s）与 worker 内部 `budget.timeoutMs` 是两套独立计时器。
当前靠父 abort 传播兜底（`worker-session.ts:144`），逻辑对，但两数字若配置漂移
（tool 30s < budget 180s）会出现 tool 先杀、worker 内部计时器空转到 finally 才清。
**修法**：worker budget 从 tool timeout 派生，单一数字源。
