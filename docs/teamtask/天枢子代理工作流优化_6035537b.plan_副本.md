## 背景与差距

天枢子代理体系（`DelegationCoordinator` + Worker 白名单 + `<worker_results>` packet 回报）在**上下文隔离**和**并行执行**上已对标 Cursor。但对比 [Cursor Subagents 文档](https://cursor.com/cn/docs/subagents)，存在四处差距：

- **自动委派未接线**：`src/agent/hooks/dispatcher-hook.ts` 已实现按 `TaskContract` 复杂度自动分解委派，但 `src/agent/create-runtime-hooks.ts` 没注册它，生产环境只能靠提示词引导显式调用。Cursor 是「智能体自动判断 + 显式 /name」双路径。
- **explore worker 被参数卡死**：worker 在 `src/main.tsx` 配置为 `maxTurns: 8` + `compact: { enabled: false }`。这是为旧的小 worker 设的；在 v4-flash 1M 上下文 + 我们刚落地的 T1/T4/T7/T10 优化下，explore worker 可以跑更多轮、用满 1M 窗口而不失控，但当前参数限制了它。
- **大结果回报粗暴**：`buildPrimaryWorkerPacket()`（`src/agent/worker-prompts.ts`）超 32K 字符就**逐级删字段**（examinedFiles/risks/nextActions/verification 直接丢弃），不是 Cursor 式的「写文件 + 主代理按需读取」。
- **探索未走「快模型大规模并行」范式**：Cursor Explore 默认用更快模型并行跑 10 次搜索。天枢 `maxWorkers: 3` 且 explore 与 patch 共用同一并发池。

## 关键洞察：v4-flash 1M worker 自动继承 T7/T10

worker 在 `src/agent/worker-session.ts` 用 `new AgentLoop(...)` 创建完整 loop。T7（`engine.ts` 的 `requestTimeCollapse`，触发条件 `contextWindow >= 1_000_000`）和 T10（`tool-execution.ts` 的 tiering，触发条件 `contextWindow >= 500_000`）**只看 contextWindow**，与 `compact.enabled` 无关。所以只要 worker 的 `contextWindow` 正确设为 1M，explore worker 跑 grep storm 时会自动触发 T4 storm guard + T7 request-time collapse + T10 tiering，不会失控——这正是放宽 `maxTurns` 的安全前提。

## Phase A：接线自动委派（✅ 已完成）

目标：复杂任务（2+ 模块）自动 spawn **只读** explore worker，对标 Cursor 自动委派，但绝不自动 spawn 写 worker。

- **A1 注册 dispatcher-hook** ✅：在 `create-runtime-hooks.ts:228-229` 注册，`autoDelegate` deps 通过 lazy getter 注入，`main.tsx` 已接线。
- **A2 强制只读探索** ✅：`dispatcher-hook.ts:94` — 自动委派 `inferWorkOrderKind()` 所有 domain 统一返回 `code_search`，不产 `patch_proposal`。Profile 按 domain 映射 `code_scout`/`doc_scout`（`dispatcher-hook.ts:106-107`）。
- **A3 去重 + 冷却 + kill-switch** ✅：
  - 去重：`dispatchedIds: Set<string>`（per-`contract.id`）
  - 冷却：`lastDispatchTurn` + `cooldownTurns ?? 3`
  - Kill-switch：`config.agent.autoDelegateEnabled`（`dispatcher-hook.ts:34`）
