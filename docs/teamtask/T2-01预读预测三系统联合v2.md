## 0. 一句话

Rivet 有三套各自独立、互不相通的「在模型开口要之前把内容准备好」系统，每套都只接通了最容易的一半。它们不是冗余——是同一个「让 harness 学会预测」的能力被切成了三个半成品。本任务把它们汇成「一个学习层 + 一个执行层 + 一个缓存」。

---

## 1. 能力定位（为什么值得做）

「前瞻式预测下一步要碰什么，提前读进缓存」是 harness 的一个真实能力维度。它走文件 IO 通道（cache-aware-fusion 文档里的 **B 臂**），不碰 prompt 字节，因此可以无限学习、跨 session 积累，而**永不威胁 prefix cache**——与 Rivet 的核心宪法零冲突。这是它最大的战略价值。

当前三套系统各持一部分能力，但没有一套是完整的：

| 系统 | 预测粒度 | 会学习 | 跨 session 持久 | 当前状态 |
|---|---|---|---|---|
| **physarum `predictNext`** | 文件·**有向时序** | ✅ | ✅（MeridianDb `physarum_edges`） | 💤 空转 + 喂垃圾 |
| **P3 ToolPatternMiner → ShadowQueue** | 工具·bigram 转移 | ✅ | ❌ 纯内存 | ✅ 活，但进程死即忘 |
| **prewarm 四驱动** | 文件·反应式 | ❌ | — | ✅ 活 |

每套都缺另两套有的东西：
- physarum 有跨 session 持久学习 + 有向时序，但**学的是垃圾**（输入接错）、**没有出口**（predictNext 零调用）。
- P3 有活的投机执行链，但**不跨 session**（内存 bigram，重启全忘）。
- prewarm 活且无 cache 代价，但**只会反应**（文件被提到/被读之后才预热），不会前瞻。

**physarum 空转 + 喂垃圾**

- `src/repo/physarum-engine.ts:55` `recordSequentialEdit()`（STDP 有向学习）—— 仅 `__tests__/physarum-engine.test.ts:60` 触发，生产零调用，故 `direction` 恒为 0。

## 3. 联合方案：一个学习层 + 一个执行层 + 一个缓存

### 步骤 A — 喂对 physarum 输入（一切前提）

physarum 现在学垃圾，因为喂的不是文件序列。**不要改 `recordFlow` 的参数（那是打补丁）**，要给它接一个真正的「文件访问序列」源：

- 维护「上一个访问文件」状态（loop 或 tool-pipeline 层已有 `lastTarget` 这类状态，见 `p3-integration.ts:30-31`）。
- 把连续两次文件访问配成 `(prevFile, currFile, dtTurns)`，喂给 `recordSequentialEdit`（它本来就是为此设计的，签名已对）。
- 单文件访问喂一个访问热度记录。
- 免疫旁路那条 `recordFlow(toolName, file)`：要么也改成喂文件序列，要么承认「工具-文件流」对图异常检测无意义、把那一路摘掉（见 T2-01 不负责免疫，留给后续；此处只要求别让它继续污染图）。

### 步骤 B — 开 physarum 预测出口，汇入 P3 投机队列

输入喂对后 `predictNext` 才有真信号。**直接接通**（不是「先做实验证明划算再接」——前瞻预测是 harness 缺的能力维度，要有）：

- `predictNext(currentFile)` 的有向时序预测结果 → 转成 `ToolPrediction` 喂 `ShadowQueue.enqueue`。
- 这样 ShadowQueue 的投机来源从「只有 ToolPatternMiner（工具 bigram）」扩展到「+ physarum（文件时序）」两个来源。
- 工具级预测（接下来调什么工具）和文件级预测（接下来碰哪个文件）互补，不重复。

### 步骤 C — 统一预读缓存

P3 的投机预读缓存（IdleSpec/ShadowQueue 持有的命中表）与 `PrewarmCache`（`src/agent/prewarm.ts`）合流，让三套预测器（physarum / P3 miner / prewarm 四驱动）写**同一个**读缓存、查同一个命中。避免「投机读了一份、prewarm 又读一份」的重复 IO。

### 步骤 D — P3 内存学习落 MeridianDb（与本任务同源，可一并）

ToolPatternMiner 的 bigram 表落 MeridianDb（仿 physarum_edges / mistake_entries 先例），让工具转移模式也跨 session 积累。harness 用得越久，预测越准。

## 4. 影响面与边界

- **新增能力**：前瞻式 + 跨 session 的文件/工具预测（当前无此维度）。
- **通道**：全程文件 IO（B 臂），零 prefix-cache 代价，不动 prompt 结构 → 不触 [[prefix-cache-invariant-registry-ref]] 任何红线。
- **持久化落点**：全部 MeridianDb，不新建 store（[[project_canonical-memory-write-invariants]] 碎片化反模式）。
- **不归并**：physarum STDP（有向时序）与 meridian-behavior co-edit（对称共编辑）是**互补非重叠**，两套都留，喂不同出口（前者喂 predictNext，后者喂 repo_map relevance）。
- **不在本任务范围**：免疫系统的 graph_anomaly 升级（physarum 图突变 → HEARTH 漂移信号）属另一条线，本任务只要求「别让 recordFlow 继续污染图」。

## 5. 验收

- physarum 图节点是文件路径，不再是工具名（查 `physarum_edges` 表内容）。
- `predictNext` 有真实有向预测输出（direction 非恒 0）。
- ShadowQueue 投机来源含 physarum；命中率统计可见 physarum 贡献。
- 重启进程后 P3 bigram + physarum 边均从 MeridianDb 恢复（跨 session 验证）。
- 全程不改 prompt 结构、不破 prefix cache（按项目纪律，此项需复现验证而非口头声称）。
