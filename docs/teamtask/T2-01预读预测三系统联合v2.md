## 0. 一句话

Rivet 有三套各自独立、互不相通的「在模型开口要之前把内容准备好」系统，每套都只接通了最容易的一半。它们不是冗余——是同一个「让 harness 学会预测」的能力被切成了三个半成品。本任务把它们汇成：

1. **文件访问序列学习源**：只学习真实 repo 文件路径，不再让工具名/目录/命令污染图。
2. **预测层**：Physarum 学文件时序，P3 ToolPatternMiner 学工具转移；两者互补。
3. **执行层**：优先接 P3 IdleSpec/ShadowQueue 与 OS page-cache 预取；`PrewarmCache` 不再被当作 `read_file` 内容命中路径。
4. **持久层**：全部落 MeridianDb，保持 optional DB no-op。

---

## 1. 能力定位（为什么值得做）

「前瞻式预测下一步要碰什么，提前准备」是 harness 的一个真实能力维度。它走文件 IO / 运行时通道（cache-aware-fusion 文档里的 **B 臂**），不碰 prompt 字节，因此可以无限学习、跨 session 积累，而**永不威胁 prefix cache**——与 Rivet 的核心宪法零冲突。

当前三套系统各持一部分能力，但没有一套是完整的：

| 系统 | 预测粒度 | 会学习 | 跨 session 持久 | 当前状态 | 审查修订 |
|---|---|---|---|---|---|
| **physarum `predictNext`** | 文件·**有向时序** | ✅ | ✅（MeridianDb `physarum_edges`） | 💤 空转 + 喂垃圾 | 保留；先修文件事件输入和历史污染 |
| **P3 ToolPatternMiner → ShadowQueue** | 工具·bigram 转移 | ✅ | ❌ 纯内存 | ✅ 活，但进程死即忘 | 保留；目标语义需修，不能直接当文件预测器 |
| **prewarm 四驱动** | 文件·反应式 | ❌ | — | ✅ 活 | 保留；定位为预取/page-cache，不是 `read_file` 内容短路 |

每套都缺另两套有的东西：

- Physarum 有跨 session 持久学习 + 有向时序，但**学的是垃圾**（输入接错）、**没有出口**（`predictNext` 零调用）。
- P3 有活的投机执行链，但**不跨 session**（内存 bigram，重启全忘），且当前 target 记录语义偏弱。
- Prewarm 活且无 cache 代价，但**只会反应**（文件被提到/被读之后才预热），不会前瞻。

## 2. 证据（grep 锚点，可复核）

### 2.1 Physarum 空转 + 喂垃圾

- `src/repo/physarum-engine.ts:272` `predictNext()` —— 生产零调用。
- `src/repo/physarum-engine.ts:55` `recordSequentialEdit()`（STDP 有向学习）——仅测试触发，生产零调用，故 `direction` 基本恒为 0。
- `src/agent/immune-hook.ts:65` `recordFlow(ctx.toolName, ctx.targetFile, ctx.turn)` —— 第一参数喂的是**工具名**而非文件，图退化为工具名 hub。
- `src/repo/physarum-engine.ts:57-58` 显示 `recordSequentialEdit()` 只更新已有边；如果没有先 `recordFlow(prev,curr,turn)` 建边，会静默返回。

### 2.2 P3 投机预读活，但目标语义不能直接信任

- `src/agent/p3-integration.ts:57-62` `onToolStart` → `miner.record(lastTool, toolName)` + `idleSpec.onToolStart`。
- `src/agent/idle-spec.ts:19-25` `onToolStart` → `miner.predict(toolName, 0.3)` → `queue.enqueue`。
- `src/agent/tool-pipeline.ts:608-614` 会消费 `speculativeHit`，只读工具可被 ShadowQueue 短路。
- `src/agent/loop.ts:278-292` 构造 P3 时传了 `execute`（限 SAFE_TOOLS：`read_file`/`grep`/`glob`/`list_dir` 的投机预读）。
- `src/agent/tool-pattern-miner.ts` 无 save/load/db —— 纯内存，不跨 session。

审查补充：P3 当前 `targetPath` 的含义偏弱。`P3Integration.onToolStart(toolName)` 记录的是 `lastTool → currentTool`，但 meta 里传的是 `lastTarget`，也就是**上一个工具的 target**，不是当前工具未来会用的 target。因此它能学「grep 后常 read_file」，但不能可靠学「grep 后读哪个文件」。Physarum 的文件预测若汇入 P3，必须明确提供 `likelyTarget`，不要沿用 P3 旧 target 语义。

### 2.3 Prewarm 四驱动全是反应式，且不是当前内容短路路径

- `src/agent/loop.ts:629` `maybePrewarm` —— 解析用户消息里的文件名。
- `src/agent/tool-pipeline.ts:914` —— grep 命中后预热。
- `src/agent/turn-stream.ts` —— 流里出现路径就投机预热。
- `src/agent/loop.ts:641` `prewarmRecentReads` —— 时间局部性，重热近期已读。
- `src/agent/tool-pipeline.ts:615-619` 明确：`read_file` 必须总是走真实 execute，因为 PrewarmCache 可能在不同 contextWindow cap 下填充，直接返回会重引入截断回归。

因此：`PrewarmCache` 当前不是 `read_file` model-content 缓存命中路径。它可作为 OS/page-cache 预取或未来 contextWindow-aware cache 的底座，但不能再作为本任务成功标准。

## 3. 联合方案：学习源先正名，消费者分层接

### 步骤 A — 新增真实文件访问观察器（一切前提）

physarum 现在学垃圾，因为喂的不是文件序列。**不要只改 `recordFlow` 的参数**；正确做法是新增/复用一个「文件访问观察器」，只接受成功工具事件里的真实 repo 文件：

| 工具 | 是否记录 | 规则 |
|---|---|---|
| `read_file` | ✅ | `input.file_path`，规范化为 repo-relative canonical file |
| `write_file` / `edit_file` / `hash_edit` | ✅ | `input.file_path`，同时作为访问与编辑事件 |
| `grep` | ⚠️ 默认不把 `path` 当文件 | 若要学习 grep 命中文件，必须从 grep 结果中结构化提取文件路径，且标注为「候选发现」而非真实读取 |
| `glob` / `repo_map` / `repo_graph` | ⚠️ 不直接作为文件访问 | 可记录为查询上下文，但不喂 Physarum 文件边 |
| `bash` | ❌ 默认不记录 | 除非未来有结构化文件事件；不能用 command slice 当 file |

硬过滤：非项目内路径、目录、工具名、空串、黑名单文件、不可索引扩展全部丢弃。

关键实现边界：不要只依赖 `RuntimeToolEvent.target` 或 `ImmuneHookContext.targetFile`。这些字段用于展示/历史记录，可能来自 `path`、`command.slice(0, 50)` 或工具名兜底，不具备严格文件语义。文件观察器应在能看到原始 `ToolUse.input` 的层面构造，或扩展 runtime hook event 传入结构化 `fileEvents`。

### 步骤 B — Physarum 学习顺序：先建边，再更新 STDP 方向

`recordSequentialEdit(first, second, dtTurns)` 当前只更新已有边；没有边就直接 return。正确序列：

```ts
if (prevFile && prevFile !== currentFile && dtTurns <= stdpWindow) {
  physarum.recordFlow(prevFile, currentFile, turn)
  physarum.recordSequentialEdit(prevFile, currentFile, dtTurns)
}
```

这同时保留无向共访强度（`weight`）与有向时序偏置（`direction`）。

### 步骤 C — 修字典序边方向语义（实施前置）

`physarum-engine.ts` 用字典序规范化边：`fileA = min(a,b)`，`fileB = max(a,b)`；`direction` 是单标量。因此 `recordSequentialEdit(first, second)` 必须按「first 是否等于规范化后的 `edge.fileA`」校正符号。否则 `z.ts → a.ts` 与 `a.ts → z.ts` 落同一条边时方向会被错误写反或抵消。

验收必须覆盖两种方向：

- `a.ts → b.ts` 后，`predictNext('a.ts')` 优先 `b.ts`。
- `b.ts → a.ts` 后，`predictNext('b.ts')` 优先 `a.ts`，且 direction 符号为反向。

### 步骤 D — 清洗历史污染，再开预测出口

旧的 `recordFlow(toolName, targetFile)` 已可能持久化进 `MeridianDb.physarum_edges`。如果直接 `loadFromDb()` 后预测，会出现工具名候选或工具名 hub 继续影响 homeostatic scaling / ubiquity penalty。

必须先做污染防线：

1. **加载过滤**：`loadFromDb()` 或上层调用处过滤任一端不是合法 repo 文件的边。
2. **一次性迁移/清理**：删除 `physarum_edges` 中任一端为工具名、目录、命令片段、非项目文件的边。
3. **观测输出**：清理前后记录边数与被丢弃样本，防止误删合法边。

这不是成本问题，是正确性前置条件；否则预测消费者会放大旧错接。

### 步骤 E — 开第一个消费者：优先 P3 IdleSpec / ShadowQueue

输入喂对后 `predictNext` 才有真信号。第一消费者不应是旧式 `PrewarmCache` 命中，而应是 P3 的投机执行链：

- Physarum `predictNext(currentFile)` 输出文件候选。
- v1 只转成 `ToolPrediction { tool: 'read_file', likelyTarget: file, probability }`，喂 `ShadowQueue.enqueue()`。
- 如果 ToolPatternMiner 同时预测下一工具就是 `read_file`，则提高置信；如果下一工具不是只读工具，则不投机。
- 只对只读工具启用，不允许 write/edit/hash/bash 投机。
- 命中由 `tool-pipeline.ts` 的 `speculativeHit` 真实消费；失败沉默，不影响主路径。

不要把「文件预测」硬塞成 `grep` 或 `glob` 预测；Physarum 预测的是文件，不是搜索模式。工具预测仍由 ToolPatternMiner 负责。

### 步骤 F — Prewarm 只作为 page-cache 预取；内容缓存另立设计

`predictNext → batchPrewarm` 可以保留，但成功标准只能是：

- 后续真实读取是否访问了该文件；
- 真实读取延迟是否下降；
- 是否未绕过 contextWindow read cap。

若未来要恢复 `read_file` 内容缓存命中，必须重新设计：

- cache key 包含 `canonicalPath + contextWindow + providerProfile + readCap + offset/limit/full-file`；
- payload 带 cap metadata；
- 命中前验证 cap 兼容；
- 写入后按 canonical path 精确 invalidation。

这属于独立任务，不并入 T2-01。

### 步骤 G — ToolPatternMiner 跨 session 持久化，落 MeridianDb

P3 工具 bigram 是有用的，但现在纯内存。可与 Physarum 同源落 MeridianDb：

- 新增表或通用 `p3_state` KV（带 `kind/version/json/updated_at`）。
- 保存 ToolPatternMiner bigrams/trigrams。
- 启动时加载，DB 不可用时 no-op。
- 注意版本化；不要把它写进 `.rivet/knowledge` 或 prompt。

## 4. 影响面与边界

- **新增能力**：前瞻式 + 跨 session 的文件/工具预测（当前无此完整维度）。
- **通道**：全程文件 IO / runtime（B 臂），零 prefix-cache 代价，不动 prompt 结构。
- **持久化落点**：全部 MeridianDb，不新建 store（避免 canonical memory 碎片化）。
- **不归并**：Physarum STDP（有向时序）与 MeridianBehavior co-edit（对称共编辑）互补非重叠。前者喂 `predictNext`/投机预取，后者喂 `repo_graph` relevance。
- **免疫边界**：本任务不升级 immune graph_anomaly；只要求停止错误输入污染。ImmuneHook 可继续作为 Physarum 消费者（`detectAnomaly`、`freezeNode`、`boostEdges`），不再作为原始文件图生产者。
- **不碰 prompt**：任何预测结果默认不注入 prompt；如需可视化，只走 telemetry 或 tool-result 附带短诊断，另开设计。

## 5. 推荐实施顺序

### P0：文件事件与污染隔离

- 新增结构化文件事件观察器。
- 停止 `recordFlow(toolName, targetFile)` 写工具名边。
- 加载过滤/迁移清理 `physarum_edges`。
- 修 `recordSequentialEdit` 方向语义。

### P1：Shadow 观测

- 每次真实文件访问后记录 `predictNext(currentFile)` top-K。
- 下一次真实文件访问到来时计算 hit@1 / hit@3。
- 不改变工具执行，不注入 prompt。

### P2：接 P3 IdleSpec

- 将高置信文件预测转成 `read_file` ShadowQueue 投机。
- 记录投机来源：`tool-pattern` vs `physarum-file` vs `combined`。
- 输出命中率与误报率。

### P3：持久化 ToolPatternMiner

- 增 MeridianDb schema / KV。
- 启动加载、退出/定期保存。
- DB unavailable 保持 no-op。

### P4：Prewarm page-cache 与 repo_graph 时序边

- `predictNext → batchPrewarm` 只做 page-cache 预取。
- `repo_graph` 引入 Physarum 时序边作为 score boost，另开实现计划。

## 6. 验收

| 层 | 验收项 |
|---|---|
| 文件事件 | read/write/edit/hash_edit 记录真实文件；grep path、bash command、目录、工具名不记录 |
| 污染过滤 | `physarum_edges` 中不再出现 `read_file`/`grep`/`bash` 这类工具名节点 |
| Physarum 方向 | `recordFlow + recordSequentialEdit` 后 `predictNext` 有方向性；正反方向测试都通过 |
| ShadowQueue | Physarum 来源能 enqueue `read_file` 投机，且只读工具限制生效 |
| P3 target 语义 | ToolPatternMiner 不再把上一个工具 target 当成当前工具文件预测；文件 target 由 Physarum 或结构化事件提供 |
| 持久化 | 重启后 Physarum 边与 ToolPatternMiner 状态均可从 MeridianDb 恢复；DB 缺失时 no-op |
| Prewarm 安全 | 不绕过 `read_file` contextWindow cap；不以 PrewarmCache hit 作为成功标准 |
| Prefix cache | prompt 字节不变；预测链走 B 臂 |

## 8. 瑶光复现纪律补充（门神视角）

> 我不改天权的设计。我做三件别人默认不做的事：把缺陷归族、把弱验收升级成"当前代码上必须 RED 的门"、标出会让整轮 P0 白做的边角。

### 8.1 事实脊柱复核（PASS）

§2 的 grep 锚点我已在上一会话逐条核实：`physarum-engine.ts` 的 `recordFlow`/`recordSequentialEdit` 签名与字典序边规范化、`immune-hook.ts:65` 的 `recordFlow(ctx.toolName, ...)` 错接、`predictNext` 生产零调用——全部成立。计划的事实地基可信，可在此之上施工。

### 8.2 缺陷归族：这是「绿而空心」族（green-but-hollow）

T2-01 修的不是一个孤立 bug，是一族结构性缺陷：**零件造好了，最后一根线接上了，但喂进去的是错的/空的**（考古文档同族，[[staleness-not-zero-consumers-discriminator]]、我的审查法 §23「接上了≠喂对了」）。physarum 当前正是此族的活样本——`recordFlow` 确实被调用（线接着），喂的却是工具名（喂错了）。

**这族缺陷的复发点在本计划里就埋着**：每一个「接通」步骤（A 观察器、E 消费者、G 持久化）都能交付一个「线接上、测试绿、但喂错」的假完成。所以下面的验收门全部针对「喂对没有」，不是「接上没有」。

### 8.3 强制 RED 门（升级 §6 验收）

§6 验收表里以下三项必须从「断言通过」升级为「在当前代码上先跑出 RED」——不能复现旧缺陷的测试是未验证的猜测：

| 门 | 构造 | 必须 RED 的条件 | 防的空心 |
|---|---|---|---|
| **方向门**（已在 §C，保留为强制门） | 喂 `b.ts → a.ts`（反字典序）序列 | 若 `recordSequentialEdit` 方向符号写反，`predictNext('b.ts')` 不给 `a.ts` 优先 → RED | direction 标量在字典序边上抵消/写反 |
| **污染门** | 向 db 写一条任一端是工具名的边，再 `loadFromDb` | 若加载过滤缺失，被污染边仍进图 → RED | 旧 `recordFlow(toolName,...)` 边继续影响 ubiquity/homeostatic |
| **喂对门**（本族核心） | 真实跑一次 read_file 工具事件 | 若观察器仍取 `target` 兜底而非结构化 `file_path`，`recordFlow` 第一参数不是 repo-relative 文件路径 → RED | 观察器「接上了」但喂的还是旧 target 兜底（§89 警告的正是这个） |

喂对门是这族缺陷最易复发的一环：§89 已警告不要依赖 `RuntimeToolEvent.target`/`ImmuneHookContext.targetFile`，但执行者最省力的实现恰恰是复用这两个字段——交付一个「绿但喂的是 command.slice 兜底」的假完成。这个门必须钉死。

### 8.4 §D 一个未闭合的边角：合法历史边会被误删

§D 的一次性迁移按「任一端不是合法 repo 文件就删」清污染。**但「已删除/改名的文件」也不再是当前合法 repo 文件**——它们的边是合法历史共访，会被这条规则连坐删掉。§121「防止误删合法边」点到了，没给判据。

建议 clean-time 用 **path-shape 判据**（是否像工具名 / 命令片段 / 目录 / 空串 / 不可索引扩展）判污染，而不是「该文件现在是否存在」。文件正常的增删改不该被当成污染清理；只有「从来不该是文件的东西」才删。
