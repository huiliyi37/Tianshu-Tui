# 天枢桌面架构 v2 · 引擎具身化

> 日期：2026-06-09
> v1 被否：把免疫/CVM/Physarum/注意力做成可视化面板——方向错了。那些是后台基础设施，用户不需要看。
> v2 聚焦：天枢真正的价值引擎——自由能引擎、具身智能、智能路由、Team Max、审查门、学习闭环——如何在桌面形态中作为一等公民能力被用户使用。

---

## 0. 天枢真正的价值引擎

梳理最近 T2/T3 系列的成果（非文档声明，代码坐实）：

| 引擎 | 代码 | 做什么 | 为什么 Codex/Antigravity 没有 |
|---|---|---|---|
| **自由能引擎** | `prediction-error.ts`(computeEFE) + `policy-selection.ts`(selectPolicy) | 基于 Expected Free Energy 主动推理最优动作——不是被动反应，是最小化预期自由能的行动选择 | 他们用 LLM 直接输出 next action；天枢用 active inference 公式计算后再选 |
| **CVM 引擎** | `sycophancy-trap.ts` + `virtue-signals.ts` + `dissipative-kick.ts` + `behavior-mirror.ts` + `projection-detector.ts` + `sensorium.ts` | **元认知引擎**——"我在想清楚吗？" 谄媚检测→质疑注入、投影检测→校准、僵局检测→耗散踢、五常美德→静默累积正面信号。不是被动监控，是主动自我校准 | 他们的 agent 从不质疑自己的判断——要么盲从用户，要么盲信自己。天枢会对自己说"等一下，我可能在附和" |
| **具身智能** | `loop.ts`(AgentLoop) + `tools/*` + TUI/桌面 | agent 有身体：能读写文件、执行命令、操作浏览器——身体不是装饰，是自由能引擎降低 uncertainty 的手段 | 他们有，但 agent 是无状态的 worker；天枢的 agent 有 self/world 边界、有认知季候、会累 |
| **智能路由** | `model-policy-selection.ts` + `model-tier-bandit.ts` + `routing-reward.ts` | 多模型选择不是硬编码——用 Bandit 学习哪个模型在什么场景下表现好，reward closure 闭环反馈 | 他们锁单一模型（Codex 锁 GPT-5-Codex）或手动选（Antigravity） |
| **Team Max** | `team-orchestrator.ts`(runTeamSkeleton) + `team-scheduler-bandit.ts` + `team-scope-health.ts` | 多 worker 并行编排 + Bandit 调度 + scope 越界检测 | 他们有 worker 并行，但没有 Bandit 调度优化、没有 scope-health 越界检测 |
| **审查门** | `review-router.ts` + `review-discipline.ts` + `delivery-gate-v2.ts` | L1(verify)/L2(review)/L3(squadron) 对抗审查——agent 挑战 agent 的决策，不是人审 | 审查/批准都靠人；天枢的审查门是 agent 对 agent 的对抗验证 |
| **学习闭环** | `reward-loop.ts`(recordRoutingRewardClosure) + `team-reward.ts` + `routing-reward.ts` | 从行动结果中学习：路由决策→结果→reward→更新 Bandit→下次更好 | 无跨会话学习；天枢从每次路由/编排决策中学习并优化 |

**这七个引擎才是天枢真正的差异化。其中 CVM 是元引擎——它不直接产生用户可见的输出，而是渗透在所有其他引擎中，让天枢的每个决策都经过自我校准。**

## 1. 桌面架构核心命题

不是"把 TUI 换成 GUI"。是：**天枢的七个引擎在桌面形态中各得原生表达。其中 CVM 是元引擎——它渗透到其他六个引擎的每个决策点中。**

| 引擎 | TUI 中的表达 | 桌面中的表达 | CVM 渗透点 |
|---|---|---|---|
| 自由能引擎 | 不可见（后台计算 EFE→选 tool→执行） | **认知驾驶舱**：实时展示 EFE 推理过程——epistemic vs pragmatic 权衡、为什么选这个动作 | 谄媚检测触发 → epistemic 飙升；投影检测 → precision 降低；僵局检测 → novelty bonus 注入 |
| CVM 引擎 | 完全不可见（只注入 prompt 不展示） | **不独立成面板**——渗透到所有其他面板中。在对话流中标注 CVM 干预时刻，在 EFE 四元组旁显示 CVM 信号源 | — |
| 具身智能 | Ink TUI + 线性消息流 | **多窗口工作空间**：editor/terminal/browser 是 agent 的手 | 耗散踢触发 → agent 主动切换工作窗口；行为镜像 → agent 重读刚才改的文件 |
| 智能路由 | 不可见（后台选模型） | **路由控制台**：当前模型、选择理由、Bandit 学习状态、可手动 override | CVM 开销追踪影响模型选择：overhead 高 → 切轻量模型；谄媚检测触发 → 切高能力模型重新审视 |
| Team Max | `/team max` 命令 + 文本输出 | **团队指挥中心**：wave 调度、worker 卡片、scope-health 告警、Bandit arm 表现 | 每个 worker 有微型 CVM 指示器：是否盲从用户指令、是否陷入局部僵局 |
| 审查门 | `deliver_task` 文本输出 | **交付控制台**：L1/L2/L3 审查进度、对抗发现、门禁状态、一键提交 | 五常美德信号参与门禁判定：信(cache-loyalty) 未达标 → 黄灯 |
| 学习闭环 | 不可见（后台 reward closure） | **学习仪表盘**：Bandit 收敛曲线、team 调度奖励趋势、模型 tier 升降 | CVM 触发次数趋势：谄媚频率下降 = 学习有效 |

**CVM 不单独成面板——它是"为什么 agent 这样做"的解释层，散布在所有其他面板中。**

## 2. 对标分析（不是比面板，是比引擎）

| | Codex 桌面 | Antigravity 2.0 | 天枢桌面 |
|---|---|---|---|
| 行动选择 | LLM 直接输出 next tool call | LLM 直接输出 | **自由能引擎**：EFE 最小化驱动 |
| 模型选择 | 只用自己的模型 | 多模型但手动选 | **智能路由**：Bandit 学习+自动选择 |
| 多 agent | worktree 并行 | workspace 并行 | **Team Max**：Bandit 调度+scope-health |
| 审查 | 人审 diff/action cards | 人看 artifacts | **审查门**：agent 对抗 agent |
| 学习 | 无 | 无 | **学习闭环**：reward→Bandit→更好 |
| 具身 | computer use (beta) | browser 验证 | **全具身**：editor+terminal+browser+fs |
| 元认知 | 无——agent 从不质疑自己 | 无 | **CVM 引擎**：谄媚检测、投影检测、耗散踢、五常美德——渗透所有决策 |

## 3. 架构设计

### 3.1 技术选型

| 层 | 选择 | 对标 Codex |
|---|---|---|
| 桌面壳 | **Tauri 2.x (Rust)** | Codex 同款（codex-rs 是 Rust monorepo） |
| 前端 | **React + TypeScript** | Codex 用 Rust TUI；我们用 React（团队技能） |
| Runtime | **Sidecar 子进程** `rivet serve` | Codex 的 `app-server` 是 Rust 进程；天枢已有 Node server |
| 通信 | **HTTP/SSE + 扩展引擎 API** | Codex 用 JSON-RPC（app-server-protocol） |
| 多窗口 | **Tauri 多 webview** | Codex 的多 agent 每人一个 worktree |
| 打包 | **Tauri bundle** (macOS/Windows/Linux) | 同 |

### 3.2 与 Codex 架构对标

天枢复刻 Codex 的工程骨架（这些都是正确且必要的工程实践），然后在引擎层做差异化：

| Codex crate | 天枢对应 | 差异化 |
|---|---|---|
| `app-server` (Rust, 消息处理/线程状态) | `src/server/` + 扩展 session manager | **自由能引擎**注入行动选择 |
| `app-server-protocol` (JSON-RPC) | 扩展 SSE → 结构化引擎事件 | **智能路由**事件 |
| `app-server-daemon` (后台+自动更新) | Tauri sidecar 管理 | — |
| `agent-identity` (27KB) | `self-recognition.ts` self/world | 天枢的更深刻：不只"谁在用"，是"我是谁" |
| `agent-graph-store` | `meridian-db.ts` + `physarum-engine.ts` | 天枢的远超：不只是存状态，是神经演化 |
| `worktree` | `worktree-baseline.ts` | 已有基础 |
| `cloud-tasks` (TUI) | **认知驾驶舱 + 团队指挥中心** | 不只是任务列表，是认知过程可视化 |
| `cli` (134KB main.rs) | `rivet` CLI（已有） | 保留 |

**关键差异**：Codex 的 computer use 是 beta——agent 操作你的桌面。天枢的具身是 agent 在**自己的**工作空间里操作——editor/terminal/browser 是 agent 的"手"，不是你的桌面。你看着 agent 工作，而不是 agent 接管你的鼠标。

## 5. 实施路线

### 5.1 四条硬红线

1. `AgentLoop` 核心不改
2. `deliver_task` / ownership-ledger 不改
3. prompt frozen/cache 不变量不破
4. T6 self/world 判定不改

### 5.2 三阶段

| 阶段 | 内容 | 引擎覆盖 |
|---|---|---|
| **Phase 1: 骨架** | Tauri 壳 + React 前端 + sidecar 通信 + 多会话 API | 具身智能（基础多窗口） |
| **Phase 2: 引擎面板** | 认知驾驶舱 + 团队指挥中心 + 路由控制台 | 自由能引擎 + Team Max + 智能路由 |
| **Phase 3: 完整形态** | 交付控制台 + 学习仪表盘 + 具身工作空间(editor/terminal/browser) + 打包分发 | 审查门 + 学习闭环 + 完整具身 |

### 5.3 不做的事

- 不做器官仪表盘（免疫/CVM/Physarum/注意力）——CVM 渗透到其他面板，不独立成面板
- 不做完整 IDE —— editor 是 agent 的工具面，不是人的开发环境
- 不做 Browser 工具（M4 前）——新攻击面，后置
- 不做 M0 探针——直接到完整通信层

### 5.4 Phase 1 立即开始

```
分支: G1xT8-desktop (已切)

1. Tauri 项目初始化 (desktop/ 子目录)
2. React 前端骨架 (主窗口 + 消息流 + 输入)
3. Sidecar 通信层 (spawn rivet serve + token)
4. 多会话 API (runtime-session-manager.ts)
5. 基础事件流 (SSE → React state)
```

## 6. 与 v1 的关键差异

| | v1（器官具身化） | v2（引擎具身化） |
|---|---|---|
| 核心命题 | 器官在视觉空间活过来 | 引擎在桌面形态可被使用 |
| CVM 表达 | CVM 仪表盘（被否——用户不需要看后台） | **CVM 渗透所有面板**：EFE 修正、路由影响、per-worker 状态、五常门禁、趋势——自然融入而非独立面板 |
| 免疫表达 | 免疫监视器（被否） | 不可见——免疫是 CVM 的输入通道，不是用户面 |
| Physarum 表达 | 神经拓扑图（被否） | 不可见——Physarum 是 generative model 的 A/B 矩阵 |
| 自由能引擎 | 未出现 | **认知驾驶舱**——EFE 推理 + CVM 信号源标注 |
| 智能路由 | 未出现 | **路由控制台**——Bandit 学习 + CVM 开销影响 |
| Team Max | 未出现 | **团队指挥中心**——Bandit 调度 + per-worker CVM |
| 审查门 | 未出现 | **交付控制台**——L1/L2/L3 + CVM 五常门禁 |
| 学习闭环 | 未出现 | **学习仪表盘**——reward 曲线 + CVM 趋势（谄媚/僵局/投影频率下降） |
| CVM 定位 | 独立仪表盘 | 元引擎——"为什么 agent 这样做"的解释层 |
