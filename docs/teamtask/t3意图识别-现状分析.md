## 一、数据流全景（已实现）

```
用户消息
  │
  ▼
IntentRetrievalRouteController.buildForTurn()
  │
  ├─ getLastAssistantMessageContent()          ← 倒序遍历 messages 取最后一条 assistant
  ├─ sessionStateManager.extractTaskList()     ← 从 assistant 回复提取任务列表持久化
  ├─ sessionStateManager.updateTaskListItem()  ← 跟踪用户引用的编号状态
  │
  ▼
classifyIntentRetrievalRoute()
  │
  ├─ [llm 模式] buildIntentRouterPrompt()
  │     ├─ resolveContextualIdentifier()       ← 1. 先查 lastAssistantMessage
  │     │                                        2. 未命中查 taskList 持久化回溯
  │     ├─ enrichUserMessageWithContext()      ← P1 → P1 (上下文关联任务: 修复 loop.ts)
  │     ├─ sanitizeForIntentClassification()   ← 文档编号 → [REF]
  │     └─ 注入 contextLines + strippedTokens 到 LLM Prompt
  │
  ├─ LLM 4s 超时 → 失败/超时 fallback
  │
  └─ [heuristic 模式 / fallback] buildHeuristicRetrievalRoute()
        └─ inferTaskKinds()
              ├─ 1. resolveContextualIdentifier
              ├─ 2. enrichUserMessageWithContext
              ├─ 3. sanitizeForIntentClassification
              ├─ 4. extractSemanticVerb
              ├─ 5. 正则匹配 (修复→bug_fix, 审查→review_audit, ...)
              ├─ 6. disambiguateByVerb (多候选时动词语义优先)
              └─ 7. followUp 继承 (上一轮 taskKinds 优先)
```

### 2.4 intent-retrieval-route-controller.ts ✅ 已实现（架构优于设计）

设计文档预期在 `loop.ts` 中内联实现，实际抽成了独立 `IntentRetrievalRouteController` 类：

| 功能 | 状态 |
|------|------|
| `getLastAssistantMessageContent` 倒序取最后一条 assistant | ✅ |
| `extractTaskList` 从 assistant 回复中提取任务列表持久化 | ✅ |
| `updateTaskListItem` 跟踪用户引用编号的状态变更 | ✅ |
| `followUp` 模式继承上一轮 taskKinds | ✅ |
| `debugLog` 遥测输出 | ✅ |

**集成点（loop-factory.ts）**：`loop-factory → createTurnHooks → controller.buildForTurn(userMessage)`，在每轮开始时注入路由。

**消费链路**（路由结果如何到达主模型）：
```
IntentRetrievalRouteController.buildForTurn()
  → setIntentRetrievalRoute(routeXml)
    → promptEngine.setIntentRetrievalRoute(routeXml)
      → volatile.ts buildDynamicAppendix
        → <intent-retrieval-route> XML 块注入 system prompt
```
这条链路解释了为什么 Section 三.1 的 `context-intent-association` 规则至关重要——分类器给出了正确路由，但主模型执行阶段缺少 System Prompt 约束时，`<intent-retrieval-route>` 块的实际效果大打折扣。路由告诉模型"这个任务是什么类型"，但如果没有 context-intent-association 规则，模型在遇到 `P1` 时仍可能去搜索名为 `P1` 的文件。

### 2.7 projection-scorer.ts ✅ 已实现

### 2.8 anchor-vault.ts ⚠️ 间接覆盖

设计文档要求排除 P1/P2/T1 成为 anchor phrase。实际通过两层机制间接覆盖：
1. `AnchorVault.seal()` 内部调用 `sanitizeForIntentClassification`，P1 已被替换为 `[REF]`
2. 标识符匹配正则 `[a-zA-Z_][a-zA-Z0-9_]{2,}` 要求最小 3 字符，P1/T2 等 2 字符 token 被排除

**注意**：CJK 路径 `[一-鿿]{2,6}` 没有最小长度排除逻辑——中文短词（如"做""修"）也可能被纳入 anchor phrases，存在过度密封的风险。目前通过 `STOPWORDS` Set 部分缓解（含"帮我""帮""请""能""会"等虚词），但未覆盖所有高频单/双字动词。

**结论**：P-编号排除已满足，无需额外改动。CJK 短词风险当前影响有限（stopwords 兜底），但值得关注。

### 2.9 prompt/static.ts ❌ 未实现 — 关键缺失

设计文档要求在 `<rules>` 节点下增加 `<rule name="context-intent-association">`：

```xml
<rule name="context-intent-association">
当用户反馈或指令中包含 P1、P2、T1、T2 等编号，或者"刚才说的那个"、"你列的第一个"时，
这通常是指代你在上一轮回复中提出的任务计划、选项或问题：
1. 你必须首先检索和回顾你上一轮回复的具体内容，找出该编号或代词所映射的具体任务
2. 将你的注意力和后续操作锁定在被指代的具体任务语义上
3. 编号只是一个上下文临时引用，不是任务类型
</rule>
```

**影响**：分类器层面已正确处理编号→任务映射，但**主模型执行阶段**没有 System Prompt 约束。用户说"做 P1"时，分类器正确识别 `bug_fix`，但主模型可能在执行时跑到整个项目搜索名为 `P1` 的文件或旧文档。

**插入位置**：`src/prompt/static.ts` 第 85 行（`</rules>` 闭合标签之前，`context-update-protocol` 规则之后）。

## 三、缺陷清单

### 3.1 【高】prompt/static.ts 缺少 context-intent-association 规则 ✅ 已修复 (ca4f3853)

- **根因**：设计文档要求的 System Prompt 规则未落地
- **影响**：主模型执行阶段缺少编号→任务强制关联约束
- **修复**：在 `src/prompt/static.ts` 的 `<rules>` 块末尾插入 `<rule name="context-intent-association">` 规则（commit ca4f3853）

### 3.2 【中】resolveContextualIdentifier 不支持序数词 ✅ 已修复

- **根因**：原实现只匹配 `P1/P2/T1` 等编号格式，不匹配 "第一项/第一个/第1个"
- **影响**：Agent 回复为纯叙述（如"第一项是修复 loop.ts"）时无法解析
- **修复**：新增 `extractOrdinalReferences` + `resolveOrdinal` + `extractListItems` 函数链，支持中文/阿拉伯数字序数词（第一个/第二项/第3个），解析后按 1-based 索引从 lastAssistantMessage 列表条目取值，未命中则回退到 taskList

### 3.3 【中】LLM 分类器默认关闭

- **根因**：`DEFAULT_INTENT_RETRIEVAL_ROUTER_CONFIG.classifier = 'heuristic'`
- **影响**：精心设计的脱敏 LLM prompt 从未被消费，所有分类走启发式正则
- **建议**：考虑对含编号引用的消息自动升级到 LLM 分类器，或在 LLM router prompt 语义足够清晰后默认开启

### 3.4 【低】disambiguateByVerb 单动词决定可能存在误判 ✅ 已修复

- **根因**：`extractSemanticVerb` 返回第一个匹配的动词（按 key 长度降序），`disambiguateByVerb` 将其映射到的 taskKind 无条件提升到首位
- **案例**："test the bug fix" → `test` 映射到 `verification`，但真实意图可能是 `bug_fix`
- **修复**：引入 `UNDEMOTEABLE_KINDS` 集合（security_safety, bug_fix），当候选中存在这些高优先级类型时，动词不可将其他类型提升到它们之上

### 3.5 【低】resolveContextualIdentifier 的 Markdown 解析鲁棒性有限

- **根因**：正则模式支持 `- P1: xxx`、`**P1**: xxx`、`1. P1: xxx`、`P1 -> xxx`，但 Agent 回复格式偏离时失效
- **影响**：纯文本叙述格式无法解析
- **当前降级**：解析失败时 fallback 到编号脱敏（P1 → [REF]），分类器退化为常规意图识别

## 五、优化建议（优先级排序）

1. **【立即】补齐 prompt/static.ts 的 context-intent-association 规则** — 插入位置明确，改动量小，影响面大
2. **【建议】对含编号引用的消息自动启用 LLM 分类器** — 当前 `classifier: 'heuristic'` 默认使得设计文档的脱敏 prompt 从未被 LLM 消费
3. **【可选】增强 resolveContextualIdentifier 的序数词支持** — 补充 "第一项/第一个/第1个" 解析
4. **【可选】disambiguateByVerb 添加多候选置信度衰减** — 防止单动词误判覆盖真实意图
