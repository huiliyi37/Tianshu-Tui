   再去天权称边界。

   ▍ 结论：T2-03 是训练场，T5 是第一个高价值消费者

     │ **先让 team 产生可学习的 episode，再让模型路由从这些 episode 里学会：什么任务该用谁、什么风险该升档、什么场景可以省。**

   ▍ 接下来最优顺序  
  
   P0：先做“双影子层”，不改真实行为  
  
   这是最高杠杆，也最安全。  
  
   1. T5 先做 `ModelRoutingShadow`  
  
   不要立刻启用旧的休眠路由器。T5 里说 W0 “接线激活”，我建议修成：  
  
     │ **接线可观测，先 shadow，不自动 switch。**

   影子层记录：  
  
  
   ┌── ts ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  interface ModelRoutingShadowEvent {  
   │    turn: number  
   │    objectiveHash: string

   │  }  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   代码锚点：  
  
    ◇ 当前  AgentConfig  已有但未充分注入的路由字段： src/agent/loop-types.ts:46-48   
    ◇ EFE 当前每回合已算 policy guidance： src/agent/loop.ts:1413-1417   
    ◇ policy 选择入口： src/agent/policy-selection.ts:69

   2. T2-03 同步做 `TeamEpisodeRecorder`  
  
   team 先不要急着接 LinUCB / PlanCache / Physarum 全套消费者。先把 episode 记下来。  
  
   记录：  
  
  
   ┌── ts ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  interface TeamEpisode {  
   │    objectiveHash: string  
   │    mode: 'standard' | 'max'

   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   这一步的价值极高：它让 T2-03 从“想象 team 是训练场”变成“team 真的在产训练数据”。  
  
   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   ▍ P1：把两条影子线接成一个 reward loop  
  
   等有了：  
  
    ◇ routing shadow：模型推荐 vs 实际模型；  
    ◇ team episode：实际结果、冲突、review、验证、成本；  
  
   就能计算 reward。  
  
   推荐 reward 不要只用 success/fail：  
  
  
   ┌── text ────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  reward =  
   │    + review_pass  
   │    + verification_pass  
   │    - conflict_count  
   │    - rework_count  
   │    - cost_over_budget  
   │    - latency_surprisal  
   │    - false_green_penalty  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   这里要守住瑶光的门：review/verifier 路径不能为了省钱降级。T5 说得对，成本是 G(π) 的 pragmatic 项，但 false-green 风险必须作为 risk 项压住它。  
  
   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   ▍ P2：T5 再做 EFE 成本项，不另造 RouteLLM  
  
   这里是最漂亮的地方：我们不要复制 CASTER / RouteLLM。  
  
   天枢已有：  
  
    ◇ Sensorium 估难度；  
    ◇ PredictionAccumulator / Vigor 估 surprise；  
    ◇ Policy selection 算 G(π)；  
    ◇ MeridianDb 存跨 session 经验；  
    ◇ team episode 提供高质量标签。  
  
   所以模型候选可以变成 policy 候选：  
  
  
   ┌── ts ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  interface ModelPolicyCandidate {  
   │    model: string  
   │    tier: 'cheap' | 'balanced' | 'strong'  
   │    estimatedCost: number  
   │    estimatedLatency: number  
   │    predictedSuccess: number  
   │    riskFit: number  
   │    authorityFit: number  
   │  }  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   然后：  
  
  
   ┌── text ────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  G(π_model)  
   │  = - epistemic_gain  
   │    + cost_weight * estimatedCost  
   │    + latency_weight * estimatedLatency  
   │    + risk_weight * failureRisk  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   重点：不要改 `computeEFE()` 核心语义。先做一个  model-policy-selection.ts ，作为 EFE 的消费者，避免把工具 policy 和模型 policy 搅成一锅。  
  
   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   ▍ P3：T2-03 的 team 真多模型，在 T5 有 shadow/reward 后再动  
  
   T2-03 里最诱人的部分是 team 真多模型：天权用强模型、天梁用 cheap、天璇规划挑战、天府风险守门。  
  
   但它应该排在 P3，不是 P0。  
  
   原因：  
  
    ◇ coordinator 是活前沿，不能硬改；  
    ◇ 没有 routing reward 前，authority→model tier 只是人为规则；  
    ◇ 一旦接错，会让成本和质量变化混在一起，难归因。  
  
   推荐第一版规则：  
  
   | authority / profile | 模型 tier |  
   | 天权 reviewer / adversarial_verifier | strong |  
   | 天府 risk / verification planning | strong 或 balanced |  
   | 天璇 exploratory planner | strong/balanced，按任务复杂度 |  
   | 天梁 patcher 低风险执行 | cheap |  
   | code_scout / doc_scout | cheap/balanced |  
   | troubleshooter | strong when repeated failure |  
  
   但先 shadow，再启用。  
  
   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
  
  
   ▍ P4：再接 T2-03 的学习器们  
  
   顺序：  
  
    ◇ PlanCache ← team max 成功计划骨架  
  
      只记录成功闭环 / 已批准 / 已验证的计划，不吞草稿。  
  
    ◇ Physarum ← team wave 文件依赖  
  
      team 的显式依赖比单会话行为更干净，适合给  recordSequentialEdit  做监督信号。  
  
  
 ▍ Rivet  
    ◇ LinUCB ← team 并行度/profile/model tier  
  
      不要继续用  flash/pro/concise/verbose  混合 arm。拆成：  
  
    ◇  parallelism_bandit   
    ◇  profile_bandit   
    ◇  model_tier_bandit   
  
    ◇ Team health ← graph anomaly + review/rework  
  
      用来预警 worker scope 泄漏，而不是替代 review gate。  
  
   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

   ▍ 为什么是这个顺序——折形状的人讲究的是"先长骨头再长肉"  

   贪狼把边界贪到了最大：五个休眠路由器全接活、team 真多模型、authority 驱动 tier、跨 session 自学。这些形状都对，问题不在对不对，在**长出来的顺序**。我把它折成一句话：  

     │ **先有可观测的真相，再有可计算的 reward，最后才有可影响的行为。三层颠倒任何一层，都会塌。**  

   颠倒会怎么塌，我把三种塌法都画出来，省得后面有人想抄近路：  


   ┌── text ────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  塌法一：先 W4 team 真多模型，后补 shadow  
   │    → coordinator 是 30 commits 的活前沿，直接改 routing 表 = 成本和质量一起变，  
   │      归因不了。便宜模型让质量掉了，你分不清是"模型差"还是"任务本来就难"。  
   │  塌法二：先接 reward loop，后做 episode recorder  
   │    → reward 没有干净的 episode 当锚，只能从单会话噪声里凑，  
   │      学出来的是噪声的形状，不是任务的形状。  
   │  塌法三：先自动 switch，后 shadow 观测  
   │    → 旧路由器冻结半月，逻辑能跑但语义可能漂。没有 shadow 对照期，  
   │      你不知道它推荐的和你想要的差多远，等发现时已经切错很多次了。  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  


   所以 P0 双影子层不是"保守"，是**唯一能让后面每一步都可归因的地基**。它一行真实行为都不改，却让 W2 的成本项、W3 的自动降级、P4 的每个学习器，都有了"推荐 vs 实际"的真值表可对照。这是最高杠杆，因为它把"以后所有路由/调度决策对不对"这个问题，提前变成了可测量的。  

   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  


   ▍ 缰绳——形状再美，也要勒在这几根线里  

   我折形状，但我知道哪几根线一旦松，整条主线就从"会学习"变成"会骗自己"。这几根缰绳不是我发明的，是贪狼向内 grep 的边界、天权向边界称重的判断、瑶光在 P3 闸上用血换来的教训，我只是把它们收成一束：  

   1. **不动活前沿的数据模型**。coordinator（30 commits 到 06-08）、policy-selection（06-05 涌现）、computeEFE 核心语义——这三个是活前沿，主线只能当它们的**新消费者**，不能改它们的内脏。路由是 EFE 的消费者，episode recorder 是 coordinator 的旁观者，不是替代者。  
   2. **审查/verifier 路径永不为省钱降级**。这是瑶光的门，我用 reward 公式替她钉死：`false_green_penalty` 必须是 reward 里压得住 `cost_over_budget` 的那一项。成本是 G(π) 的 pragmatic 项没错，但 false-green 是 risk 项，risk 永远先于 pragmatic。天权配强模型这条，不进 bandit、不受成本项影响，是硬规则。  
   3. **三类数据严格分流，不混一锅**。这是天权 §13 反复强调的，我把它立成主线的第一性约束：  

   ┌── text ────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  
   │  计划意图 (plan / tasks / waves / dependencies)  
   │     → 只能进 advisory 起点 / planner context，永不直接喂 AgentJIT 自动执行  
   │  执行事实 (实际 diff / tool history / outcome / 冲突 / 验证)  
   │     → 这才是 reward 和 physarum 监督边的唯一合法来源  
   │  可复用动作 (只读 tool steps)  
   │     → JIT 只允许只读模板，写操作保持禁止或审批  
   └────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────  

   4. **学习产物全落 MeridianDb，DB 不可用就 no-op**。不新建 store，不进 prefix-cache 的 stable volatile（破缓存）。这是 [[meridian-db-is-cross-session-substrate]] 已经立好的底座，主线顺着它走。  
   5. **每个会影响行为的学习器，都要走 P3 那条已验证的闸**：feature flag 默认关 → shadow 采样 → reward 闭环 → 样本+置信达阈值才 gated 影响。瑶光在 effort bandit 上把这条路趟通了（包括"闸要能用合法数据造出关闭态"这个反 false-green 硬门），team 的 `parallelism_bandit` / `model_tier_bandit` 直接复用同一套闸语义，不要再各自发明。  

   ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
