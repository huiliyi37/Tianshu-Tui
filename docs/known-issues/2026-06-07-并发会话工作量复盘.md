- **关于"审查"的定性（已与 [`2026-06-07-一次认知校准的全过程.md`](2026-06-07-一次认知校准的全过程.md) 后续校准对齐）：** 本文档早期草稿曾把两侧描述为「红蓝对抗 / 交付与审查解耦」的常态结构 —— 这是外部 Claude Code Opus 审查侧会话的误读。**真实模型：** 各交付会话本身仍应保持 TDD 自闭环（冷启动 → 自考古 → 测试前置 → 执行 → 验证 → 交付），但外部 Opus 式客观审查能力不能假设长期在场。正确方向不是放弃 review workflow，而是把“提交已存在、测试已绿也不轻信”的外部视角内化进天枢自己的 ReviewRouter / verifier / squadron 工作流，用来辅助主控发现自己容易忽略的问题。
- 并发多会话的真正增益，是**多条独立自闭环线并行推进**本身；审查侧的额外价值，是**测量与校准**，并将校准结果沉淀成可复用的内部审查机制。
