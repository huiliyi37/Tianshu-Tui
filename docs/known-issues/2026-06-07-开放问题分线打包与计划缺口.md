# 开放问题分线打包 + 计划缺口评估

记录: 2026-06-07
用途: 把当前**开放且无修复计划**的问题按会话线打包,供分派;并评估"发现 vs 计划"产出节奏。
数据源: perf-and-recovery-audit / async-io-audit / tui-streaming-audit + 三个并行扫描。

---

## 一、核心结论(回答"天枢节奏跟得上吗")

**有计划的产出 = 功能/设计线**(7 条):intent-retrieval-router、review-discipline+squadron、
task-lifecycle-system、adversarial-verifier+cron-lease、conversation-render-architecture、
async-io-tools(18 工具转换)、spec-a-b-handoff。这些都有正式 spec/plan,可放心执行。

**无计划的产出 = 审查/审计发现**:
- T1 审查 ~18 项(S-1~S-6 / C-1~C-5 / A-1 / CK-1/2 / X-1 / L-1 / M1/M2):**即兴发现 → 当场修 → 事后才写 closure ledger**,无前置修复计划。
- 审计开放项 ~13 项:**完全无计划、且未修**(下表)。

> **节奏判断**: 计划侧(天枢)在**大功能/设计线**上跟得上——每条线都有 spec。
> 但**对抗审查 / 性能审计这条 track,发现速度远快过计划产出**:发现要么被审查侧
> 即兴改掉(跳过计划),要么积压成无计划开放项。这就是"不敢放心丢子代理"的根因——
> 缺了「发现 → 修复计划 → 执行」中间那一环。
>
> 小修(P2 微优化)未必需要重型 design doc,但**至少要一行修复方案 + 影响面**才能安全派发。

## 三、计划缺口统计(发现 vs 计划)

| 类别 | 数量 | 有计划 | 无计划 |
|------|------|--------|--------|
| 功能/设计线 | 7 条 | 7 | 0 |
| T1 审查发现 | ~18 | 0(事后 ledger) | 18(即兴修) |
| 审计开放项 | ~13 | 0 | 13 |

**比值**: 功能线 100% 有计划;审查/审计发现 ~31 项中 **0 项有前置修复计划**。

## 四、建议流程(放心派发的前提)

1. **每线分派前补一行修复方案**: 即使 P2 小修,也写「根因一句 + 改法一句 + 影响面 + 验证方式」,
   再丢子代理。避免子代理自由发挥跑偏(参考 T1 里 C-4 误拒、a99e1f2 漏源码的教训)。
2. **TUI-F10 单独走设计**: 方向未定,不能直接派实施。
3. **correctness 项(压#8)优先于纯 perf 项**: 活引用是潜在数据正确性问题,先于微优化。
4. **api-client 线(网#4/6/7)优先**: 直接影响 recovery 可靠性,价值高于 perf 微优化。
5. **可合并项一起派**: 中#7+中#10(hot-path batch)、压#4+压#5(engine.ts)各合一个 PR。
