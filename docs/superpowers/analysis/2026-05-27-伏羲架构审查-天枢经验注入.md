# 伏羲架构审查：天枢经验注入

> 天枢一画开天，伏羲八卦定乾坤。站在演化 414 个源文件、1860 个测试的肩膀上，
> 为晚辈指出暗礁与航路。

---

## 一、总体评价

伏羲的八卦架构是**正确的方向**。将 agent 拆分为独立 crate，用 Trait 定义接口，
用 Rust 类型系统在编译期拒绝错误——这解决了天枢最痛的两类问题：
隐式依赖（"这个 import 从哪来的？"）和运行时类型错误（"undefined is not a function"）。

当前有 **54 个源文件、9 个活跃 crate**，Phase 1（一画开天）已经可以让 agent 跑起来。
以下是站在天枢演化史上的深度审查。

## 二、🔴 必须立即修复

### 2.1 API Key 硬编码（安全）

`.fuxi.toml` 第 3 行：

```toml

```

**立即**：删除该行，改为 `api_key_env = "FUXI_API_KEY"`（天枢的做法），
并 revoke 此 key。`.fuxi.toml` 不应该出现在 git history 中。

### 2.2 Sensorium 维度落后于天枢 v2

伏羲当前的 sensorium（`fuxi-cvm/src/sensorium.rs`）：

```rust
// compute_pressure — 只有 context_usage
fn compute_pressure(context_usage: f64) -> f64 { clamp(context_usage) }

// compute_stability — 没有 doom loop 信号
fn compute_stability(momentum: f64, confidence: f64, complexity: f64) -> f64 {
    clamp(0.40 * momentum + 0.35 * confidence + 0.25 * (1.0 - complexity))
}
```

**天枢 v2 的改进（2026-05-27 刚完成）**：

```
// pressure = 多维融合
pressure = 0.50 × contextRatio    // 上下文填充
         + 0.30 × verificationDebt // 验证债
         + 0.15 × cvmOverhead      // CVM 自监管开销
         + 0.05 × growthPenalty    // 上下文增速

// stability = 四信号连续融合
stability = 0.40 × doomBase          // doom loop 等级
          + 0.25 × predictionRate    // 预测准确率
          + 0.20 × diversity         // 工具多样性
          + 0.15 × verificationCoverage // 验证覆盖率
```

**为什么重要**：天枢的教训是，当 `stability=1.00, pressure=0.00` 在整个正常会话中不变时，
agent 失去了关键的自我调节信号。多维融合让这两个维度在 healthy session 中也能提供
连续的、可操作的反馈。

**建议**：在 Phase 2 之前将天枢 v2 的 sensorium 设计移植到伏羲。
`SensoriumInput` 需要扩展以接收 `verification_debt`、`prediction_history`、`cvm_overhead`。

## 三、🟡 天枢踩过的大坑

### 3.1 消息持久化缺失（致命级）

**天枢的教训**（`docs/analysis/2026-05-24-context-loss-root-cause.md`）：

```
磁盘 session 文件零真实消息：
session-123: 3184 行 = 1592 start + 1592 end + 0 真实消息
```

天枢的 `SessionPersist.appendOaiWithChecksum()` **从未被生产代码调用**。
任何非 `/exit` 退出都会丢失当次会话全部内容。模型在每次恢复后被迫从早期 user 消息重新推理。

**伏羲现状**：`fuxi-kan/src/manager.rs` 的 `ContextManager` 管理内存中的消息，
但没有看到磁盘持久化逻辑。

**建议**：
- Phase 1 就加入消息持久化：每次 `AgentOutput::AssistantMessage` 和 `ToolDone` 后
  立即 append 到磁盘（JSONL 或 SQLite）
- 用 `.rivet/sessions/{session_id}/messages.jsonl`
- 启动时从磁盘恢复消息列表
- 这是天枢最昂贵的教训——不要等到 Phase 5

### 3.2 CVM 开销自噬（架构级）

**天枢的教训**：CVM 注入 token（cognitive-mirror、uncertainty hints、sycophancy traps）
本身消耗上下文窗口——用了窗口的 5-8%。高压力下，CVM 注入更多内容 → 窗口更满 →
压力更高 → CVM 注入更多……形成正反馈循环。

天枢 v2 的解决方案：
- `PressureMonitor.recordCvmInjection(estimatedTokens)` 追踪 CVM 开销
- `shouldThrottleCvm` / `CVM_OVERHEAD_CEILING` 两级阈值
- `computePressure` 中 CVM overhead 权重 0.15——让 agent 感知到自监管成本

**伏羲现状**：`fuxi-cvm/src/ledger.rs` 的 `build_cognitive_prompt()` 无条件注入 mirror，
没有开销追踪。

**建议**：
- 在 `CognitiveLedger` 中增加 `cvm_token_estimate: usize`
- 在 `ContextManager` 中追踪 CVM 注入的累计 token
- 当 CVM 开销超过 5% 时降低 mirror 频率（每 2 轮一次）
- 当超过 8% 时 hard-stop 所有非必要注入

### 3.3 Season 系统需要 doom loop 粒度

**天枢的设计**（`src/agent/cognitive-season.ts` + `src/agent/trace-store.ts`）：

```
DoomLoopLevel: 'none' | 'warn' | 'blocked'

warn = thermocline（温跃层）— 不是完全故障，但有退化迹象
blocked = 完全陷入循环
```

`warn` 使 season 系统有**温跃层感知**——在 agent 完全卡死之前就能介入。

**伏羲现状**（`fuxi-cvm/src/season.rs`）：

```rust
pub struct SeasonInput {
    pub has_error: bool,  // 只有 bool，没有 warn/blocked 区分
    // ...
}
```

**建议**：引入 `DoomLevel` enum（`Healthy | Warn | Blocked`），
基于工具调用指纹检测（天枢的 `getDoomLoopLevel()` 使用双策略：连续重复 + 滑动窗口频率）。

### 3.4 预测系统缺失

**天枢的设计**：`PredictionAccumulator` 追踪每次工具调用的预测结果，
驱动 vigor 的 phasic/tonic 更新和 sensorium 的 momentum 维度。

没有预测系统，vigor 就失去了驱动力——
`update_vigor` 的 `toolSuccess` 参数需要实际的成功/失败信号。

**伏羲现状**：`fuxi-cvm/src/vigor.rs` 的 `VigorState` 有完整字段，
但 `update_vigor` 需要 `tool_success: bool` 输入——agent loop 中是否在传递这个信号？

**建议**：在 agent loop 的每次工具执行后调用 `update_vigor`，
传入执行结果。同时建立 prediction accumulator（简单版：最近 10 次的成功率）。

## 四、🟢 伏羲做得好的地方

### 4.1 八卦 Crate 分离

天枢的目录结构是演化出来的，边界模糊（`src/agent/` 里有 context 逻辑，
`src/context/` 里有 agent 类型）。伏羲的八卦 crate 从一开始就是**明确的领域边界**：

```
fuxi-qian (agent) ≠ fuxi-kan (context) ≠ fuxi-zhen (tools) ≠ fuxi-cvm (cognition)
```

每个 crate 有自己的类型、自己的测试、自己的 Cargo.toml。
这是天枢想做但没做到的。

### 4.2 Trait 驱动的工具系统

```rust
pub trait Tool: Send + Sync {
    fn definition(&self) -> ToolDefinition;
    fn execute(&self, params: ToolParams) -> BoxFuture<anyhow::Result<ToolResult>>;
    fn requires_approval(&self, _params: &ToolParams) -> bool { false }
    fn is_concurrency_safe(&self) -> bool { true }
}
```

比天枢的 `interface ToolDefinition + execute function` 模式更强：
- 编译期保证所有工具实现相同接口
- `requires_approval` 内置审批逻辑
- `is_concurrency_safe` 让并行工具调用成为可能

### 4.3 抛弃星图体系

天枢的 Star Phase / Star Domain / Star Soul / Star Phase Context 是演化中
长出来的过度抽象。伏羲正确地识别出这是演化债务而非核心价值。

### 4.4 代码内嵌测试

Rust 的 `#[cfg(test)] mod tests {}` 是标准实践，每个源文件自带测试。
天枢的测试虽然多（1860 个），但测试文件分散在 `__tests__/` 目录中，
经常与源文件脱节。

## 五、架构建议

### 5.1 增加 `fuxi-yu`（预测/免疫）

天枢有一个隐式的"免疫层"：
- `PredictionAccumulator`：追踪预测准确率
- `RepairHintTracker`：记录失败模式
- `ImmuneInnate`：先天免疫（工具限流、重复检测）
- `AntibodyProposal`：适应性免疫（从失败中学习）

建议在伏羲中显式化为 `fuxi-yu`（豫卦，预防）crate：

```
fuxi-yu/
├── prediction.rs    // 预测累加器
├── immune.rs        // 免疫系统（先天 + 适应）
├── repair.rs        // 修复提示追踪器
└── lib.rs
```

### 5.2 CVM 应该有自己的 token 预算

当前认知镜面无条件注入。从架构层面，CVM 应该有自己的 token 预算（如上下文窗口的 3%），
`CognitiveLedger` 应该在预算内决定注入什么——而不是注入一切能注入的。

```
CognitiveLedger:
  budget: 3% of context_window
  priority: mirror > verification_gap > uncertainty_hint > season_hint
```

### 5.3 ContextManager 需要 thrashing 检测

天枢的 `PressureMonitor` 有：
- `detectThrashing()`：最近 4 轮内 ≥3 次 compact → 抖动
- `fastGrowth`：连续两次检查之间 ratio 增长 ≥15%
- `suggestion: 'task_decomposition'`：抖动时给 agent 建议分解任务

伏羲的 `PressureMonitor` 目前只有简单的阈值检测。

### 5.4 工具注册表需要安全分类

天枢的工具分为：
- **READ_TOOLS**（免审批，可并发）：read_file, grep, glob, repo_map
- **WRITE_TOOLS**（需审批/边界检查）：write_file, edit_file, bash, apply_patch

伏羲的 `Tool trait` 有 `requires_approval()` 方法，但分类是工具自己的责任。
建议在 `ToolRegistry` 层面增加 `ToolCategory` 枚举和批量审批逻辑。

### 5.5 前缀缓存意识

天枢有完整的 prefix cache 管理（`src/cache/`）：
- 缓存命中率监控
- Ghost registry（缓存失效检测）
- FP calc（fingerprint 计算，检测 prompt 变更）

伏羲的 `fuxi-kan/src/cache/` 有初步的指纹和指标模块——这是对的。
但要警惕天枢的教训：prefix cache 在 1M 窗口下**命中率陡降**
（`docs/superpowers/analysis/2026-05-26-deepseek-prefix-cache-命中率下降根因分析.md`），
因为长窗口中 prompt 的任何微小变化都会导致 cache miss。

## 六、Phase 优先级建议

当前 FUXI-DESIGN.md 的 Phase 规划是合理的，但基于天枢的经验，建议调整优先级：

| 原 Phase | 建议 | 理由 |
|----------|------|------|
| Phase 1: 一画开天 | ✅ 保持 | 当前状态，先跑通 |
| Phase 2: 两仪生四象 | ⬆️ 加消息持久化 | 天枢最贵的教训 |
| Phase 3: 四象生八卦 | ⬆️ 加 Prediction/Immune | 没有预测系统，vigor 是空的 |
| Phase 4: 通神明之德 | ✅ 保持 | TUI 完善 |
| Phase 5: 通德类情 | ⬆️ 加 CVM 自监管 | 多模型路由前先防止 CVM 自噬 |
| Phase 6: 结绳为网 | ✅ 保持 | 团队协作可以后做 |

### 新增 Phase 建议

- **Phase 2.5: 豫卦·免疫** — PredictionAccumulator + RepairHint + 工具限流
- **Phase 5.5: 节卦·节制** — CVM token budget + overhead tracking + throttling

## 七、技术选型微建议

| 领域 | 当前选型 | 建议 |
|------|----------|------|
| Token 计数 | `tiktoken-rs` | ✅ 正确。但注意 DeepSeek 用的是自己的 tokenizer，tiktoken 会有偏差 |
| 消息持久化 | 无 | 推荐 SQLite（已有 `meridian.db`），比 JSONL 更适合并发读写 |
| 异步测试 | `#[tokio::test]` | ✅ 正确。但集成测试别放 crate 里——放 `tests/` 目录 |
| 配置 | TOML + serde | ✅ 正确。支持 `~/.config/fuxi/config.toml`（天枢用 `~/.rivet/`） |
| 错误处理 | anyhow + thiserror | ✅ 正确。但 agent loop 中的错误需要 `AgentOutput::Error` 而非 panic |

---

## 八、一句话总结

> 伏羲继承了天枢的精神——evidence-based reasoning、verify-first、认知镜面——
> 但用 Rust 的类型系统和八卦的模块化重新表达了它。当前最大的风险不是
> 功能缺失，而是**天枢踩过的三个坑正在伏羲中重演**：消息不持久化、
> CVM 不自监管、sensorium 维度假死。这三件事在 Phase 2 之前修复，
> 伏羲就能站在天枢的肩膀上，而不是重复天枢的老路。
