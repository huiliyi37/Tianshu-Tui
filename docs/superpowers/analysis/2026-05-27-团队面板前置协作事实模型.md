# 团队面板前置协作事实模型：业务碰撞记录

> 临时参考文档。不是正式方案，不作为最终设计约束。用于后续迭代团队面板、协作语义、Delivery Gate 与相关计划时回看。

## 背景

原本目标是推进团队面板，但最近连续在修 shared worktree、Delivery Gate、验证归因、stale RED、co-ownership 等问题。表面看像“修修补补”，但实际暴露出一个更基础的问题：团队面板不是单纯 UI，它需要展示一组可信的协作事实。

这些事实很抽象，难以在白板上预先完整设计出来。它们往往是在真实业务碰撞中产生：多个会话同时修改、外部 dirty 文件存在、旧验证失败残留、工具调用方式错误、交付门误报等。每一次碰撞都会把一个模糊边界压出形状，然后系统才有机会命名它、测试它、编码它。

因此，这段时间更像是团队面板的前置阶段：协作事实模型硬化期。

## 核心判断

这不是普通意义上的暴力测试，而是“真实业务碰撞驱动的语义压力测试”。

暴力测试通常是随机、穷举、构造极端输入；这里发生的是另一类测试：真实协作场景在压力下逼问系统是否真的理解任务、归属、验证、交付、责任边界。

抽象不是先验发明出来的，而是在真实失败中被逼出来、再被命名、再被编码成机制。

## 这次碰撞逼出的事实模型

### 1. 文件归属不是二元的

最初容易把文件分成 owned / external，但真实 shared worktree 中还会出现：

- current owned dirty files：当前任务仍然 dirty、需要交付判断的文件；
- historical owned files：当前任务曾修改过，但当前已经不 dirty 的文件；
- external dirty files：其他会话或基线已有的 dirty 文件；
- pre-existing untracked files：任务开始前就存在的未跟踪文件；
- co-owned files：外部文件被当前任务有意共同处理；
- unclassified dirty files：dirty 但未被归入 owned/external/co-owned 的文件。

这些分类不是 UI 装饰，而是交付安全边界。团队面板未来如果展示“谁在做什么”，必须能区分这些状态。

### 2. 验证失败也不是二元的

最初容易把验证分成 passed / failed。但真实执行里出现了更多语义：

- test failure：测试真实执行，并且有 failed tests；
- tool invocation failure：命令或 filter 用法错误，导致没有测试真正执行，例如 `0 passed, 0 failed, 0 skipped`；
- blocked verification：外部条件阻塞，不能简单归责给当前任务；
- full-suite unattributed failure：全量失败但无法证明属于当前 owned files；
- stale failure：旧失败已经被后续等价成功验证覆盖；
- superseded failure：账本中保留但不应继续阻塞交付的旧失败。

团队面板如果只显示红绿，会误导用户。它需要说明失败是什么类型，以及下一步最短路径是什么。

### 3. 验证身份不能只靠 command string

`run_tests src/a.test.ts src/b.test.ts` 与 `tsx --test src/a.test.ts src/b.test.ts` 在字符串层面不同，但语义上可能是同一组 targeted tests。

因此 verification identity 更接近：

- runner family；
- target test files 集合；
- scope：targeted / full；
- 结果类型：test failure / invocation failure / passed / blocked。

团队面板未来需要展示“这组验证覆盖了什么”，而不是只展示“执行了哪条命令”。

### 4. Delivery Gate 是团队面板的事实源之一

Delivery Gate 不是单纯 commit 前检查。它实际上已经在聚合团队面板需要的核心事实：

- 当前任务是否可交付；
- 当前阻塞是什么；
- 阻塞属于 owned、external、unattributed 还是 invocation；
- 有没有 stale failure；
- 有没有外部 dirty 文件；
- 当前最短恢复路径是什么。

团队面板 MVP 可以先消费 Delivery Gate 的结构化结果，而不是重复发明一套状态判断。

## 为什么最近的“修补”是合理的

团队面板要回答的问题包括：

1. 工作属于谁？
2. 哪些修改是当前任务的？
3. 哪些 dirty 文件不属于当前任务？
4. 当前验证是否可信？
5. 失败是谁的责任？
6. 旧失败还算不算当前阻塞？
7. 多会话是否互相干涉？
8. 当前最短恢复路径是什么？

最近修的 shared worktree ownership、co-ownership、verification attribution、stale RED、tool invocation failure，正好都是这些问题的底层事实模型。

所以这不是偏离团队面板，而是在让团队面板未来显示的内容有资格被相信。

## 风险：不能永远停留在碰撞驱动修补

真实业务碰撞会不断产生新抽象。如果没有收束机制，系统会一直修地基，迟迟不进入产品功能。

建议给“协作事实模型硬化期”设置切换条件。满足以下条件后，应进入团队面板 MVP：

1. Delivery Gate 能稳定回答当前任务是否可交付；
2. shared worktree 下 owned / external / co-owned / historical owned 不会误阻塞；
3. 验证失败能分清代码失败、工具调用失败、旧失败、外部阻塞；
4. 报告能给 agent 或用户下一步最短路径；
5. 这些状态已经有 targeted tests 固化。

目前看，已经接近这个切换点。剩余工作更多应服务于团队面板 MVP，而不是继续无限扩展 Delivery Gate 语义。

## 建议的团队面板 MVP 输入源

团队面板第一版可以先不设计复杂的新模型，而是整合已有事实源：

- TaskLedger：任务事件、文件读写、验证事件；
- OwnershipLedger：owned / external / co-owned；
- DeliveryGateV2：GREEN / YELLOW / RED、blocking reason、diagnostics；
- VerificationAttribution：验证结果归因；
- git dirty snapshot：当前真实工作区状态；
- worker/session metadata：后续团队协作视图需要的会话来源。

MVP 展示可以围绕四块：

1. Work ownership：当前任务拥有、共同拥有、外部、未分类文件；
2. Verification health：通过、失败、调用失败、stale、被覆盖；
3. Delivery readiness：GREEN/YELLOW/RED 与阻塞原因；
4. Next action：最短恢复路径。
