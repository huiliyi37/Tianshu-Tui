# 工作流迭代：计划与设计文档的对齐审查

> 日期：2026-05-19
> 触发事件：Phase 1 计划遗漏了设计文档要求的 claim 接入 coordinator 环节
> 目的：建立"计划执行前必须与设计文档交叉验证"的检查机制

---

## 事件回顾

### 发生了什么

设计文档 `2026-05-19-multi-session-orchestration-design.md` 明确要求：

> Phase 1 成功标准：
> - 实现 `ClaimRegistry` 类（acquire/release/check/reap_stale）
> - **现有 `DelegationCoordinator` 的 hands worker 使用 claim 检查**
> - 允许多 Rivet 实例同时运行

但 Phase 1 计划文档的任务列表是：

| 任务 | 内容 | 是否覆盖设计要求 |
|------|------|-----------------|
| Task 1 | 安装 better-sqlite3 | ✅ 基础设施 |
| Task 2 | SessionRegistry 核心（注册+心跳+崩溃检测） | ✅ 会话管理 |
| Task 3 | ClaimRegistry（claim API） | ⚠️ 只建了表和 API |
| Task 4 | main.tsx 替换 LWTGuard | ✅ 入口接入 |
| Task 5 | 集成验证 | ❌ 只验证 typecheck+tests |

**遗漏：没有任务将 claim 检查接入 `DelegationCoordinator.delegateOrder()` 的 hands worker 路径。**

Claim 只建了表和 API（`acquireClaim` / `releaseClaim` / `checkClaim`），但没有在实际的工具执行链路中被调用。等于造了锁但没人用。

### 执行过程中的信号

回溯执行过程，有几个时刻本可以发现这个遗漏：

1. **读设计文档时**：我读到了"现有 DelegationCoordinator 的 hands worker 使用 claim 检查"这句话，但没有将它映射为一个具体的实现任务。

2. **执行 Task 3 时**：我实现了 `SessionRegistry` 类（包含 claim 方法），测试通过。但没有问自己："这些方法在哪里被调用？"

3. **执行 Task 5（集成验证）时**：我只检查了 `npx tsc --noEmit` 和测试全过。没有回对照设计文档的成功标准逐条验证。

4. **用户说"继续"时**：我进入了"执行下一个任务"的惯性模式，而不是"还有什么没做完"的审查模式。

### 为什么发生

| 层面 | 原因 |
|------|------|
| 计划层 | Worker 生成的计划文档没有覆盖设计文档的全部成功标准 |
| 执行层 | 我把计划文档当作唯一权威，没有回对照设计文档 |
| 验证层 | 集成验证只做了技术验证（typecheck + tests），没有做需求验证（设计文档成功标准） |

---

## 根因分析

**核心问题：计划文档和设计文档之间没有强制对齐机制。**

当前流程：
```
设计文档 → Worker 生成计划文档 → 执行者按计划逐任务实现 → 技术验证
```

问题：Worker 生成计划文档时，可能遗漏设计文档的要求。执行者信任计划文档，不会回查设计文档。技术验证只检查代码能不能跑，不检查需求有没有被满足。

应该的流程：
```
设计文档 → Worker 生成计划文档 → 【交叉验证：每条设计要求是否被计划覆盖】→ 执行 → 【需求验证：每条设计要求是否被实现】
```

---

## 改进方案

### 1. 计划文档必须包含"设计要求覆盖矩阵"

每个计划文档末尾必须有一个表格，逐条映射设计文档的成功标准：

```markdown
## 设计要求覆盖矩阵

| 设计文档要求 | 对应计划任务 | 状态 |
|-------------|-------------|------|
| ClaimRegistry 类 | Task 3 | ✅ |
| hands worker 使用 claim 检查 | Task 6 (新增) | ✅ |
| 多实例共存 | Task 4 | ✅ |
```

如果某个设计要求没有对应的计划任务，**必须新增任务或明确标注为"Phase N 后续"**。

### 2. 执行者的"设计文档回查"检查点

在以下时刻，执行者必须回查设计文档：

- **开始执行前**：读完计划文档后，读设计文档的成功标准，确认计划覆盖了所有要求
- **每个任务完成后**：问自己"这个任务满足了设计文档的哪条要求？"
- **集成验证时**：不只做 typecheck + tests，还要逐条验证设计文档的成功标准

### 3. 集成验证必须包含"需求验证"

当前的集成验证：
```bash
npx tsc --noEmit          # 技术验证
npx tsx --test ...        # 测试验证
```

改进后的集成验证：
```bash
npx tsc --noEmit          # 技术验证
npx tsx --test ...        # 测试验证
# 需求验证：逐条检查设计文档成功标准
# 1. ClaimRegistry 类存在且有测试 → ✅
# 2. hands worker 调用 claim 检查 → 需要验证
# 3. 多实例可以同时启动 → 需要验证
```
