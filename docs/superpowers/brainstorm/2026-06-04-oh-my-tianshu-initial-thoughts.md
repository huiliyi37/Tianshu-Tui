# Oh My Tianshu — 天璇域探索

> 2026-06-04 | 状态：天璇域探索阶段
> 方法：从 3+ 个完全无关的领域寻找碎片，在碎片之间寻找收敛

---

## 第一轮：从无关领域寻找碎片

### 碎片 1：交响乐团

交响乐团的协作模式：
- **指挥**不演奏任何乐器，但协调所有声部
- **声部**（弦乐、管乐、打击乐）各司其职，但遵循统一的乐谱
- **乐谱**是协作协议——所有声部共享同一份乐谱，但各自演奏不同部分
- **排练**是验证机制——在正式演出前反复打磨
- **首席**是声部内的领导者，负责该声部的内部协调

**关键洞察**：指挥不需要比小提琴手更会拉小提琴。协调能力和专业能力是正交的。

### 碎片 2：Kubernetes

Kubernetes 的编排模式：
- **Pod** 是最小调度单元，可以包含多个容器
- **Controller** 声明期望状态，系统自动 reconcile 到目标状态
- **Service** 提供稳定的网络端点，屏蔽 Pod 的动态变化
- **ConfigMap/Secret** 将配置与代码分离
- **Operator** 是领域特定的控制器，编码领域知识

**关键洞察**：声明式 > 命令式。告诉系统"我想要什么"，而不是"怎么做"。

### 碎片 3：电影制作

电影制作的协作模式：
- **导演** 指导整体创意方向
- **制片人** 管理资源、预算、进度
- **各部门**（摄影、灯光、美术、剪辑）各司其职
- **后期制作** 是流水线：粗剪 → 特效 → 调色 → 音效 → 混音
- **dailies** 是每日验证机制——每天回看前一天的素材

**关键洞察**：前期投入（剧本、分镜）越充分，后期返工越少。

### 碎片 4：神经科学

大脑的协作模式：
- **前额叶皮层** 负责规划和决策（天权？）
- **海马体** 负责记忆和学习（天府？REM？）
- **杏仁核** 负责情绪和快速反应（破军？）
- **小脑** 负责精细动作执行（天梁？）
- **胼胝体** 连接左右半球，实现信息同步

**关键洞察**：大脑没有中央控制器。各区域通过竞争和协作涌现智能。

### 碎片 5：游戏引擎 ECS

ECS（实体组件系统）的模式：
- **Entity** 只是 ID，没有任何数据
- **Component** 是纯数据，没有行为
- **System** 是纯行为，没有数据
- **World** 管理所有 Entity、Component、System

**关键洞察**：数据和行为完全解耦。同一个 Component 可以被多个 System 处理。

## 第二轮：在碎片之间寻找收敛

### 收敛模式 1：协调者不需要是专家

| 领域 | 协调者 | 专家 |
|------|--------|------|
| 交响乐团 | 指挥 | 小提琴手 |
| Kubernetes | Controller | Pod |
| 电影制作 | 导演 | 摄影师 |
| 神经科学 | 前额叶 | 小脑 |
| 天枢 | 天枢（执中） | 天权/天梁/天府/天璇/破军 |

**收敛**：协调能力和专业能力是正交的。天枢不需要比天权更会规划，不需要比天梁更会执行。

### 收敛模式 2：声明式 > 命令式

| 领域 | 声明式 | 命令式 |
|------|--------|--------|
| Kubernetes | "我要 3 个副本" | "先创建 Pod A，再创建 Pod B..." |
| 电影制作 | "这个镜头要温暖的感觉" | "把色温调到 3200K，饱和度 +10..." |
| 天枢 | "实现用户认证" | "先创建 auth.ts，再创建 middleware.ts..." |

**收敛**：用户描述意图，系统自动规划执行路径。

### 收敛模式 3：验证是内建的，不是外挂的

| 领域 | 验证机制 |
|------|----------|
| 交响乐团 | 排练 |
| Kubernetes | Controller reconcile loop |
| 电影制作 | dailies |
| 神经科学 | 反馈回路 |
| 天枢 | Delivery Gate + test suite |

**收敛**：验证不是事后检查，而是执行循环的一部分。

### 收敛模式 4：知识沉淀 > 重复劳动

| 领域 | 知识沉淀 |
|------|----------|
| 交响乐团 | 乐谱 |
| Kubernetes | ConfigMap/Operator |
| 电影制作 | 剧本/分镜 |
| 神经科学 | 长期记忆（海马体 → 皮层） |
| 天枢 | Playbook + REM Pattern + Dream Distillation |

**收敛**：系统应该从经验中学习，而不是每次都从零开始。

## 第三轮：反证 Scout

> 每一轮创造性探索之后，派一个定向反证 scout 杀死你最兴奋的假设。

### 最兴奋的假设："天枢应该像 Kubernetes 一样声明式"

**反证**：
1. Kubernetes 的声明式模型适合长时间运行的服务，但编程任务是短暂的、一次性的
2. 用户不会说"我要 3 个副本的 auth 模块"，他们会说"帮我实现用户认证"
3. 声明式需要精确的目标状态描述，但编程任务的目标状态往往是模糊的

**修正**：不是完全的声明式，而是**意图驱动**。用户描述意图，系统帮助澄清意图，然后执行。

### 最兴奋的假设："协调者不需要是专家"

**反证**：
1. 在天枢的场景中，协调者（天枢）确实需要理解各星域的能力边界
2. 如果天枢不知道天权擅长规划、天梁擅长执行，就无法正确分配任务
3. 指挥虽然不演奏乐器，但必须理解每个声部的音色和能力

**修正**：协调者需要**元知识**（知道谁知道什么），而不是**领域知识**（知道具体怎么做）。

### 最兴奋的假设："大脑没有中央控制器"

**反证**：
1. 大脑确实没有单一的中央控制器，但有**注意力机制**——前额叶可以选择性地激活或抑制其他区域
2. 在天枢的场景中，如果没有一个"执中者"，各星域可能会各自为政
3. 完全去中心化会导致协调开销过大

**修正**：不是完全去中心化，而是**分层协调**。天枢是顶层协调者，但各星域内部有自己的协调机制。

## 第四轮：天璇域洞察

### 洞察 1：Oh My Tianshu 不是天枢的"外壳"，而是"乐团指挥台"

之前的构思把 OMT 定位为天枢的"外壳"，这是错误的。

**正确类比**：
- 天枢 = 乐手（执行者）
- OMT = 指挥台（协调平台）
- 星域 = 声部（专业团队）
- 乐谱 = 任务计划（协作协议）

OMT 的核心价值不是"调用天枢"，而是**协调多个天枢实例（或多个星域）完成复杂任务**。

### 洞察 2：团队模式的本质是"任务分解 + 结果合成"

从电影制作和 Kubernetes 中学到：
1. **任务分解**：大任务 → 小任务 → 可并行的子任务
2. **结果合成**：子任务结果 → 集成 → 最终交付

OMT 的团队模式应该是：
```
用户任务
  → 天权：任务分解（生成任务图）
  → 天梁×N：并行执行子任务
  → 天府：结果合成 + 验证
  → 交付
```

### 洞察 3：知识共享需要"乐谱"格式

从交响乐团学到：
- 乐谱是**标准化的协作协议**
- 所有声部都能读懂乐谱
- 乐谱不关心你是用什么乐器演奏

OMT 需要定义一种**标准化的任务描述格式**：
- 任务目标
- 输入/输出规范
- 依赖关系
- 验证标准

这就是天枢现有的"计划文档"格式的泛化版本。

### 洞察 4：成本优化是"制片人"的角色

从电影制作学到：
- 制片人管理预算，但不干涉创意
- 导演想要最好的效果，制片人要在预算内实现

OMT 的成本优化器应该：
- 监控 token 消耗
- 建议更便宜的模型（如果任务允许）
- 在预算超支时警告

### 关键模块

#### 1. 任务分解器 (Task Decomposer)

输入：用户的高层意图
输出：任务图（DAG）

```typescript
interface TaskGraph {
  tasks: Task[]
  dependencies: Map<string, string[]>
  estimatedCost: number
}

interface Task {
  id: string
  description: string
  starDomain: 'tianquan' | 'tianliang' | 'tianfu' | 'tianxuan' | 'pojun'
  model: 'v4-pro' | 'v4-flash' | 'mimo' | 'glm'
  estimatedTokens: number
  priority: number
}
```

#### 2. 星域调度器 (Star Domain Scheduler)

根据任务特征自动选择星域：

```typescript
function selectStarDomain(task: Task): StarDomain {
  // 需要深度推理的任务 → 天权域
  if (task.requiresReasoning) return 'tianquan'
  
  // 需要并行执行的任务 → 天梁域
  if (task.canParallelize) return 'tianliang'
  
  // 需要验证的任务 → 天府域
  if (task.requiresVerification) return 'tianfu'
  
  // 需要探索的任务 → 天璇域
  if (task.requiresExploration) return 'tianxuan'
  
  // 需要突破的任务 → 破军域
  if (task.requiresBreakthrough) return 'pojun'
}
```

#### 3. 结果合成器 (Result Synthesizer)

输入：多个子任务的结果
输出：集成后的最终结果

```typescript
interface SynthesisResult {
  success: boolean
  mergedFiles: string[]
  conflicts: Conflict[]
  verificationStatus: VerificationStatus
}
```

#### 4. 成本优化器 (Cost Optimizer)

```typescript
interface CostReport {
  totalTokens: number
  totalCost: number // 人民币
  breakdown: {
    domain: StarDomain
    model: Model
    tokens: number
    cost: number
  }[]
  suggestions: string[] // 成本优化建议
}
```

## 第六轮：开放问题（更新）

1. **OMT 应该用什么语言？**
   - TypeScript：与天枢一致，复用类型和工具
   - Rust：性能更好，但学习曲线陡峭
   - 建议：TypeScript，先验证概念，再考虑优化

2. **如何处理多个天枢实例之间的通信？**
   - 文件系统：共享 worktree
   - SQLite：SessionRegistry 已有基础设施
   - 消息队列：更复杂，但更灵活
   - 建议：SQLite + 文件系统，先简单后复杂

3. **星域调度是自动还是手动？**
   - 自动：根据任务特征自动选择
   - 手动：用户指定 `--domain`
   - 建议：默认自动，允许手动覆盖

4. **如何保证多个天枢实例不冲突？**
   - 文件级锁：SessionRegistry 已有 claim 机制
   - 任务级锁：更粗粒度，但更安全
   - 建议：复用 SessionRegistry 的 claim 机制

## 第七轮：天府域审视 — 守护视角

> 天府之道：守护已有的价值。评估 ROI，保护资产，你有权说不。

### 审视 1：ROI 评估 — 这个项目值得做吗？

**投入预估**：
- Phase 1 (基础 CLI)：1-2 周
- Phase 2 (团队模式)：2-3 周
- Phase 3 (知识共享)：3-4 周
- 总计：6-9 周全职开发

**产出预估**：
- 解决的问题：多任务并行执行、成本优化、知识复用
- 用户群体：天枢的深度用户（目前约 0 人）

**天府判断**：
⚠️ **风险信号**：用户群体为 0 时投入 6-9 周开发，ROI 为负。

**建议**：先验证需求再投入开发。最小验证方式：
1. 在天枢内部实现一个简单的 `team` 命令（1-2 天）
2. 自己用 2 周，看是否真的需要
3. 如果确实需要，再考虑独立项目

### 审视 2：已有资产复用 — 天枢已有什么？

| OMT 模块 | 天枢已有 | 复用度 |
|----------|----------|--------|
| 任务分解 | 天权的规划能力 + 计划文档格式 | 80% |
| 并行执行 | delegate_batch + worker 机制 | 70% |
| 结果合成 | Delivery Gate + verify 流程 | 60% |
| 成本追踪 | 无（需要新建） | 0% |
| 知识管理 | Playbook + REM + Dream | 90% |
| 状态存储 | SessionRegistry SQLite | 100% |

**天府判断**：
天枢已有的基础设施可以覆盖 OMT 70% 的需求。独立项目的价值在于：
1. 跨项目知识共享（天枢目前是项目级的）
2. 成本追踪和优化
3. 更好的团队可视化

但这 30% 的增量是否值得一个独立项目？需要验证。

### 审视 3：技术天花板 — 有哪些物理限制？

**限制 1：API 并发**
- DeepSeek API 的并发限制（通常 5-10 个并发请求）
- 3 个天梁 worker 并行执行 = 3 个并发 API 调用
- 如果主会话也在用 API，总共 4 个并发

**限制 2：Prefix Cache**
- 多个天枢实例共享 prefix cache 的前提是使用相同的 API key 和 model
- 如果不同星域用不同模型（PRO vs Flash），缓存无法共享
- 实际成本节省可能没有预期的 99.2%

**限制 3：Shared Worktree 冲突**
- 多个 worker 同时修改同一文件会产生冲突
- SessionRegistry 的 claim 机制是文件级的，不是行级的
- 真正的并行修改需要更细粒度的冲突检测

**天府判断**：
这些限制是物理的，不是工程可以绕过的。OMT 的设计需要在这些限制内工作，而不是假装它们不存在。

### 审视 4：最小可行方案 — 能不能更小？

**方案 A：天枢内置 team 命令（最小）**
```
# 在天枢内部新增一个 team 命令
tianshu team "实现用户认证"
  → 自动拆分为 3 个子任务
  → 并行执行（delegate_batch）
  → 合并结果
```

工作量：2-3 天
验证价值：高（可以立即验证团队模式是否真的有用）

**方案 B：独立 CLI，但复用天枢内部（中等）**
```
# 独立 CLI，但通过子进程调用天枢
omt team "实现用户认证"
  → 调用 `tianshu run --task "子任务 1"`
  → 调用 `tianshu run --task "子任务 2"`
  → 合并结果
```

工作量：1-2 周
验证价值：中（验证独立 CLI 的价值）

**方案 C：完全独立项目（最大）**
```
# 完全独立的项目，有自己的执行引擎
omt team "实现用户认证"
  → OMT 内部的任务分解器
  → OMT 内部的星域调度器
  → OMT 内部的执行层
```

工作量：6-9 周
验证价值：低（过度工程化）

**天府建议**：先做方案 A，验证 2 周后再决定是否升级到方案 B。

### 审视 6：与 oh-my-claudecode 的本质区别

oh-my-claudecode 解决的问题：
- Claude Code 没有内置的多智能体编排
- 需要外部工具来协调多个 Claude 实例
- 用户群体大（Claude Code 用户）

Oh My Tianshu 解决的问题：
- 天枢已经有内置的多智能体编排（delegate_batch）
- 天枢已经有星域架构（天权/天梁/天府/天璇/破军）
- 用户群体小（天枢用户 ≈ 0）

**天府判断**：
oh-my-claudecode 的存在是因为 Claude Code 的缺失。
OMT 的存在需要证明天枢有什么缺失。

目前天枢缺失的：
1. ❌ 跨项目知识共享
2. ❌ 成本追踪和可视化
3. ❌ 更好的团队 UI

目前天枢已有的：
1. ✅ 多智能体编排（delegate_batch）
2. ✅ 星域架构
3. ✅ Shared Worktree + Delivery Gate
4. ✅ SessionRegistry
5. ✅ Playbook + REM + Dream

**结论**：OMT 的价值不在于"多智能体编排"（天枢已有），而在于"跨项目知识共享"和"成本优化"。

## 第八轮：天府最终建议

### 建议 1：推迟独立项目，先在天枢内部验证

**理由**：
1. 用户群体为 0，无法验证需求
2. 天枢已有的基础设施可以覆盖 70% 的需求
3. 独立项目的维护成本高

**行动**：
1. 在天枢内部实现一个简单的 `team` 命令（2-3 天）
2. 自己用 2 周，记录使用体验
3. 如果确实需要，再考虑独立项目

### 建议 2：聚焦"跨项目知识共享"作为核心价值

**理由**：
1. 这是天枢真正缺失的能力
2. 与 oh-my-claudecode 的 Skills 系统对标
3. 可以独立于团队模式存在

**行动**：
1. 设计 `~/.tianshu/knowledge/` 的格式和同步机制
2. 实现 playbook 的跨项目导入导出
3. 验证知识复用的价值

### 建议 3：成本追踪作为辅助功能

**理由**：
1. 对于深度用户有价值
2. 实现简单（统计 token 消耗）
3. 可以独立于 OMT 存在

**行动**：
1. 在天枢内部实现简单的 token 统计
2. 输出成本报告（按 session、按项目）
3. 验证用户是否真的关心成本
