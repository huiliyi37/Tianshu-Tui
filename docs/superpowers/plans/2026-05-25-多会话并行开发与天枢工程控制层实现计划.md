### 任务 2：创建多会话并行开发背景说明

**目标：** 用背景文档记录生产力现实：单会话等待两小时再下发任务是浪费，多会话并行不是可选花活，而是当前 AI 开发生产力的基本形态。

- 修改：无
- 测试：无

**步骤：**

- [ ] 创建 `docs/superpowers/specs/2026-05-25-多会话并行开发背景说明.md`，完整写入以下结构与要点：

  ```markdown
  # 多会话并行开发背景说明

  ## 1. 摘要

  天枢面对的生产力现实不是单会话顺序执行，而是人类同时调度多个 AI 会话并行推进真实工程。长程任务中，一个主控模型即便能协助子代理，也可能运行一到两个小时；开发者不可能等待该任务完全结束后才开始下一个任务。

  ## 2. 现实背景

  - 单会话长程任务可能持续一到两个小时。
  - 开发者等待长任务结束再下发下一任务，会造成严重生产力浪费。
  - Claude Code、天枢或其他 agent 都会被用于多会话并行工作流。
  - 人类已经在承担任务拆分、冲突判断、审查和合并节奏控制。

  ## 3. 当前人工调度模式

  过去主要由开发者与 Claude Opus 一起审查、拆任务、分配会话和发现风险。这个模式有效，但依赖 Opus 持续在线；当 Opus 不常久在线时，调度、审查、归因、交付边界需要被沉淀到天枢自己的工程控制层中。

  ## 4. 单会话假设为什么不成立

  - 单会话无法覆盖多个独立任务的等待时间。
  - 单会话容易把当前上下文内的失败误认为全局必须修复的问题。
  - 单会话主控并不等于高吞吐；它可能形成新的排队瓶颈。
  - 真实工程中的未提交改动可能属于其他会话，不是异常状态。

  ## 5. 多会话并行的必要性

  多会话并行不是为了让 AI 自主接管项目，而是为了让人类在安全边界内放大自己的调度能力。人类负责决定哪些任务可以并行、哪些文件不能碰、哪些风险需要审查；agent 必须服从边界，而不是要求人类迁就 agent 的串行工作方式。

  ## 6. 对天枢的要求

  天枢需要逐步承担工程控制层职责：记录任务归属、识别外部改动、归因验证失败、拦截越权还原和删除、暴露 agent 认知风险，并在交付时给出可审查证据。
  ```

  ```markdown
  # 天枢工程控制层设计

  ## 1. 定位

  天枢不是单纯用于指挥 AI 干活的 TUI。TUI 是驾驶舱，天枢更核心的价值是工程控制层：把人类意图、工程现场、AI 行为、验证反馈、任务归属和长期记忆组织在一起。

  ## 2. 设计原则

  - 人类负责调度，AI 不抢主控权。
  - 未提交改动默认可能属于其他会话，HEAD 不是共享工作区的唯一真相。
  - agent 只能在任务边界内行动，跨边界必须询问。
  - 验证失败必须归因，不允许为了通过测试乱修无关文件。
  - 用户说“还原”时，只能还原本会话明确引入的改动。
  - 删除 untracked 文件前必须得到明确确认。

  ## 3. 能力分层

  ### 3.1 工程现场感知

  识别 git 状态、已有 diff、untracked 文件、任务边界、相关设计文档和测试历史。

  ### 3.2 任务归属与交付账本

  记录本会话拥有的文件、外部文件、验证结果、交付状态和 commit scope。

  ### 3.3 验证归因

  区分本任务失败、历史失败、外部会话失败、环境失败和命令使用错误。

  ### 3.4 越权操作拦截

  在 write_file、edit_file、rm、git checkout、git reset、stash、commit 等操作前检查 ownership 与用户授权。

  ### 3.5 认知状态投射

  将 confidence、complexity、pressure、freshness、stability、当前 phase、风险信号和下一步动作暴露给人类。

  ### 3.6 长期协作记忆

  把事故、历史失败、项目规则、常见命令、设计约束和交接记录沉淀为可检索知识。

  ## 4. 当前过渡形态

  在天枢能力未完全建成前，开发者仍需要人工调度多会话，并可能借助 Claude Opus 做审查和任务拆分。但 Opus 不会一直在线，所以天枢必须逐步把这些审查规则和交付边界固化为 runtime 约束。

  ## 5. 非目标

  - 不让 AI 取代人类技术负责人。
  - 不要求开发者为了 agent 安全性改成串行开发。
  - 不把多会话并行视为异常。
  - 不把所有 dirty worktree 状态视为需要清理的问题。

  ## 6. 最小闭环

  天枢的最小工程控制闭环是：任务边界 → 文件归属 → 操作授权 → 验证归因 → 交付账本 → 事故沉淀。任何一步缺失，agent 都可能把生产力放大变成破坏力放大。
  ```
