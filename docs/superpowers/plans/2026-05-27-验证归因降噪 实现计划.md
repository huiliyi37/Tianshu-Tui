# 验证归因降噪 实现计划

> **面向 AI 代理：** 使用 subagent-driven-development（推荐）或 executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]` / `- [x]`）语法来跟踪进度。

**目标：** 让 Delivery Gate 正确识别验证调用错误与等价验证覆盖关系，避免旧 `run_tests` 误用记录造成 stale RED。

**架构：** 在 `TaskLedgerEvent.meta` 中保留结构化验证结果，在 `verification-attribution.ts` 中生成语义化 verification identity，并把 `exit=1 且 0 passed/0 failed/0 skipped` 归类为验证调用错误。DeliveryGateV2 继续作为唯一交付门聚合入口，只扩展诊断字段；`deliver_task` 只负责展示诊断、阻塞原因和最短重跑命令，避免把展示逻辑反推到归因层。

**技术栈：** TypeScript strict、node:test、node:assert/strict、现有 TaskLedger / OwnershipLedger / DeliveryGateV2 / ToolPipeline。

**执行状态：** 已闭环。Task 1-7 均已完成；集成验证通过；额外补充了 `npx tsx --test` 等价命令与“无法抽取 test file 时回退 normalized command”的 supersession 边界测试。

## 1. Scope check

本功能只跨一个强耦合子系统：B1 ownership / verification delivery gate。涉及模块均服务于同一交付门闭环，不拆分为多个独立计划。

纳入范围：

- 结构化记录 `run_tests` 生成的 verification metadata。
- 用语义化 verification identity 识别 `run_tests <files>` 与 `tsx --test <files>` 的等价性。
- 把 `exit=1` 且 `0 passed, 0 failed, 0 skipped` 归类为 `tool_invocation_failure`，不再显示为 owned test failure。
- 在 Delivery Gate / deliver_task 报告中区分 current blocking failure、stale failure candidate、tool invocation failure candidate，并给出最短恢复命令。

不纳入范围：

- 不重写 `run_tests` 工具的命令构造器。
- 不改变 scoped commit 文件归属规则。
- 不引入真实测试失败到具体 owned file 的堆栈归因；当前仍以 targeted/full scope 作为归因代理。
- 不修改 TUI 渲染层。

## 3. Research endorsement（调研背书）

### 行为变更 A：`getEffectiveVerifications()` 从纯 command/scope key 改为语义化 verification identity

- 现有位置：`src/agent/verification-attribution.ts:41-100`。
- 调用者：
  - `src/agent/delivery-gate-v2.ts:95`：DeliveryGateV2 在归因前调用，决定哪些 verification 参与 gate。
  - `src/agent/__tests__/verification-supersession.test.ts:29-181`：直接覆盖 supersession 行为。
- 存在原因：当前实现需要“较晚同类成功验证覆盖较早失败验证”，但只按 normalized command 和 scope 匹配。
- 当前缺陷：`run_tests src/a.test.ts src/b.test.ts` 与 `./node_modules/.bin/tsx --test 'src/a.test.ts' 'src/b.test.ts'` command 字符串不同，实际验证目标相同却不能 supersede。
- 边界风险：
  - 过度归并不同测试命令会隐藏真实失败。
  - 文件路径顺序不同应当视为同一组测试。
  - 无法抽取 test file 的命令不能被宽松归并。
- 约束策略：
  - 只有抽取到至少一个 `*.test.ts` / `*.test.tsx` / `*.spec.ts` / `*.spec.tsx` 路径时，才使用 `runnerFamily + sortedTargetFiles + scope` 作为 key。
  - 无 test file 路径时保留现有 `normalizedCommand + scope` key。
  - full 与 targeted scope 继续分开，避免 targeted success 覆盖 full failure。

### 行为变更 B：`attribute()` 把 `exit=1 且 0/0/0` 从 owned failure 改为 tool invocation failure

- 现有位置：`src/agent/verification-attribution.ts:129-178`。
- 调用者：
  - `src/agent/delivery-gate-v2.ts:121` 通过 `getAggregateAttribution()` 间接调用。
  - `src/agent/__tests__/verification-attribution.test.ts:29-164` 直接测试。
- 存在原因：targeted verification failure 当前被视为 owned failure，因为 targeted test 通常对应当前任务修改文件。
- 当前缺陷：test runner/filter 用法错误也会形成 targeted failed，并被显示为 `Owned verification failed`。
- 边界风险：
  - 某些真实 import/runtime failure 也可能解析出 0 个测试。
  - 如果只看命令字符串，无法区分“没有测试被执行”和“测试执行失败”。
- 约束策略：
  - 归类条件必须同时满足：`status === 'failed'`、`exitCode !== 0`、`passed === 0`、`failed === 0`、`skipped === 0`。
  - 真正 `failed > 0` 的 targeted failure 继续保持 RED owned blocker。
  - 对 owned dirty files 存在且只发生 invocation failure 的场景，Delivery Gate 仍要求重跑验证；阻塞理由改为“验证调用失败”，不是“owned test failed”。

### 行为变更 C：`tool-pipeline` 记录 `run_tests` verification 时保留 parsed counts

- 现有位置：`src/agent/tool-pipeline.ts:664-667`。
- 调用者：
  - `TaskLedger.getVerifications()`：`src/agent/task-ledger.ts:102-104`。
  - `DeliveryGateV2.assess()`：`src/agent/delivery-gate-v2.ts:92-95`。
- 存在原因：ToolPipeline 是工具结果进入 B1 ledger 的唯一写入点。
- 当前缺陷：`run_tests` 工具已经返回 `VerificationMetadata`，但 ledger 只保存 `scope`，导致 `0 passed, 0 failed, 0 skipped` 信息在 DeliveryGate 前丢失。
- 边界风险：
  - 旧测试断言当前 meta 精确等于 `{ scope: 'targeted' }`。
  - 过多 meta 字段可能影响测试可读性。
- 约束策略：
  - 更新对应测试，断言关键字段存在而非仅精确等于单字段对象。
  - `command` 仍保留用户调用视角：`run_tests <filter>`；`resolvedCommand` 放入 meta，用于诊断和最短重跑命令。

### 行为变更 D：DeliveryGateV2 / deliver_task 报告增加诊断分层

- 现有位置：
  - `src/agent/delivery-gate-v2.ts:27-56` result/report 类型。
  - `src/agent/delivery-gate-v2.ts:90-230` assess/report 构造。
  - `src/agent/deliver-task.ts:106-164` 文本报告。
- 调用者：
  - `src/agent/deliver-task.ts:104` 调用 `ctx.gate.getReport([], currentDirtyFiles)`。
  - `src/agent/__tests__/delivery-gate-v2.test.ts` 与 `src/agent/__tests__/deliver-task.test.ts` 覆盖输出。
- 存在原因：DeliveryGateV2 是状态机，deliver_task 是用户可读交付报告。
- 当前缺陷：RED 文案只显示 `Owned verification failed`，没有区分 stale、invocation、current blocking。
- 边界风险：
  - 文案过长会增加噪音。
  - commit=true 仍必须以 gate state 为准，不能因文案降噪放松交付门。
- 约束策略：
  - DeliveryGateV2 只产生结构化字段；deliver_task 决定展示。
  - owned dirty files 为空时保留 GREEN，不展示阻塞图标。
  - commit=true 继续仅在 `report.state === 'RED'` 时拒绝。
