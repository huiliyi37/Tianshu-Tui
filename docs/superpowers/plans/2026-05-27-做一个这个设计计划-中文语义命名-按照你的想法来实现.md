# 计划闭环一键标注 实现计划

> **面向 AI 代理：** 使用 subagent-driven-development（推荐）或 executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 构建一个确定性的计划闭环能力，让用户可以用 `/plan close ...` 或 `plan_close` 工具预览并应用任务勾选、执行状态和闭环记录更新。

**架构：** 核心逻辑放在 `src/plan/plan-close.ts`，只负责解析 Markdown task block、生成变更预览和产出新内容；工具层 `src/tools/plan-close.ts` 负责路径校验、预览/应用写入和用户可读报告。Slash workflow 只把 `/plan close` 转成使用工具的代理提示，避免 TUI 直接写文件；应用写入后由 ToolPipeline 记录到 TaskLedger，确保 B1 归属门能识别计划文档变更。

**技术栈：** TypeScript strict、node:test、node:assert/strict、现有 ToolRegistry / ToolPipeline / slash workflow / B1 TaskLedger。

---

## 1. Scope check

本功能跨三个紧耦合层，但仍属于同一个“计划文档闭环”子系统，不拆成多个计划：

- Markdown 计划闭环核心：解析 `docs/superpowers/plans/*.md` 中的 `### Task N` block，只改指定 task 内 checkbox，并维护执行状态与 closure 段。
- 工具层：新增 `plan_close` 工具，支持默认 preview、`apply=true` 写入、路径限制、结构化报告。
- 入口层：新增 `/plan close` 与 `/plan-close` workflow 提示、帮助文案和命令面板入口。

不纳入本计划：

- 不做自然语言任意总结器；closure 文案由确定模板和用户传入字段组成。
- 不直接从 TUI slash handler 写文件；所有写入走工具和 approval 流程。
- 不自动读取最近所有验证历史并推断验证命令；第一版只接受显式 `verifiedCommands` 或工具参数中的简短验证记录。
- 不支持非 Markdown 计划文件。

## 3. Research endorsement（调研背书）

### 行为变更 A：`resolveEcosystemWorkflowInput()` 为 `/plan close` 增加子命令分流

- 现有位置：`src/workflows/ecosystem-workflows.ts:169-177`。
- 调用者：
  - `src/tui/slash-commands.ts:150-156` 的 `resolveAppPromptInput()` 先调用 `resolveEcosystemWorkflowInput()`。
  - `src/tui/app.tsx:672-675` 在 slash handler 未直接处理时调用 `resolveAppPromptInput()`。
  - `src/workflows/__tests__/ecosystem-workflows.test.ts:76-90` 覆盖 `/plan` / `/write-plan` prompt 行为。
  - `src/tui/__tests__/slash-commands.test.ts:73-97` 覆盖 TUI slash prompt 解析。
- 存在原因：`/plan` 与 `/write-plan` 是 writing-plans workflow 的入口，`resolveEcosystemWorkflowInput()` 将 slash 输入转换为普通用户提示，让 AgentLoop 执行计划编写流程。
- 修改理由：用户需要“一键闭环计划”，语义上属于 plan workflow；用 `/plan close` 作为子命令比新增完全独立的 TUI 写文件逻辑更小、更安全。
- 边界风险：
  - 现有 `/plan close something` 目前会被当成“为 close something 编写计划”。
  - 空 `/plan` 必须继续返回 `null`，由 slash handler 展示 usage。
  - `/write-plan close ...` 不应被劫持，保留给“为 close 相关功能写计划”的场景。
- 约束策略：
  - 只让 `/plan close ...` 和 `/plan-close ...` 进入闭环 workflow。
  - `/write-plan close ...` 继续走 writing-plans。
  - 解析失败时返回包含 usage 的 prompt，不直接写文件。

### 行为变更 B：`createDefaultToolRegistry()` 注册新写工具 `plan_close`

- 现有位置：`src/tools/default-registry.ts:1-38`。
- 调用者：
  - `src/main.tsx:150-155` 创建主 registry，并额外注册 delegate、undo、deliver 等运行期工具。
  - `src/main.tsx:808-812` goal loop 使用默认 registry。
  - `src/tools/__tests__/default-registry.test.ts:16-29` 断言核心工具存在且 `delegate_task` 不在 base worker registry。
  - 多个 AgentLoop 测试手动创建 `ToolRegistry`，不受默认注册影响。
- 存在原因：集中声明默认可用工具，保证 PromptEngine 注入工具定义和 ToolRegistry 执行入口一致。
- 修改理由：`plan_close` 是通用工程工具，应和 `edit_file`、`write_file` 一样由默认 registry 暴露给主 agent。
- 边界风险：
  - 默认 registry 同时作为 worker base registry；新增工具不能意外进入 worker allowlist。
  - 新写工具会增加工具列表，可能影响 prompt cache。
- 约束策略：
  - 只在 default registry 注册；`READ_ONLY_WORKER_TOOLS` 与 `WRITE_WORKER_TOOLS` 不加入 `plan_close`。
  - 工具本身 `requiresApproval()` 在 `apply=true` 时返回 true，preview 不需要 approval。

### 行为变更 C：`tool-pipeline` 将 `plan_close apply=true` 记录为 file_write

- 现有位置：`src/agent/tool-pipeline.ts:650-690`。
- 调用者：
  - 所有工具调用都经 ToolPipeline 执行并记录 TaskLedger。
  - `OwnershipLedger.autoOwnFromLedger()` 读取 `file_write` 事件归属 owned files。
  - `deliver_task` 通过 DeliveryGateV2 展示 owned/external 文件和交付状态。
- 存在原因：B1 归属星轨依赖 ToolPipeline 把工具行为转成 TaskLedger 事件，`write_file` 与 `edit_file` 已在这里记录写入。
- 修改理由：`plan_close` 可能直接写计划文件；如果不记录 `file_write`，交付门无法知道计划文档是当前任务 owned file。
- 边界风险：
  - preview 模式不能污染 ownership。
  - apply 失败不能记录写入。
  - 路径字段必须和工具 input 对齐。
- 约束策略：
  - 工具 input 使用 `file_path` 字段。
  - 仅当 `tu.name === 'plan_close' && tu.input.apply === true && !harnessResult.isError && filePath` 时记录 `file_write` 并 `registerOwned(filePath)`。

### 行为变更 D：`getPaletteCommands()` 与 `/help` 增加可发现入口

- 现有位置：
  - `src/tui/command-palette.tsx:90-130`。
  - `src/tui/slash-commands.ts:156-184`。
- 调用者：
  - `src/tui/app.tsx:1223-1234` 渲染命令面板并把选择结果交给 `handleSubmit()`。
  - `src/__tests__/command-palette.test.ts:33-39` 覆盖面板 entries。
  - `src/tui/__tests__/slash-commands.test.ts:102-130` 覆盖 `/help` 和 `/plan` usage。
- 存在原因：命令面板和 help 是用户发现 slash workflow 的主要入口。
- 修改理由：一键闭环功能如果只靠记忆命令，不符合“简单机制”的目标。
- 边界风险：
  - 命令面板条目只是输入预设，不应绕过 slash 安全守卫。
  - `/help` 文案不能暗示 TUI 直接写文件；实际写入仍走工具 approval。
- 约束策略：
  - 面板 entry 使用 `/plan-close`，选择后仍走 `handleSubmit()`。
  - help 文案明确 preview 默认行为和 `--apply` 需要工具 approval。
