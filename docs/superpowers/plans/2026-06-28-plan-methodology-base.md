# 计划方法论基础模板（Base）

> 参考并改编自 [obra/Superpowers writing-plans](https://github.com/obra/Superpowers/blob/main/skills/writing-plans/SKILL.md)。
> 定位：天枢任务计划的默认基础模板。所有计划都从这里出发；如果任务涉及多 enforcement gate 的安全/权限/沙箱变更，再在此基础上追加「安全附录」（安全不变量、触发路径清单、双门对齐数据流图）。
> 适用场景：任何需要结构化实现计划的功能、重构或修复；对执行工程师零上下文假设。
> 不适用场景：纯社交/闲聊、无需代码改动的诊断问答。

---

## 设计哲学

- **先计划，后写代码**。在没有把计划写清楚之前，不生成任何会改变工作区的工具调用。
- **任务小到能一口吃完**。每个任务应是一次独立可测的改动，2–5 分钟完成，附带明确的验证步骤。
- **零上下文假设**。计划读者是一个熟练但对本仓库、本工具链、本问题域几乎不了解的工程师，且测试设计能力一般。
- **DRY、YAGNI、TDD、频繁提交**。
- **禁止占位符**。任何 "TODO / TBD / 后续补充 / 添加适当错误处理" 都是计划缺陷。

---

## 工程纪律（非可选）

每个计划及其执行都必须满足以下四条纪律。它们不是装饰，是验收的一部分。

### 1. 一图胜千言

**每个计划至少包含一张 Mermaid 图。** 根据任务性质选择：

- 多组件/跨模块/有数据流 → 画**架构/模块依赖图**或**数据流图**
- 涉及状态转换 → 画**状态图**
- 涉及安全/权限/沙箱/多 enforcement gate → 画**双门对齐数据流图**（见安全附录）

图必须能在 Markdown 中直接渲染，禁止用占位符文字代替图形。

### 2. TDD：RED → GREEN → 重构

- 每个任务以**失败测试**开始（RED）
- 然后写**最小实现**让测试通过（GREEN）
- 验证通过后才允许重构
- 测试必须断言**行为**，而非内部 plumbing

### 3. 探针先行

动手写正式代码/复杂测试前，先用 **30 秒探针**验证核心假设或机制可行性：

- 写 3–5 行最小代码/命令验证你将要依赖的能力
- 探针失败 → 立刻换更简单的方法，不要继续堆代码
- 探针通过 → 再写完整实现/测试

临时探针（`console.log`、`assert`、`debugger`）在交付前必须清理；结构化的可观测探针可以保留。

### 4. 瑶光反证

**计划期（出计划的同时做复现，不留到执行期）**：

- **计划必须含「瑶光反证」章节**（plan submit 有门禁）：方案依赖的每条代码行为断言 + 计划期证据
- **设计定稿后回译验证**：设计阶段发明的断言（时序、块名、字段清单这类"我推过所以可信"的结论）在定稿后重新 read/grep 复现——调研阶段的旧读不算数，正是它被方案构思覆盖掉
- **bugfix 类先拿 RED**：plan mode 下 `run_tests` 可直接跑——复现原缺陷的失败输出进计划，绿非证明，复现即证
- **复现专员**：跑不了的断言派 `delegate_task profile=adversarial_verifier authority=yaoguang` 独立复现
- **复现不了的降级为"待验证假设"**：显式标注 + 执行期第一步如何验证，禁止写成结论

面对"已修复/测试通过/方案已落地"的声称，执行计划时必须：

- **绿非证明，复现即证**：用原缺陷输入或真实数据跑一遍，确认能复现原问题，再验证修复后通过
- **不取信提交信息，取 exit code**：独立跑 `tsc --noEmit`、独立跑相关测试、读实际 diff
- **方案 GREEN ≠ 落地 GREEN**：把 spec/方案的验收条件逐条核对到代码，不凭"看起来完成了"判断
- **fixture 必须复现真实输入形状**：测试数据要追踪到生产链路中产出它的那行代码，禁止手造真实系统从不产出的形状
- **反身自审**：对自己上一刻的结论也 fail-closed——有没有 ground truth 数据？有没有恒等式能自检？

## Scope Check

如果需求覆盖多个独立子系统，而前文没有把它们拆成多个子项目规格，建议先拆分为**每个子系统一个计划**。每个计划单独产出可工作、可测试的软件。

---

## 文件结构

在定义任务之前，先列出会创建或修改的文件，以及每个文件的职责。分解决策在这里锁定：

- 每个文件有清晰边界和单一职责。
- 优先小而聚焦的文件，而不是什么都做的大文件。
- 一起变更的文件应放在一起；按职责而非技术分层拆分。
- 在已有代码库中遵循既有模式；如果目标文件已经臃肿，可以在计划中包含拆分。

---

## 任务粒度

一个任务是**最小可独立测试交付单元**，值得一次新的 reviewer gate。划分边界时：

- 把搭建、配置、脚手架、文档步骤折叠进需要它们的那个任务。
- 只在 reviewer 可能拒绝 A 而批准 B 的地方拆分。
- 每个任务以**独立可测的交付物**结束。

**每步都是一次动作（2–5 分钟）**：

- "写失败测试"
- "运行确认它失败"
- "写最小实现"
- "运行确认测试通过"
- "提交"

## 计划文档头部

每个计划必须以这个头部开始：

```markdown
# [功能名称] 实现计划

> **面向 AI 执行代理：** 使用 `subagent-driven-development`（推荐）或 `executing-plans` 逐任务实现。步骤使用 checkbox（`- [ ]`）语法以便跟踪。

**目标：** [一句话描述这个计划构建什么]

**架构：** [2–3 句话描述方案、关键决策及理由]

**技术栈：** [关键技术/库]

## 全局约束

[把规格中的项目级要求逐条列出：版本下限、依赖限制、命名/文案规则、平台要求等，精确复制原文。每个任务的隐含要求都包含本章节。]

---
```

## 任务结构

```markdown
### Task N: [组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费： earlier tasks 产出的内容 —— 精确签名
- 产出： later tasks 依赖的内容 —— 精确函数名、参数、返回类型。执行者只看自己的任务，这里是他们了解邻居任务接口的方式。

- [ ] **Step 0: 探针验证（30 秒）**

如果该任务依赖新的机制、库行为或数据形状，先写一个 3–5 行的最小探针确认前提成立。

```python
# probe: 验证库/机制行为符合预期
print(some_new_api(sample_input))
```

运行：`python probe_task_n.py`
预期：输出与假设一致；若不一致，停止并换方案。

- [ ] **Step 1: 写失败测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 运行测试确认失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL with "function not defined"

- [ ] **Step 3: 写最小实现**

```python
def function(input):
    return expected
```

- [ ] **Step 4: 运行测试确认通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **Step 5: 瑶光反证——用真实输入形状复现**

从生产链路中取出真实输入（或构造能复现原缺陷的输入），运行一次确认：

- 修复前会失败（RED 复现）
- 修复后通过（GREEN 验证）

禁止用手造的、真实系统从不产出的 fixture 蒙混过关。

- [ ] **Step 6: 清理临时探针并提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
```

## 禁止占位符

任何一步都必须包含工程师实际需要的完整内容。以下写法视为**计划失败**，绝不允许出现：

- "TBD"、"TODO"、"待定"、"后续实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为上述代码编写测试"（没有给出具体测试代码）
- "与 Task N 类似"（执行者可能乱序阅读任务，重复代码）
- 只描述做什么、却不展示怎么做的步骤（代码步骤必须带代码块）
- 引用在任务中未定义的类型、函数、方法、属性

## 自检清单

计划写完后，用审视的眼光重新对照规格检查一遍。这是写计划的人自己运行的 checklist，不是派发子代理。

1. **规格覆盖**：逐段扫过规格/需求。能否指出每个需求由哪个任务实现？列出缺口。
2. **占位符扫描**：搜索计划中的红旗模式（见上）。修复它们。
3. **类型一致性**：后序任务中出现的函数/方法/属性名是否与前序任务定义的一致？Task 3 叫 `clearLayers()` 而 Task 7 叫 `clearFullLayers()` 就是 bug。
4. **一图检查**：计划中是否至少有一张 Mermaid 图？图是否反映了真实的组件/数据流/状态关系？
5. **TDD 检查**：每个任务是否都有 RED→GREEN 步骤？测试是否断言行为而非 plumbing？
6. **探针检查**：涉及新机制/假设的任务是否有 Step 0 探针？临时探针是否在交付阶段要求清理？
7. **瑶光反证检查**：计划是否含「瑶光反证」章节且关键断言带计划期证据（定稿后回读 / RED 输出 / 复现专员结论）？是否要求用真实输入形状复现原问题？是否把 spec 验收条件逐条核对到代码？测试 fixture 是否绑定了真实派生逻辑？设计阶段类比推理得出的机制是否已复现或降级为待验证假设？

发现问题时直接在内联修复，无需重走一遍 review。如果某条规格没有对应任务，补上任务。

## 执行交接

计划保存后，向用户提供两种执行选项：

> 计划已完成并保存到 `docs/superpowers/plans/YYYY-MM-DD-<slug>.md`。两种执行方式：
>
> 1. **子代理驱动（推荐）**——每个任务派一个全新子代理，任务间审查，快速迭代。
> 2. **内联执行**——在当前会话使用 `executing-plans` 批量执行，带人工检查点。
>
> 请选择？

- 若选子代理驱动：必须调用 `subagent-driven-development`。
- 若选内联执行：必须调用 `executing-plans`。

## 安全附录（可选，由路由决定）

如果任务涉及安全、权限、沙箱、多 enforcement gate，除了上述基础模板外，还必须在计划中追加：

- **安全不变量**：列出不可违反的约束，并标注由哪个测试验证。
- **触发路径清单**：枚举所有会触发授权扩宽/收窄的路径，标注自动（内联门）还是显式（工具调用）。
- **双门对齐数据流图**：用 Mermaid 画出授权状态的生产者、消费者、存储，标注 "write 蕴含 read" 等语义约束。

具体写法参考旧完整版模板：`docs/superpowers/plans/2026-06-14-plan-methodology-template.md` 的阶段五至阶段七。
