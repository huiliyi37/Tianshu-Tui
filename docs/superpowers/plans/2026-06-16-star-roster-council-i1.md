# I1 — 星域名册 + 议事会评审 · 业务流设计

> 本文档聚焦**用户视角的业务流**：用户打开桌面端后做什么、看到什么、系统如何响应。
> 技术实现方案（API 契约、组件树、数据流）在确认业务流后再细化。

## 0. 背景锚点

### 0.1 这个功能在 ROADMAP 里的位置

I1 是桌面端 ROADMAP 中「本轮不做」的后续迭代首项：

> 把 Antigravity 的匿名 dynamic subagents 升级为北斗八星人格：各带 decisionStyle / toolWhitelist / 方法论 suffix / glyph+accent。新会话/子代理自动匹配星域，Agent Manager 卡片显示星符；重大决策唤起「星图议事会」——多星对抗性评审。

当前 Antigravity 2.0 基座（M0–N5）已全部交付，L0/L1 打磨和 Cursor 3.0 渲染对齐也已完成。I1 是下一阶段的**核心差异化**——把后端已存在的星域人格系统，变成用户真正能感知、能交互、能依赖的功能。

### 0.2 已有什么（不需要重新设计）

**星域人格系统**（`src/agent/star-domain.ts`）已完整定义：

| 星域 | 决策风格 | 定位 | 星符 |
|------|---------|------|------|
| 天枢 | methodical | 全貌调度 · 统筹协调 | ✹ |
| 破军 | bold | 先锋探索 · 快速试错 | ✷ |
| 天府 | cautious | 守护稳固 · 风险感知 | ✦ |
| 天梁 | methodical | 精确执行 · 逐波交付 | ✧ |
| 天权 | cautious | 权衡审查 · 架构称量 | ✶ |
| 天机 | methodical | 前提质疑 · 盲点发现 | ✸ |
| 天璇 | bold | 跨域洞察 · 视角转换 | ★ |
| 辅 | methodical | 认知蒸馏 · 提示词调校 | ⊕ |
| 文曲 | methodical | 体验设计 · 视觉语汇 | ✺ |

每个星域有：`volatileBlock`（身份定义）、`systemPromptSuffix`（行为方法论）、`toolWhitelist`（权限边界）、`keywords`（自动匹配规则）、`uiPersona`（glyph + accent 色）。

**关键能力已落地**：
- `buildActiveDomain(taskDescription)` — 根据任务描述关键词自动匹配星域
- `DelegationRequest.authority` — 子代理可绑定星域，注入对应方法论
- `StarDomainRegistry` — 支持用户自定义星域（`.rivet/domains/<id>/card.md`）
- `onDecisionShift` — 星域切换事件已入 SSE 通道（session-manager.ts:949）

**议事会后端计划**（`.rivet/plans/星图议事会-多星域单轮会诊出计划.md`）已定义：
- 5 波次（W-C1~W-C5）：schema → 编排器 → 汇总渲染 → 多模型路由 → 工具注册
- 核心约束：只出计划不执行、单轮不循环、风险席不降级模型

### 0.3 缺什么

桌面端前端对星域系统**零感知**：
- `NewSessionDialog` 没有星域选择
- Agent Manager 卡片没有星符
- 没有地方浏览全部星域（名册）
- 议事会流程没有前端 UI
- `GET /stars` API 不存在

## 1. 用户故事全景

整个 I1 覆盖**三条用户路径**，按用户接触顺序排列：

```
路径 A：认识星域（名册）
  用户打开桌面端 → 浏览星域名册 → 了解每颗星的定位和能力

路径 B：日常使用（会话绑定星域）
  用户新建会话 → 选择星域（或自动匹配）→ agent 以该星域人格工作

路径 C：重大决策（议事会）
  用户面对复杂决策 → 发起议事会 → 多星域对抗评审 → 产出可审计计划
```

---

## 2. 路径 A — 星域名册

### 2.1 用户场景

用户第一次打开天枢桌面端，在左侧导航栏看到一个新的 tab：「星域」。点击进入后看到一个网格——九颗星的卡片，每张卡片上写着名字、格言、决策风格和一句话简介。用户点开天权的卡片，看到完整的自我描述："称量者与规划审查者。秤的本质不是拒绝，是让轻重可见…"

用户理解了每颗星的定位后，回到工作台开始工作。

### 2.2 业务流

```
用户点击 Rail「星域」tab
  → 系统从 GET /stars 获取全量星域列表
  → StarRosterSurface 渲染星域卡片网格
  → 每张卡片显示：glyph（accent 色大号星符）+ name + motto + decisionStyle badge + 一句话简介
  → 用户点击某张卡片
    → 展开详情：volatileBlock 全文 + keywords 标签 + toolWhitelist 工具列表
    → 如果用户自定义了星域（.rivet/domains/），也一并显示
```

### 2.3 关键体验点

- **第一印象**：名册是静态浏览，不需要任何操作就能理解北斗八星是什么
- **色彩体系**：每颗星的 accent 色不同（天权 warning 黄、天府 primary 蓝、破军 error 红…），卡片用对应色条区分
- **自定义星域可见**：用户放在 `.rivet/domains/` 下的自定义星域自动出现在名册中，与内置星域并列

---

## 3. 路径 B — 日常会话绑定星域

### 3.1 用户场景

用户新建一个会话时，在「新建线程」弹窗中看到一个星域选择器——默认选项是「自动匹配」。用户输入任务 "审查一下 loop.ts 的架构是否合理"，系统自动将星域匹配为「天权」（因为关键词 "审查" "架构" 命中天权的 keywords）。

会话开始后，Agent Manager 的会话卡片左侧出现天权的星符 ✶（warning 黄色），提醒用户这个会话当前由天权驱动。对话过程中，如果 agent 感知到任务性质变化（比如从审查转为重构），可能触发星域切换——消息流中出现一条「改道」提示："天权 → 天府：任务已从审查转向守护性重构"。

### 3.2 业务流

```
── 新建会话 ──

用户在 NewSessionDialog 输入任务
  → 星域选择器默认「自动匹配」
  → 用户也可以手动选择指定星域（下拉：天枢/破军/天府/天梁/天权/天机/天璇/辅/文曲）
  → 创建会话时 authority 字段发送到 POST /sessions
  → 后端 SessionManager 存储 authority 到 session.metadata
  → AgentLoop 启动时 buildActiveDomain(authority ?? taskDescription)
    → 如果是「自动匹配」：用 starDomainRegistry.matchDomain(taskDescription) 匹配
    → 注入对应 volatileBlock + systemPromptSuffix 到 system prompt

── 会话运行中 ──

Agent Manager 卡片显示：
  - 左侧：星符 glyph（accent 色）+ 星域名
  - 右侧：会话状态/进度（已有）

对话消息流中：
  - 如果发生星域切换（DecisionShift 事件），插入「改道」卡片：
    "天权 ✶ → 天府 ✦ · 任务从审查转向守护性重构"
  - 这个卡片是已有的 SSE decision_shift 事件 → event-reducer 渲染

── 委派子代理时 ──

agent 调用 delegate_task 时，可以指定子代理的 authority：
  - 比如："请天府审查这个 PR 的安全风险"
  - 子代理 session 独立绑定星域
  - DelegationTree 中显示子代理的星符
```

### 3.3 关键体验点

- **自动匹配是默认**：用户不需要每次手动选，系统根据任务关键词自动分配合适的星域
- **手动覆盖有出口**：用户可以在新建时指定，也可以在会话中途切换（通过 `/star tianfu` 或设置面板）
- **星域切换可见**：不是静默的 prompt 变化，而是在消息流中有一条清晰的「改道」提示
- **子代理也有星域**：委派出去的 worker 同样绑定星域，DelegationTree 中可以看到不同星域的子代理在并行工作

## 4. 路径 C — 议事会评审

### 4.1 用户场景

用户完成了一个涉及跨模块重构的方案设计，但不确定是否遗漏了什么。在 PlanPanel 中点击「发起议事会」，系统弹出席位配置——默认四席：天权（方案权衡）、天府（风险守护）、天机（前提质疑）、天璇（跨域反证）。用户确认后开始。

桌面端右侧 ReviewPanel 区域切换为 CouncilSurface——四张席位卡片并排，每张卡片实时显示该席星域专家的思考过程。天权首先在质疑方案的数据库迁移策略，天府紧接着指出三个文件的修改缺少回滚方案，天机追问"如果上游 API 版本不兼容怎么办"，天璇从完全不同的角度提出可以用事件溯源替代迁移脚本。

几分钟后四席全部完成，主控（天枢）汇总生成一份计划文档——包含每席的贡献摘要、冲突标注、主控裁决（哪些建议接受、哪些拒绝、哪些暂缓），以及最终的可执行任务表。议事记录完整保留，用户可以将计划推入 Build 列开始执行。

### 4.2 业务流

```
── 发起议事会 ──

用户在以下任一入口触发议事会：
  a) PlanPanel 的「议事会」按钮（当存在 plan draft 时）
  b) 对话中输入 /council 命令
  c) ThreadView 中 agent 自动提议（当 agent 判断当前决策复杂度超过阈值）

触发后：
  → 弹出 CouncilSetup 弹窗
    - 显示默认席位（天权/天府/天机/天璇）+ 可选增减席位
    - 每席显示：glyph + name + 领域简述 + 建议模型 tier
    - 可配置是否包含「自定义席位」（从用户自定义星域中选择）
    - 输入框：本次评审的核心问题（默认 = 当前上下文的计划草案）
  → 用户确认 → POST /sessions/:id/council { objective, seats[] }

── 议事会进行中 ──

后端：
  → council_convene 工具被调用
  → 扇出 N 个星域专家子代理（复用 delegateBatch）
  → 每席子代理以对应 authority 运行，产出结构化贡献
  → SSE delegation 事件流推送每席的实时进度

桌面端 CouncilSurface：
  ┌─────────────────────────────────────────────────────┐
  │  议事会 · "loop.ts 拆分方案评审"                      │
  ├──────────┬──────────┬──────────┬────────────────────┤
  │ ✶ 天权   │ ✦ 天府   │ ✸ 天机   │ ★ 天璇             │
  │ 方案权衡 │ 风险守护 │ 前提质疑 │ 跨域反证           │
  │ (strong) │ (strong) │(balanced)│ (balanced)         │
  │          │          │          │                    │
  │ 正在思考 │ 已完成   │ 正在思考 │ 等待中             │
  │ ···      │ 3 条风险 │ ···      │                    │
  ├──────────┴──────────┴──────────┴────────────────────┤
  │  ── 当全部完成 ──                                    │
  │  主控汇总（天枢 ✹）                                  │
  │  裁决：                                              │
  │  ✅ 接受 天权·数据库迁移策略改为两阶段                 │
  │  ✅ 接受 天府·添加 rollback 方案                      │
  │  ⏸ 暂缓 天璇·事件溯源方案（成本过高，留后续评估）     │
  │  ⚠ 冲突：天权与天府对文件拆分粒度意见不同              │
  │     → 裁决：采纳天府方案（文件级拆分，非函数级）       │
  │                                                      │
  │  [导出议事记录]  [推入 PlanPanel Build 列]            │
  └─────────────────────────────────────────────────────┘

── 议事会完成后 ──

产物：
  1. 最终计划文档（finalPlanMarkdown）→ 可推入 PlanPanel Build 列
  2. 议事记录（含全部贡献 + 裁决 + 冲突标注）→ 可导出为 .md 文件
  3. 遥测落库（council_session:*）→ 不可用于训练，仅审计

交接面：
  CouncilSurface → [推入 Build 列] → PlanPanel（plan 模式）
    → 用户可以在 PlanPanel 中看到议事会产出的计划
    → 后续可以触发 team_orchestrate 执行
```

### 4.3 议事会与 Team 执行的关系（关键边界）

```
议事会（Council）                 Team 执行（Team Orchestrator）
─────────────────────────────────────────────────────────────
目的：出计划                      目的：跑计划
方式：多星域单轮对抗评审           方式：多 worker 分波执行
产物：计划文档 + 议事记录          产物：代码改动 + 测试结果
触发：用户主动 / agent 提议        触发：plan 模式下自动
循环：单轮，不循环                 循环：多波，按依赖顺序
模型：按席位 tier 分模型           模型：按 task kind 路由
```

两个系统**互不调用**。议事会产出的计划文档是二者之间的唯一接口。

### 4.4 关键体验点

- **实时可见**：不是黑箱——用户实时看到每个席位在思考什么，什么时候完成
- **分歧可视化**：席位间的冲突不被隐藏，而是标注出来由主控裁决
- **可审计**：所有裁决都有理由，议事记录可导出。不是因为"主控说这样"所以这样，是因为"天权认为X、天府认为Y、主控根据Z选择了Y"
- **不阻塞**：议事会运行期间用户可以切到其他会话继续工作（后台异步运行 + inbox 通知完成）

## 5. 三条路径的关系

```
名册（路径 A）
  │
  │ 用户理解星域后
  ▼
日常会话（路径 B）─→ 每次对话绑定星域
  │                    │
  │  遇到复杂决策       │ agent 提议议事会
  ▼                    ▼
议事会（路径 C）─→ 多星评审 → 产出计划 → 执行
```

- **A 是基础**：用户先认识星域，才能信任星域
- **B 是日常**：每次对话的星域绑定是静默体验，用户不需要每次关注
- **C 是高光**：议事会是星域系统价值最集中的时刻——"北斗八星不是装饰，是在关键时刻给你八种视角"

## 6. 与现有系统的衔接点

| 现有系统 | 衔接方式 |
|----------|---------|
| `StarDomain` / `STAR_DOMAINS` | 名册直接读取展示；会话绑定复用已有注入链路 |
| `StarDomainRegistry` | 名册 API 调用 `registry.list()`；议事会席位从 registry 读取 |
| `buildActiveDomain()` | 会话新建时自动匹配（已有能力，不需要改动） |
| `DelegationRequest.authority` | 议事会扇出时每席设置对应 authority（已有字段，不需要改动） |
| `onDecisionShift` (SSE) | 桌面端已有 `decision_shift` 事件处理，渲染「改道」卡片 |
| `onDelegationActivity` (SSE) | 议事会席位进度推送复用此事件（需扩展字段） |
| PlanPanel Build 列 | 议事会产出计划 → 推入 PlanPanel，触发 team 执行 |
| DelegationTree | 委派子代理时显示星符（已在 N3 交付，只需加 authority 字段渲染） |
| `council_convene` 工具 | 已有计划（W-C1~W-C5），按原计划执行 |
| `NewSessionDialog` | 扩展：加星域选择器 |
| Agent Manager 卡片 | 扩展：左侧加星符 |

## 7. 开放决策点（待确认）

以下是业务流设计中尚未拍板的问题，需要在进入技术实现前决定：

1. **星域切换的触发方**：agent 自动感知并切换（当前 `DecisionShift` 已支持），还是用户手动切换（`/star` 命令）？还是两者都支持？
   - 建议：两者都支持。自动切换 + 用户可覆盖。

2. **议事会的默认席位**：固定天权/天府/天机/天璇四席，还是根据任务性质动态调整？
   - 建议：默认四席，用户可以增减。后续可探索「议事会模板」（如安全评审模板只包含天府+天机）。

3. **议事会发起权限**：agent 可以自动提议议事会吗？还是只允许用户手动触发？
   - 建议：agent 可以提议（在 PlanPanel 中显示提示），但最终由用户确认发起。

4. **名册入口位置**：作为 Rail 的独立 tab，还是放在 Settings 内部？
   - 建议：独立 tab。名册是差异化核心，值得一级入口。如果 Rail 拥挤，可以放在 Settings 内但给一个醒目的入口。

5. **自定义星域在议事会中的使用**：用户自定义的星域能否作为议事会席位？
   - 建议：可以。议事会席位选择器从 registry 读取全量星域，内置和自定义并列。

## 8. 实施次序建议

```
Phase 1 — 名册 + 会话绑定（先让星域可见可用）
  1a. GET /stars API
  1b. StarRoster 名册页面
  1c. NewSessionDialog 星域选择器
  1d. Agent Manager 卡片星符

Phase 2 — 议事会后端（按已有 plan W-C1~W-C5）
  └─ 独立于桌面端前端的纯后端管线

Phase 3 — 议事会前端
  3a. 扩展 SSE delegation 事件
  3b. CouncilSurface + CouncilSeat + CouncilVerdict
  3c. Council → PlanPanel 交接
```

Phase 1 改动量小、风险低、立即可见——用户打开桌面端就能看到北斗八星。Phase 2/3 可以在 Phase 1 交付后并行推进。
