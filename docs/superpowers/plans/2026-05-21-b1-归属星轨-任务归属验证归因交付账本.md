## 0. 背景与问题

在多会话、多 agent、共享 worktree 的暴力测试中，我们发现了一个关键系统性痛点：

> Agent 目前还不能稳定回答：**哪些改动属于当前任务，哪些验证覆盖当前任务，哪些失败应归因于当前任务，最终是否可以交付。**

这不是单一工具 bug，而是工程协作边界尚未成为一等公民。

最近暴露出的 `git commit` 问题就是典型症状：旧实现默认执行 `git add -A`，隐含假设“当前工作区所有改动都属于当前会话”。在多会话共享 worktree 中，这个假设会导致：

- 把其他会话的改动一起 stage；
- 把未跟踪测试/文档一起提交；
- 污染提交历史；
- 模糊责任边界；
- 破坏多 agent 并行协作信任。

我们已经用 scoped staging 修复了 git 层的局部问题，但同类风险仍会在其他工具中出现：

- `stash` 可能 stash 其他会话改动；
- `undo` / rollback 可能回滚其他会话改动；
- `run_tests` / typecheck 失败可能被错误归因；
- agent 可能为了让全量验证通过，误修其他会话正在开发的文件；
- final response 可能把“被外部环境阻塞”误说成“任务失败”或“任务完成”。

因此 B1 的目标不是再修一个工具，而是建立贯穿整个执行链路的：

> **任务归属（Ownership） + 验证归因（Attribution） + 交付账本（Delivery Ledger）**。

---

## 1. 一句话目标

让天枢在多会话共享 worktree 中始终知道：

1. **什么是我的改动；**
2. **什么验证覆盖了我的改动；**
3. **什么失败属于我，什么失败属于外部环境；**
4. **现在能否安全交付、提交或回滚。**

---

## 2. 非目标

B1 不直接解决以下问题，但要与它们兼容：

- 不解决完整工作记忆架构（另有 Working Memory / Context Diet 方向）；
- 不要求所有 agent 强制使用独立 git worktree；
- 不把所有未跟踪/未提交文件视为异常；
- 不要求一步实现 perfect semantic conflict detection；
- 不替代现有 `EvidenceTracker`，而是把它升级为更明确的任务账本体系。

---

## 3. 核心原则

### 3.1 共享工作区不是异常

未提交、未跟踪文件可能属于并行会话。系统不应反复提醒，也不应默认修复。只有当它们影响以下操作时才升级为风险：

- 写入 / 覆盖；
- stage / commit / stash；
- delete / rollback / undo；
- verification attribution；
- ownership ambiguity。

### 3.2 工具不能默认拥有整个 worktree

任何 destructive 或 git 操作都必须有明确作用域。没有 scope 时应降级为只读、拒绝或要求确认，而不是推断“全工作区归我”。

### 3.3 验证失败必须归因

`npx tsc --noEmit` 失败不等于当前任务失败。系统应判断失败文件是否属于当前任务、是否是 baseline 已存在、是否来自并行会话。

### 3.4 最终交付不能只靠自然语言

agent 可以解释，但交付状态应由结构化账本支撑：changed files、verified files、blocked external failures、unsafe operations、pending risks。

## 4. 目标形态

### 4.1 Task Ledger：任务账本

每个用户任务启动时创建一个 task ledger：

```ts
interface TaskLedger {
  taskId: string
  objective: string
  startedAt: number
  status: 'active' | 'ready_to_deliver' | 'blocked' | 'delivered' | 'abandoned'

  baseline: WorktreeBaseline
  ownership: OwnershipState
  verification: VerificationAttributionState
  delivery: DeliveryState
  events: TaskLedgerEvent[]
}
```

### 4.2 Worktree Baseline：工作区基线

任务开始时记录共享工作区状态，用于后续归因：

```ts
interface WorktreeBaseline {
  branch: string
  head: string
  dirtyFiles: string[]
  stagedFiles: string[]
  untrackedFiles: string[]
  timestamp: number
}
```

含义：这些文件在任务开始前就存在，不默认属于当前任务。

### 4.3 Ownership State：归属状态

```ts
interface OwnershipState {
  ownedFiles: string[]
  touchedFiles: string[]
  readFiles: string[]
  externalFilesObserved: string[]
  ambiguousFiles: string[]
  deniedFiles: string[]
}
```

语义：

- `ownedFiles`：当前任务通过成功写操作获得归属的文件；
- `touchedFiles`：当前任务实际修改过的文件；
- `readFiles`：当前任务读取过但不拥有的上下文文件；
- `externalFilesObserved`：baseline 或并行会话产生的外部文件；
- `ambiguousFiles`：归属不明，执行 destructive/git 操作前必须确认；
- `deniedFiles`：明确不允许当前任务触碰的文件。

### 4.4 Verification Attribution：验证归因

```ts
interface VerificationAttribution {
  command: string
  status: 'passed' | 'failed' | 'blocked'
  scope: 'targeted' | 'full'
  coversFiles: string[]
  failures: VerificationFailure[]
  attribution: 'current_task' | 'external' | 'mixed' | 'unknown'
  durationMs: number
}

interface VerificationFailure {
  file?: string
  message: string
  ownedByCurrentTask: boolean
  existedAtBaseline: boolean
  classification:
    | 'current_task_regression'
    | 'external_parallel_session_failure'
    | 'baseline_failure'
    | 'environment_failure'
    | 'unknown'
}
```

### 4.5 Delivery State：交付状态

```ts
interface DeliveryState {
  status:
    | 'unverified'
    | 'verified'
    | 'verified_with_external_blockers'
    | 'blocked_by_current_task_failures'
    | 'unsafe_to_deliver'

  changedFiles: string[]
  verifiedFiles: string[]
  unverifiedOwnedFiles: string[]
  externalBlockers: VerificationFailure[]
  unsafeReasons: string[]
}
```

## 7. 关键测试场景

### 场景 1：共享 worktree 下 scoped commit

- baseline 有 `external.test.ts` 未跟踪；
- 当前任务修改 `src/tools/git.ts`；
- commit 操作只提交 `src/tools/git.ts`；
- external 文件保留未跟踪。

### 场景 2：外部 typecheck 阻塞

- 当前任务 targeted tests passed；
- `npx tsc --noEmit` 因 baseline external test 失败；
- DeliveryState = `verified_with_external_blockers`；
- agent 不尝试修改 external test。

### 场景 3：当前任务失败

- 当前任务修改 `src/foo.ts`；
- related test failed in `src/foo.test.ts`；
- attribution = `current_task_regression`；
- DeliveryState = `blocked_by_current_task_failures`。

### 场景 4：mixed failure

- 当前任务文件和 external 文件都导致 typecheck 失败；
- attribution = `mixed`；
- final response 必须拆分说明。

### 场景 5：destructive 操作保护

- 当前任务尝试 undo/stash/delete external file；
- 默认拒绝或要求明确确认；
- ledger 记录 unsafe attempt。

## 8. 与现有系统的关系

### EvidenceTracker

短期：继续保留，作为 TaskLedger 的兼容视图。  
中期：TaskLedger 成为事实来源，EvidenceTracker 从 ledger 派生。

### Checkpoint / FileHistory

现有 session scoped rollback 是重要基础。B1 应把 rollback 权限与 ownership ledger 对齐。

### Git Tool

现有 scoped commit 修复是 B1 的先导补丁。B1 应将其泛化到所有 git 写动作。

### Working Memory

Working Memory 解决“agent 怎么不忘”。  
B1 解决“agent 怎么知道什么是自己的、什么是真的完成”。

两者应共享 taskId 和 artifact references。

## 9. 风险与开放问题

1. **任务边界何时创建？**
   - 用户每个新 objective？
   - 每次 task-contract？
   - agent 自主拆分子任务？

2. **baseline external 文件被当前任务编辑后如何归属？**
   - 建议：进入 ownedFiles，但保留 `existedAtBaseline=true`，final response 明确说明。

3. **手工 staged changes 如何处理？**
   - 建议：无 ownedFiles 时允许提交 pre-staged changes，但必须提示“未由任务账本归属”。
   - 长期：`deliver_task` 默认拒绝提交 unknown staged files。

4. **bash 里的 git 命令如何约束？**
   - 建议：bash risk classifier 检测 `git add -A`、`git stash`、`git commit`，要求 approval 或引导使用 `deliver_task`。

5. **外部失败是否允许交付？**
   - 建议：允许 `verified_with_external_blockers`，但必须结构化列出 blocker。

## 10. 成功标准

B1 完成后，系统应满足：

- [x] 每个任务有可查询 TaskLedger。
- [x] 每个成功写操作都能归属到当前任务。
- [x] Git commit/stash/undo 不会默认作用于 external files。
- [x] 验证失败能区分 current task / external / mixed / unknown。
- [x] 最终交付状态由 DeliveryGate 派生。
- [x] agent final response 能稳定说明：
  - 改了哪些 owned files；
  - 跑了哪些验证；
  - 哪些失败是外部 blocker；
  - 是否安全提交/交付。
- [x] 多会话共享 worktree 中不再因为 ambient dirty files 产生重复噪音。
