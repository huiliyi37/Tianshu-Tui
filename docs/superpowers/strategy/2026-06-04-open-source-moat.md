# 天枢开源策略：护城河分析

> **日期：** 2026-06-04
> **方法：** 天璇视角 — 跨域碎片收敛 + 定向反证
> **核心问题：** 开源什么、闭源什么、什么不怕抄袭

---

## 1. 先回答一个前置问题：什么才是天枢真正的护城河？

不是代码。代码可以被复制。

天枢的护城河是**三层的**：

| 层 | 护城河 | 可复制性 | 说明 |
|---|--------|---------|------|
| L1 | 代码架构 | ⭐ 高度可复制 | 任何人都能 fork 并重写 |
| L2 | 星域方法论 + 协作协议 | ⭐⭐ 中度可复制 | 需要 AI 研究经验才能理解为什么这样设计 |
| L3 | 持续迭代飞轮 | ⭐⭐⭐ 极难复制 | 你和星域团队每天都在用天枢开发天枢——这个反馈闭环别人拿不走 |

**关键洞察：L2 是你最强的护城河，但 L2 恰恰是最适合开源的部分。** 因为方法论越多人用，它就越成为标准——而你是标准的制定者。

## 2. 开源分层方案

### 第一层：开源（社区版 / OSS Core）

**目标：** 让开发者能跑起来，能感受到天枢的不同，但不会成为你的竞争对手。

| 模块 | 开源内容 | 理由 |
|------|---------|------|
| **agent loop** | 完整的 AgentLoop + SessionContext | 核心引擎，必须开源才能让人信任 |
| **tools** | 所有基础工具（read_file, bash, grep, glob, edit_file, write_file） | 这是功能基线 |
| **TUI** | 完整的 Ink 6 界面 + Static 渲染 + 流式动画 | 视觉冲击力是传播力 |
| **compact** | 三层上下文压缩（per-call cap / per-turn budget / pressure truncation） | 技术实力的展示 |
| **cache** | 前缀缓存策略 + cache-log 诊断 | 这是别人没有的，展示了你对成本的理解 |
| **prompt static** | 系统提示词的 static 部分 | 社区可以学习你的 prompt 工程 |
| **loop-types** | AgentConfig / AgentCallbacks 等类型 | 类型即文档 |
| **claim-store** | 基础 claim 存储 + recall | 项目记忆的基础能力 |
| **config** | 多层配置加载 | 基础设施 |

**开源后社区获得的能力：**
- 单星域终端 coding agent（相当于当前的 GLM/DeepSeek 单会话模式）
- 三层上下文管理
- 前缀缓存优化
- 基础项目记忆

### 第二层：闭源（Pro / Team）

**目标：** 这才是你变现的能力——团队协作和多星域调度。

| 模块 | 闭源内容 | 理由 |
|------|---------|------|
| **coordinator** | 多 worker 调度 + 任务依赖图 + 真并行 | 这是团队模式的核心引擎 |
| **worker-profiles** | 天权/天府/天璇/天梁的星域 profile + system prompt | 星域方法论的具体实现 |
| **team-orchestrate** | 单会话 → 自动规划 → 并行执行 → 集成 | 天枢 3.0 的入口工具 |
| **task-board TUI** | 终端任务面板 | 团队模式的可视化 |
| **plan aggregator** | 多 planner 输出 → unified_plan 合并 | 规划阶段的核心智能 |
| **prompt volatile/engine** | 动态提示词生成（星域路由、季节判断、收敛检测） | 这些是你调了数千轮才调出来的 |
| **convergence/CVM** | 收敛检测 + 认知镜 + 上下文压力自适应 | 高级自省能力 |
| **ownership ledger** | 多 worker 文件归属追踪 | 团队模式的安全网 |

**闭源的理由不是"藏"，是"需要持续服务"：**
- 星域 profile 需要随着新模型发布持续调优
- 任务面板需要配套的云服务（如果做 SaaS）
- coordinator 的并发策略需要实际团队使用反馈来迭代

### 第三层：商业版（Enterprise）

| 能力 | 描述 |
|------|------|
| **云任务面板** | Web 版任务面板（参考 Multica 的 board view） |
| **多工作区** | 团队级隔离 + 权限管理 |
| **模型路由** | 自动选择最优模型（天权用 V4-PRO 规划、天梁用 Flash 执行） |
| **审计日志** | 企业合规需求 |
| **SaaS 部署** | 一键部署，不需要自己搭 |

## 3. 什么不怕抄袭？

### 不怕抄袭的（开源这些）

| 能力 | 为什么不怕 |
|------|-----------|
| 三层上下文压缩 | 算法公开了，但要调对参数需要实战。你的 cache-log 数据是别人没有的。 |
| 前缀缓存策略 | 别人可以复制代码，但不知道为什么你的 hit rate 能到 99%。秘密在于 prompt 的结构设计——static/volatile 分层。 |
| 工具设计模式 | Tool interface + ToolResult 是好的设计，但不是护城河。护城河是**你每天在用这些工具开发天枢**所积累的 prompt 经验。 |
| Ink 6 TUI 组件 | UI 代码人人能写。但你的月相呼吸指示器、thinking cursor 这些微动画展现了你的品味——品味不可复制。 |

### 怕抄袭但必须保护的（闭源这些）

| 能力 | 抄袭风险 | 保护方式 |
|------|---------|---------|
| 星域 profile（天权/天府/天璇/天梁） | 高——这是核心方法论的具体实现 | 闭源 + 作为 Pro 功能 |
| 多 planner 聚合策略 | 中——算法不复杂，但需要大量调参 | 闭源 |
| coordinator 并行调度 | 中——delegate_batch 的架构可以被模仿 | 闭源 + 持续迭代保持领先 |
| 动态 prompt engine | 高——这是让不同模型在不同星域表现一致的关键 | 闭源 + 混淆 |

## 4. 定向反证

**反证假设：** "如果我开源了全部代码，别人就能做一个天枢 clone。"

**反证：** 不一定。

1. **Cursor 开源了吗？** 没有。但 Claude Code 的体验已经追上了。市场不等你。
2. **Linux 全部开源了。** 但 Red Hat 的企业版照样赚钱——因为企业需要的是**持续的服务和支持**，不是一次性代码。
3. **你的真正优势不是代码，是你在天枢上投入的 300+ 小时的调优经验。** 别人拿到代码，还需要 300 小时才能理解为什么 prompt 要这样写、为什么缓存要这样分层。

**结论：** 适度开源不会削弱你的竞争力，反而会加速你的影响力。

## 6. 一个重要的战略选择

你有两条路：

**路线 A：开源工具，闭源团队模式**
- 类似 VS Code（开源）→ GitHub Copilot（闭源插件）
- 社区用你的工具，团队模式收费
- 优点：快速积累用户，低风险
- 缺点：如果大厂复制你的团队模式，你很难防御

**路线 B：全部开源，卖服务和调优**
- 类似 Red Hat（全部开源，卖企业支持 + 认证）
- 所有代码都开源，但你的优势是"调了 300 小时的参数和 prompt"
- 优点：最大化影响力，适合"投简历进模型团队"的路线
- 缺点：收入天花板较低

**我的建议：先走路线 A，积累用户和口碑。如果 6 个月后大厂开始复制你的团队模式，再考虑路线 B。**

原因：路线 A 给你时间建立品牌。等社区足够大时，即使大厂复制代码，用户也已经认准天枢这个名字了。Linux 不怕 Windows，因为社区在你这边。
