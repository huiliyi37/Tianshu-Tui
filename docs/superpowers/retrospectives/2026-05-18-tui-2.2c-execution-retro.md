## 1. 时间线与关键决策

| # | 任务 | 耗时 | 关键摩擦点 |
|---|------|------|-----------|
| C1 | Kick Cooldown | ~10 min | 平滑：plan 代码直接可用，测试只需补 turn 参数 |
| C2 | Hook 注册工厂 | ~15 min | 测试中误加了 telemetry-writer postTurn hook，纠正后通过 |
| C3 | Snapshot Builder | ~10 min | 需要确认 afterPerception 的 `currentSensorium`/`currentStrategy` 与 `this.sensorium`/`this.strategy` 语义等价 |
| C4 | Telemetry Writer | ~25 min | 测试失败 `.rivet` 目录不存在 → writer 需要 `mkdir`；`StrategyProfile` 类型缺字段 |
| C5 | /retrospect 激活 | ~25 min | 最大不确定性：命令注册入口在哪、`SlashHandlerContext` 没有 `cwd`、`TraceStore` 没有 `getAll()` 只有 `.events`、format 兼容性需要 round-trip 验证 |

**关键决策**：

1. **C5 命令注册选在 `app.tsx` 而非 `slash-commands.ts`**：因为 `/retrospect` 需要异步文件 I/O，而 `handleSlashCommand` 是同步函数（返回 `boolean`）。`/rollback` 和 `/interview` 也走 app.tsx 内联模式，保持了一致性。

2. **C4 的 telemetry writer 加了 `mkdir`**：原 loop.ts 内联代码直接 `appendFile`，依赖 `.rivet` 目录已由其他组件（stigmergy store）创建。提取后 writer 应自包含 → 加了 `mkdir(…, { recursive: true })`。

3. **C5 不传 git log**：`generateRetrospect` 接受 `gitLog: string[]` 但命令处理器暂时传空数组。理由是当前 SlashHandlerContext 没有暴露 git 能力，且 plan 允许增量交付。

## 2. 架构观察

### 2.1 硬度层次验证

Plan 的 `pure core → hook wrapper → runtime registration → telemetry → behavior` 规约在实践中运转良好：

```
C1: pure core       → kick-hook.ts 内部加 cooldown 状态闭包
C2: hook wrapper    → createDefaultRuntimeHooks() 封装注册
C3: runtime reg     → buildRuntimeSnapshot() 消除构造重复
C4: telemetry       → TelemetryWriter seam 独立可测
C5: behavior        → /retrospect 命令对外激活
```

每层改动只影响自己所在层及上层 wiring——C1 改 kick-hook 不影响 C2-C5，C3 改 loop.ts 内部不影响 hook 实现。这是好的分层设计。

### 2.2 loop.ts 仍然是热点

尽管 C2/C3 减少了 loop.ts 的 import 行数和构造重复，`loop.ts`（~930 行）仍然是 agent 目录中最大的文件。主循环中嵌入的逻辑包括：

- Hook pipeline 调度（preTurn / afterPerception / postTool）
- 感知计算（sensorium + strategy）
- 星相事件（createStarEvent）
- telemetry 写入（现在是 writer.write，但仍在此处构造 snapshot）
- repair hint 注入
- context ceiling 强制执行
- LLM 调用 + streaming

**建议**：下一步可以考虑提取 `TurnExecutor`——将单个 turn 的执行逻辑从 loop.ts 中拆出。这会让 loop.ts 退化为纯调度循环，turn 内逻辑独立可测。

### 2.3 SlashHandlerContext 缺少 cwd

`SlashHandlerContext` 有 `agent: AgentLoop`、`session: SessionContext`、`persist: SessionPersist`……唯独没有 `cwd`。`/rollback` 和 `/retrospect` 都是用 `process.cwd()` 绕过的。如果将来有命令需要操作非当前工作目录的 agent session，这会成为瓶颈。

**建议**：`SlashHandlerContext` 加 `cwd: string` 字段，或者在 `AgentLoop` 上暴露公共 getter。

### 2.4 TraceStore 的 API 不对称

`TraceStore` 是一个 plain object interface（`{ maxEvents, events, toolFingerprints }`），不提供方法封装。loop.ts 中直接操作 `events` 数组。而 `getTraceStore()` 返回的是可变引用——调用者可以随意修改。这与 `EvidenceTracker`（有 `getState()`、`recordVerification()`）形成对比。

**建议**：给 `TraceStore` 加只读查询方法（如 `getToolEvents(): TraceEvent[]`），或者返回 `Readonly<TraceStore>`。

## 3. TDD 经验

### 3.1 什么时候「先写失败测试」容易

- **纯逻辑改动**（C1 cooldown）：在现有测试框架上加一个 case，直接表达期望行为
- **已有函数的 round-trip 测试**（C5 adapter）：用 `buildTelemetrySnapshot` 造数据 → `parseSensoriumLog` 解析 → 断言字段

### 3.2 什么时候「先写失败测试」难

- **提取 seam 不改变行为**（C3 snapshot builder、C4 telemetry writer）：测试验证的是「改动后行为不变」，不是「新行为正确」。这时测试先于实现的价值在于捕获回归，而非驱动设计。
- **TUI 命令处理器**（C5 app.tsx 内联）：Ink 组件的命令分发逻辑依赖 React state + agent 实例，难以在不启动完整 TUI 的情况下单独测试。这里「先写 round-trip 测试」捕获了最关键的 format 兼容性问题，命令分发本身依赖手工验证。

### 3.3 教训

1. **测试的抽象层次很关键**：C4 的测试写了真正的文件 I/O（`readFileSync` 验证写入），暴露了 `.rivet` 目录不存在的问题，这是纯 mock 测试无法发现的。
2. **类型系统是第一道测试**：C4 的 `StrategyProfile` 缺字段是 `tsc` 捕获的，不是运行时。TypeScript strict 模式在 seam 提取中价值巨大。
3. **测试框架的模块解析差异**：`node:test` + `tsx` 的模块解析与 `tsc` 不同——`tsx` 需要 `.js` 扩展名但在运行时自动处理。这在 C2 的测试创建时表现为 `ERR_MODULE_NOT_FOUND`，是预期的「失败测试」。

## 5. 对 2.3 Conscious Agent 的建设方向

C5 完成后，2.3 的 Playbook Evolution 管线已经就绪：

```
session 运行 → sensorium.jsonl 写入 (C4 TelemetryWriter)
             → /retrospect 命令 (C5)
             → parseSensoriumLog + generateRetrospect
             → NTSB 四层分析报告
             → 提取 delta bullets
             → .rivet/playbook.jsonl
```

**建议 2.3 的前 3 个任务**：

1. **自动触发 retrospect**：session 结束时（非用户手动 `/retrospect`）自动调用 `generateRetrospect()`，结果写入 `.rivet/retrospect-<date>.md`
2. **Delta bullet 提取**：从 retrospect 报告的「根因判定」和「寻址建议」章节提取结构化 delta bullets，写入 playbook
3. **Playbook injection**：下个 session 开始时，将 playbook 中最近 N 条 delta 注入 volatile context

这三个任务完全依赖 C1-C5 的成果（cooldown 防止 kick 污染 playbook、hook factory 让 session-end hook 可注册、snapshot builder + telemetry writer 保证格式稳定）。

## 6. 随手记

- `import('node:fs/promises').then(...)` 动态导入模式在 telemetry writer 中出现——这是为了在 import 时避免同步文件系统调用。但 writer 本身不导出任何同步依赖，可以用顶层 `import { mkdir, appendFile } from 'node:fs/promises'` 简化。
- `SensoriumEntry`（retrospect.ts）和 `PerceptionTelemetrySnapshot`（perception.ts）的字段名不完全一致（`thetaInterval` vs `thetaCycleInterval`），但 `buildTelemetrySnapshot` 做了映射。如果将来加字段需要在两个接口间同步，建议一个 adapter 函数显式转换。
- C1 的 cooldown 默认值 3 的选择：如果 turn 间隔很长（用户思考时间久），3 turn 足够；如果 turn 很快（模型快速迭代），可能需要调低到 2。当前默认值合理，可通过 `cooldownTurns` 参数调整。
