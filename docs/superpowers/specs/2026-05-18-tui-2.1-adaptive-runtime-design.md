## 背景

### 用户需求
天枢（GPT-5.5）完成 StarFlow v2 闭环接线后，提出 5 个 TUI 2.1 方向：
1. `/retrospect` — 内建复盘命令
2. Worker 降级更优雅
3. Theta telemetry 增强
4. Git status freshness
5. 更稳定的多代理协作

### 调研发现摘要

| Scout | 领域 | 核心洞察 |
|-------|------|----------|
| 菌根网络 | 多代理协作 | 局部自利涌现全局协作；降级状态是常态；不对称 hub 拓扑最优 |
| NTSB 航空调查 | /retrospect | 四层故障分类（HFACS）；事实与分析分离；寻址建议 |
| 生物钟基因网络 | Theta + Git freshness | 无固定周期（free-running + entrainment）；精度在处理层；互锁双环路 |
| 黏菌网络优化 | Worker 降级 | 排斥信号 4x 快于吸引信号；三层韧性（热/温/冷）；记忆编码在网络拓扑中 |

### 关键收敛

5 个特性收敛为 3 个独立工作流：
- **Git freshness + Theta telemetry** → 工作流 A（git 是 theta 的 Zeitgeber）
- **Worker 降级 + 多代理协作** → 工作流 B（同一问题的两面）
- **/retrospect** → 工作流 C（独立，消费 A 的数据）

## 工作流 A：Git Freshness 作为 Theta Zeitgeber

### 生物学原理
生物钟不使用固定周期。SCN 的自由运行周期 ~24.2h，每天被光照信号（Zeitgeber）校准回 24.0h。theta-gamma 节律应该同样有一个"自由运行倾向"，被外部信号（代码变化率）持续校准。

### 具体设计

**信号采集**：每 turn 开始时执行 `git diff --stat HEAD~5 --numstat`
- 输出：changed_files_count / total_tracked_files → change_rate (0-1)
- 平滑：指数移动平均 `smoothed = α × raw + (1-α) × prev`，α = 0.3

**注入 Sensorium**：
- 将 smoothed change_rate 作为额外的 pheromone 信号注入
- 或直接影响 freshness 维度的计算（与 stigmergy pheromones 加权平均）

**Theta 自适应**：
- 当前：`thetaCycleInterval = complexity > 0.5 ? 3 : 7`（固定两档）
- 改为：`thetaCycleInterval = baseInterval × (1 - changeRate × 0.5)`
- 效果：代码活跃时检查更频繁（interval 缩短），代码稳定时检查更稀疏

**Telemetry 增强**：
- sensorium.jsonl 自动包含 git change_rate
- theta 触发时记录 tsc 结果（已有）+ git diff summary

### 成功标准
- sensorium.jsonl 中 freshness 在 session 内变化 > 0.2
- theta interval 在同一 session 内至少变化 1 次

### 退出条件
- git diff 耗时 > 100ms → 降级为每 5 turn 采样一次
- 无 git 仓库 → 跳过，freshness 回退到纯 pheromone 模式

## 工作流 B：Physarum Worker 路由（三层韧性）

### 生物学原理
黏菌通过"先广泛探索、后选择性收敛"构建最优网络。管道粗细由流量正反馈决定。关键发现：排斥信号（失败）传播速度是吸引信号（成功）的 4 倍。

### 具体设计

**Provider 状态机**：
```
type ProviderTier = 'hot' | 'warm' | 'cold'

状态转换规则：
  hot → warm: 连续 2 次失败
  warm → cold: 连续 3 次失败 或 30 分钟无成功
  cold → warm: 手动重试成功 1 次
  warm → hot: 连续 3 次成功
```

**权重更新（黏菌管径公式简化）**：
```typescript
// 成功时缓慢升权（吸引信号慢）
weight = weight + 0.1 × (1 - weight)

// 失败时快速降权（排斥信号快，4x）
weight = weight - 0.4 × weight
```

**路由选择**：
- 从 hot tier 中按权重加权随机选择
- hot 为空时 fallback 到 warm
- warm 为空时 fallback 到 cold（触发重新探测）

**记忆持久化**：
- Provider 权重存入 `.rivet/provider-weights.json`
- 跨 session 保留（类似黏菌管径层级编码记忆）
- 影响收敛速度但不锁定方向

### 成功标准
- 模拟 provider 失败 → < 1s 切换到备选
- 权重在 5 次调用后开始分化（不再均匀）

### 退出条件
- 只有 1 个 provider → 跳过路由，直接使用
- 所有 provider 都 cold → 全部重置为 warm，重新探测

## 工作流 C：/retrospect（NTSB 四层分析）

### 方法论原理
航空事故调查的核心洞察：大多数"操作错误"背后是系统设计缺陷。HFACS 四层模型确保分析不停留在表面。

### 报告结构

```markdown
# Session Retrospective

## 1. 事实时间线
[从 sensorium.jsonl + git log + tool trace 重建]
- 纯事实，无解读
- 多流时间同步（tool calls × text output × file changes）

## 2. 四层分析
### L4 系统层（prompt/tooling/model）
- 提示词模板是否引导了正确行为？
- 工具能力是否足够？
- 模型选择是否合适？

### L3 编排层（task decomposition/guardrails）
- 任务拆解是否合理？
- 是否有缺失的验证步骤？

### L2 上下文层（context/freshness/pressure）
- 上下文是否饱和？
- 文件读取是否过时？
- sensorium 维度是否异常？

### L1 执行层（agent decisions）
- 工具选择是否正确？
- 错误恢复是否及时？

## 3. 根因判定
- Probable Cause: [单一最近因]
- Contributing Factors: [系统性条件]

## 4. 寻址建议
- 致用户: [...]
- 致系统设计: [...]
- 致工具维护: [...]

## 5. 模式识别
- 是否为首次出现？
- 与历史 session 的相似度
```

### 数据源
- `.rivet/sensorium.jsonl` — 每 turn 的 6 维快照 + 策略决策
- `git log --oneline -20` — 最近提交历史
- TraceStore（内存）— tool call 序列 + 耗时 + 成功/失败
- EvidenceTracker — 文件修改 + 验证状态

### 成功标准
- 报告包含四层分析（不只是 L1）
- 每条建议指向具体执行者
- 生成时间 < 3s

### 退出条件
- sensorium.jsonl 为空 → 输出"无足够数据，至少需要 1 个完整 turn"

## 实施优先级

```
Phase 1: 工作流 A（git freshness → theta 自适应）
  ↓ 产生动态 telemetry 数据
Phase 2: 工作流 B（Physarum worker routing）
  ↓ 独立，可并行
Phase 3: 工作流 C（/retrospect）
  ↓ 消费 Phase 1 产生的数据
```

A 必须先行（为 C 提供数据）。B 独立。C 最后（需要数据积累）。

---

## 风险与应对

| 风险 | 应对 |
|------|------|
| git diff 在大仓库慢 | 采样频率自适应；> 100ms 降频 |
| Provider 权重振荡 | 指数移动平均 + 最小权重阈值 0.05 |
| retrospect 数据不足 | 最少 3 turn 才生成报告 |
| theta 自适应导致检查过频 | 设置最小间隔 floor = 2 |
