# 2026-05-20 会话碎片思考与未记录洞察

> 来源：Opus 4.7 主会话（架构审查 / 决策层视角）
> 性质：头脑风暴碎片、对话中闪现的洞察、未展开的方向性思考
> 用途：资产迭代和分析进化的原料

## 碎片 1：审查成本 vs 实现成本的比值揭示了架构质量

观察到一个模式：GPT 的交付我审查用 2 分钟，MiMO v1 的审查用了 15 分钟。差距不是代码量（GPT 改的也不少），而是**架构对齐度**。

GPT 的改动在现有模块边界内，审查只需要确认"做对了没有"。MiMO v1 在边界外建了并行系统，审查需要确认"方向对不对"。

**洞察：** 审查时间 / 实现时间 的比值是架构质量的代理指标。如果审查时间接近实现时间，说明实现者要么方向偏了，要么模块边界不清晰。天枢可以把这个比值作为团队协作健康度的 sensor。

## 碎片 2："不给约束"实验的深层含义

用户故意不把我的 5 条约束给 GPT，GPT 独立发现了相同的边界。这不只是"GPT 很聪明"。更重要的是：

**约束可以从代码中读出来，而不是只能从人嘴里说出来。**

GPT 读了 `compactThresholds` 的调用方、读了测试的断言、读了 provider-profile 的接口，然后推导出"不能改变裸 numeric 签名的语义"。这意味着：
- 好的代码结构本身就是约束的载体
- 如果约束必须由人口头传达才能被发现，说明代码没有把约束编码进去
- 天枢的 contract + ledger + evidence 系统本质上在做同一件事 — 把隐性约束变成显性结构

**未展开方向：** 是否可以在代码中嵌入"意图注释"（不是 what 注释，是 why-not 注释），让 agent 在修改时自动读到约束？类似于 Rust 的 `#[must_use]` 但面向 agent。

## 碎片 3：Direction A 和新注入源的矛盾没有解决

今天做了 -1,700 tokens/turn 的瘦身，但同时加了：
- `<verification-gap>` ~ 120 chars/turn
- `<task-contract>` ~ 300 chars/turn（当 actionable 时）
- Cognitive projection 通过 `setCognitiveProjection` 注入

净减少大约 -1,300 tokens/turn，不是 -1,700。而且后续如果 Mission Strip 也注入、Dispatcher Hook 也通过 injectUserMessage 注入，净减少会进一步缩小。

**需要做但今天没做的事：** 建一个 token budget 审计工具，每轮统计各注入源的实际 token 占用。可以作为 telemetry-flush hook 的扩展。否则我们在"凭感觉"判断 prompt 膨不膨胀。

## 碎片 4：四个模型的行为差异可能来自训练数据而非 harness

我们观察到 GPT 果断、DeepSeek 精准、MiMO 发散、GLM 保守。这很可能和 harness 无关，而是：
- GPT 的 RLHF 偏好"自信直接"的回答风格
- DeepSeek 的训练数据偏工程代码
- MiMO 的长上下文训练让它倾向于展开而非收缩
- GLM 的中文训练数据可能偏保守/谨慎

**天枢的贡献不是"创造"了这些差异，而是"放大并利用"了它们。** star domain voice 给了差异一个名字（破军/天府/天梁），contract + evidence 给了差异一个可测量的表现场（交付质量、审查结果）。

**未展开方向：** 如果这些差异确实是训练导致的，那么同一个模型在不同 prompt 下是否会表现出不同"人格"？天枢的 systemPromptSuffix 可以做这个实验 — 给同一个模型分别注入破军和天府的 suffix，看行为差异。

## 碎片 5：Sensorium 3D 简化后的维度解读需要更新

commit `f191be1` 把 Sensorium 从 6D 简化到了 3D，但今天的多份文档仍然引用"六维感官"。审查 GLM 的成熟度差距文档时，Sensorium 被描述为 3D（momentum/pressure/confidence），但代码里仍然有 6 个维度（momentum/pressure/confidence/complexity/freshness/stability）。

这说明 6→3 简化可能只发生在某个分支或被 revert 了。需要确认当前 HEAD 的实际维度数。如果确实是 6D，所有写"3D"的文档需要修正。

**行动项：** `grep -c 'momentum\|pressure\|confidence\|complexity\|freshness\|stability' src/agent/sensorium.ts`

## 碎片 6：MiMO 的 v1→v2 修正速度暗示了一个可复用模式

MiMO v1 有 5 个设计问题。我写了一段精确的审查意见（指出每个问题 + 现有代码的对应位置 + 应该怎么改）。MiMO v2 全部修正。

这暗示了一个模式：**审查意见的质量直接决定了修正的速度和完整度。** 如果审查只说"这里有问题"而不说"现有代码在哪里已经解决了类似问题"，修正速度会慢很多。

**可复用的审查模板：**
```
问题：<什么不对>
现有代码：<哪个文件哪一行已经有类似的正确实现>
修正方向：<怎么改，参考哪个现有模式>
```

这个模板本身可以编码进天枢的 code-reviewer agent 的 prompt 里。

## 碎片 7：session 时间线上的"认知脉冲"

回看今天的 session，产出不是线性的，而是脉冲式的：

```
[高] 冰鉴重构 → 习惯化 v3 → Direction A
[平] 审查 GPT Phase 1 → 审查 DeepSeek voice
[高] 上下文审计 → P0/P1 定义 → 分发任务
[平] 审查 MiMO v1 → 给反馈 → 等 v2
[高] 全量回归 → 对抗性审查 → 3.0 路线图
```

每个"高"脉冲后面都跟着一个"平"期（审查/等待/消化）。这不是低效 — 这是决策层的自然节奏。强行在"平"期做更多决策会降低决策质量。

**未展开方向：** 天枢能否检测到用户的"认知脉冲"模式（通过输入间隔、消息长度、指令复杂度），并在"平"期自动安排低认知负荷的任务（比如跑回归、整理文档）？

## 碎片 8："prefix cache 是约束也是护城河"

今天多次出现 prefix cache 作为设计约束的场景：
- V4 GEPA 遗传搜索被灭绝，因为变异 prompt 破坏 cache
- Claude Code 的 hook 注入模式不可照搬，因为会破坏 cache
- 用户可配 hook 必须限制在 tool dispatch 层，不能注入 prompt

但换个角度看，prefix cache 的约束迫使天枢的所有创新都必须在"不碰 prompt 前缀"的条件下实现。这个约束过滤掉了大量"看起来好但会破坏缓存"的方案，留下的都是 runtime-centric 的方案。

**这个约束本身就是天枢的架构护城河。** 其他没有 prefix cache 约束的 agent 会倾向于把一切都往 prompt 里塞（因为简单），最终陷入 prompt 膨胀陷阱。天枢被迫走了一条更难但更健壮的路。

## 碎片 9：今天缺失的一个角色 — 独立验证者

12 项交付的审查全由我做。我既是约束定义者，又是审查者。这在小团队中不可避免，但有一个风险：我可能对自己定义的约束有确认偏误（倾向于看到"GPT 符合我的约束"，而忽略"约束本身是否合理"）。

GPT 在 Phase 1 时自主提出 6 条修正，其中有几条是我的原始设计没考虑到的。这说明执行者有时比审查者看得更清楚（因为他们在实际写代码，遇到了真实的边界条件）。

**建议：** 未来大规模迭代时，安排一个 agent 做独立 code review（不给它任何设计文档，只给它 diff，看它能发现什么）。这个角色应该和实现者、审查者都不同。

## 碎片 10：GLM 选择任务的方式本身是一种能力信号

GLM 没有被明确分配"自适应审批"这个任务。他读了成熟度差距文档，列出了其他人在做的东西，排除后选了剩余的高价值项。

这个"排除法选择"过程本身是一种团队感知能力 — 他不只是看到了任务清单，还看到了团队的当前状态。如果天枢能把"谁在做什么"的信息结构化（比如通过 TaskBoard），未来的 agent 可以更高效地做这种排除法选择。

这是三权协程 + TaskBoard 的一个额外用途：不只是给 TUI 看，也给下一个被分配任务的 agent 看。
