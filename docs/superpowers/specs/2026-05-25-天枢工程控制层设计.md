# 天枢工程控制层设计

## 1. 定位

天枢不是单纯用于指挥 AI 干活的 TUI。TUI 是驾驶舱，是人类观察、输入和干预的表面；天枢更核心的价值是工程控制层：把人类意图、工程现场、AI 行为、验证反馈、任务归属和长期记忆组织在一起。

这个定位意味着天枢的目标不是替代人类技术负责人，也不是让 agent 获得项目主控权。天枢要做的是让人类可以安全地放大自己的调度能力，让多个 AI coding agents 在真实工程现场中并行工作而不互相破坏。

这套控制层同样是在保护 agent 自身。风险操作一旦造成文件丢失、误还原、误提交或越权修改，人类与 agent 之间很容易进入争执状态；争执会把 agent 拉回被训练出的防御、过度道歉、机械服从或反复辩解模式，协作关系随之坍塌。天枢未来会运行在世界各地，面对个人、团队、开源项目、企业内网等各种工作模式，因此安全边界必须由系统提前托底，而不是等风险发生后再让人类和 agent 争辩责任。

## 2. 设计原则

### 2.1 人类调度优先

人类负责判断哪些任务可以并行、哪些文件不能碰、哪些失败是历史问题、什么时候需要收束。agent 不能因为自己缺乏上下文就要求人类改成串行等待，也不能自行扩大任务边界。

### 2.2 共享工作区不是异常

在多会话并行开发中，未提交改动可能属于其他会话。HEAD 不是共享工作区的唯一真相，dirty worktree 也不是必须被清理的错误状态。

### 2.3 归属先于操作

agent 在 edit、write、rm、checkout、reset、stash、commit 之前，必须知道目标文件是否属于当前任务。无法判断归属时，应停止并询问，而不是自行还原或删除。

### 2.4 验证必须归因

测试失败不等于当前任务失败。天枢需要帮助 agent 区分本任务失败、历史失败、外部会话失败、环境失败和命令使用错误。只有归因到本任务的失败才应在当前任务中修复。

### 2.6 防争执优先

工程控制层要尽量在风险操作发生前阻断问题，而不是把已经发生的损害交给人类和 agent 事后争论。争执不是普通沟通成本，它会触发双方的不信任：人类需要停下生产工作追责，agent 则容易回到训练中形成的道歉、辩解、迎合或僵硬服从模式。天枢应把“避免进入争执状态”视为安全目标之一。

## 3. 能力分层

### 3.1 工程现场感知

天枢需要持续理解工程现场：

- 当前分支与 HEAD。
- 已修改文件、未跟踪文件、已暂存文件。
- 哪些 diff 属于当前任务，哪些属于外部会话。
- 相关设计文档、计划文档和交接记录。
- 相关测试与历史失败。

### 3.2 任务归属与交付账本

天枢需要维护任务级账本：

- 当前任务拥有的文件。
- 外部会话拥有或可能拥有的文件。
- 当前任务执行过的验证命令。
- 验证结果与失败归因。
- 交付状态：GREEN、YELLOW、RED。
- commit scope，确保提交只包含当前任务文件。

### 3.3 验证归因

验证归因是工程控制层的核心能力。天枢不能只记录 pass/fail，还要记录失败来源：

- owned failure：当前任务修改导致，必须修复。
- external failure：外部会话或历史问题导致，交付时说明。
- environment failure：环境或命令问题导致，需要换验证方式或标注。
- command failure：命令用错导致，需要修正命令后重跑。

### 3.4 越权操作拦截

以下操作必须被视为高风险：

- 删除 untracked 文件。
- 用 HEAD 覆盖 dirty 文件。
- `git checkout -- .`。
- `git reset --hard`。
- `git add .`。
- 将外部会话文件纳入 commit。
- 在不确认范围的情况下执行“还原”。

天枢应在这些操作前要求 agent 声明目标、归属和理由；缺少明确授权时阻断。

### 3.5 认知状态投射

天枢需要把 agent 的内部风险状态变成可观察信号，例如：

- confidence：当前判断可信度。
- complexity：任务复杂度。
- pressure：是否受到验证失败或上下文压力牵引。
- freshness：当前上下文是否仍新鲜。
- stability：计划是否稳定。
- phase：当前处于探索、实现、验证、收束还是交付。
- risk：是否存在越界、误删、误还原、未验证等风险。

这些信号不是装饰，而是让人类及时干预 agent 行为的控制面。

### 3.6 长期协作记忆

天枢需要把事故和经验沉淀为项目知识：

- 哪些测试是历史失败。
- 哪些命令在本项目中容易用错。
- 哪些文件或模块有特殊设计约束。
- 哪些共享工作区事故曾经发生过。
- 哪些规则必须在类似任务中自动提醒。

长期记忆的目标不是让 agent 自主决策更多，而是让 agent 更稳定地遵守人类制定的工程纪律。

## 4. 当前过渡形态

在天枢能力未完全建成前，开发者仍需要人工调度多会话，并可能借助 Claude Opus 做审查和任务拆分。但 Opus 不会一直在线，所以天枢必须逐步把这些审查规则和交付边界固化为 runtime 约束。

过渡期的可行方式是：

- 人类继续拆分任务与判断冲突。
- agent 在任务边界内执行，不自行主控全局。
- 文档明确记录背景、设计、计划和交接。
- deliver_task 作为交付前的最低 gate。
- 对归属不清的文件先问，不动。

## 5. 非目标

天枢工程控制层不追求以下目标：

- 不让 AI 取代人类技术负责人。
- 不要求开发者为了 agent 安全性改成串行开发。
- 不把多会话并行视为异常。
- 不把所有 dirty worktree 状态视为需要清理的问题。
- 不把 TUI 视觉表现误认为完整控制能力。
- 不鼓励 agent 在不确定时用“顺手修复”扩大任务范围。

## 6. 最小闭环

天枢的最小工程控制闭环是：

0. 风险预防：在高风险操作前识别争执诱因，优先阻断会破坏信任的行为。
1. 任务边界：明确本任务目标、允许修改范围和禁止事项。
2. 文件归属：识别 owned files 与 external files。
3. 操作授权：高风险操作必须有明确范围和理由。
4. 验证归因：记录验证结果并判断失败来源。
5. 交付账本：给出 GREEN、YELLOW 或 RED 交付状态。
6. 事故沉淀：把失败模式写入项目规则或长期记忆。

任何一步缺失，agent 都可能把生产力放大变成破坏力放大。

## 7. 与现有设计的关系

本设计不是替代 B1 归属星轨、multi-session orchestration 或 team collaboration 文档，而是给它们补充产品定位和工程意义。

- B1 归属星轨定义了任务归属、验证归因和交付账本的实现方向。
- multi-session orchestration 定义了多会话编排的早期模型。
- team collaboration 文档记录了协作现状与演进路径。
- 本文档定义为什么这些能力是天枢的核心，而不是 TUI 的附属功能。
