# Scout-Calibrated Planning 设计方案

> 深度头脑风暴结果 — 2026-05-27

## 背景

### 问题

mimo 在规划"实时 token 流式渲染"时，读了主要文件但没理解函数存在的原因（`dedup.ts`），导致计划提出了破坏性改动。根本原因不是"缺少审查 gate"，而是**调研深度不足**——快模型倾向于快速扫描而非深入理解。

### 约束

- 不对所有模型加同样重的限制（快模型和深模型需要不同策略）
- 不加阻塞性审查 gate（不增加延迟）
- 可以用多个 scout 并行（不考虑成本）
- 方案要轻量、可渐进落地

### 调研发现

| 来源 | 关键发现 |
|------|----------|
| Devin | review agent 无共享上下文，平均每 PR 2 bug；但核心是模型能力 × 架构隔离 |
| SWE-Agent 研究 | 差计划比没计划更糟；计划质量 > 计划存在 |
| OpenSpec | 5 个并行 critic agent，GO/REVISE/STOP 投票 |
| AgenTeam | 强制对抗性审查 gate，任务不通过不能完成 |
| 现有 skill 体系 | 81 个 skill，但所有审查都是同质的（同模型同上下文） |
| Scout-4 反证 | "轻量审查"和"发现深层问题"可能不兼容；问题在调研阶段不在审查阶段 |

## 核心洞察

**问题不在审查，在调研深度。** mimo 的失败发生在读代码阶段，不是写计划阶段。如果读得够深，计划自然不会错。

解法：**用并行 scout 的宽度换单点深度的不足。**

---

## 方案设计

### 机制一：调研 Scout（弥补深度）

对计划中每个"要修改/删除的函数"，派一个独立 scout 子代理完成三件事：

1. **grep 所有调用者** — 谁依赖这个函数？
2. **读注释和 commit message** — 它为什么存在？解决了什么问题？
3. **边缘情况搜索** — 如果删除/修改它，有没有只有它在处理的边缘情况？

Scout prompt 模板：
```
读 [函数名] 在 [文件路径] 的实现。回答三个问题：
1. 谁调用了它？（grep 调用者，列出文件:行号）
2. 它为什么存在？（读函数注释、git log --oneline -5 该文件、相关测试）
3. 如果删除/修改它，有没有边缘情况只有它在处理？

只报告事实，不做推荐。200 字以内。
```

### 机制二：红队假设 Scout（定向攻击）

计划写完后（或调研 scout 返回后），派一个"红队 scout"对计划中的隐含假设发起攻击：

1. **提取假设** — 从计划中找出所有"我假设 X 不需要了"、"我假设 Y 可以删除"的判断
2. **搜索反证** — 对每个假设，在代码中搜索它成立所依赖的前提是否真实
3. **输出攻击报告** — 列出被证伪的假设，或标注"未找到反证"

红队 Scout prompt 模板：
```
以下是一个实施计划的摘要：
[计划中的修改列表和理由]

你的任务是找到这个计划最依赖的隐含假设，然后尝试证伪它们。

对每个假设：
- 在代码中搜索反证（grep 关键词、读相关测试、读 commit message）
- 如果找到反证：报告"假设 X 被证伪，因为 [证据]"
- 如果未找到反证：报告"假设 X 未被证伪（搜索了 [范围]）"

只报告事实。不做推荐。
```

### 触发策略（不一刀切）

| 改动类型 | 调研 Scout | 红队 Scout | 理由 |
|----------|:----------:|:----------:|------|
| 删除函数/文件 | 必须 | 必须 | 最高风险——删除不可逆 |
| 修改函数签名/行为 | 必须 | 可选 | 中等风险——可能破坏调用者 |
| 新增代码 | 不需要 | 不需要 | 低风险——不影响现有代码 |
| 重构（改名/移动） | 1 个 scout 确认调用者 | 不需要 | 低风险但需确认完整性 |

### 模型能力适配

不硬编码"弱模型必须派 scout"。而是：

- **Scout 数量 = 计划中"要删除/修改的函数数量"**
- 强模型如果自己已经做了等价调研（读了调用者、理解了原因），可以在计划中标注"已自行验证"跳过 scout
- 弱模型或不确定时：每个要改的函数一个 scout（并行，不阻塞）

判断标准：如果计划中对某个函数的修改理由只有"不需要了"而没有"因为 X 已经由 Y 处理"，则该函数需要 scout 调研。

## 落地位置

### 改动 1：`writing-plans` SKILL.md 加调研 checklist

在"Step 1: 读取相关代码"后加：

```markdown
### 调研完整性自检

对计划中每个要修改/删除的函数，确认：
- [ ] 已 grep 所有调用者（列出文件:行号）
- [ ] 已理解它为什么存在（读注释/commit message/测试）
- [ ] 已确认删除/修改后边缘情况有人处理

如果无法自行确认，派 scout 子代理调研（每个函数一个 scout，并行）。
```

### 改动 2：`subagent-driven-development` Phase 1 加 scout 调度

在 Phase 1（调研）中，对计划中的"删除/修改"操作自动派 scout：

```markdown
### 1.3 函数影响调研（并行 scout）

对计划中每个要删除或修改行为的函数，派一个 scout 子代理：
- prompt: "读 [函数] 的实现、调用者、注释。回答：为什么存在？删了谁受影响？有没有只有它处理的边缘情况？"
- 并行执行，不阻塞规划
- scout 结果注入 Phase 2（规划）的上下文

### 1.4 红队假设攻击（可选，对删除操作强制）

计划初稿完成后，派一个红队 scout：
- prompt: "从计划中提取隐含假设，搜索反证"
- 如果发现被证伪的假设，标注到计划中
```

### 改动 3：计划文档格式增加"调研背书"章节

在 `writing-plans` 的计划模板中，每个任务的"步骤"前加：

```markdown
**调研背书**：
- `functionA`: 调用者 3 处（file1:L10, file2:L20, file3:L30），存在原因：处理 DeepSeek 重复输出。删除后需要替代方案。
- `functionB`: 无外部调用者，仅内部使用。可安全删除。
```

没有调研背书的"删除"操作，在执行阶段会被标记为"未验证假设"。

## 风险与应对

| 风险 | 应对 |
|------|------|
| Scout 本身也是浅模型，不理解"为什么存在" | Scout prompt 明确要求"读 commit message 和注释"，不只读签名 |
| Scout false positive 率高（报太多不重要的问题） | Phase 3 收集数据后缩小 scope 到只审查"删除"操作 |
| 强模型觉得 scout 多余，浪费时间 | 强模型可以标注"已自行验证"跳过；scout 是并行的不阻塞 |
| 红队 scout 找不到假设（假设提取质量差） | 红队 prompt 给出具体的假设模式（"X 不需要了"、"Y 可以删除"、"Z 没有调用者"） |
