## 第一部分：审查方法论——从"读计划"到"给可执行意见"

### 审查的三个检查层次

**层次一：物理事实验证。** 计划中声称的每个依赖关系、数据来源、调用路径，在代码中是否真实存在。方法：grep 调用方、读数据流、确认字段生命周期。

示例：因果账本计划中说 D-gate 的失败判据"取自 deps.evidence"。审查时发现 tool-pipeline 的 pre-execution 切面没有 access to deps.evidence——这个声称在物理上不成立。指出后执行者重新设计为 pipeline 直接写入 gate state。

**层次二：与现有系统的边界清晰度。** 新机制会不会和已有机制重叠、冲突、或被已有机制静默。方法：逐层比对 phase、触发条件、干预手段。

示例：advisory lifecycle 计划中"阶段抑制"的描述是"momentum 高时抑制非紧急投递"。审查时发现 reasoning spiral guard（我们自己的缺口④）的触发条件恰好是 no-tool + low momentum——阶段抑制如果实现不当会把 spiral guard 误杀。建议 category 白名单方案后被采纳。

**层次三：概念完整性。** 方案中的抽象是否自洽。关键检查点：同一概念在不同组件中是否含义一致、命名是否对后续读者有误导性。这个层次最容易在"看着合理"的文本下滑过。

### 给出审查意见的格式约定

执行层反馈表明以下格式能最大化可操作性：

1. **每个问题标注精确的代码/数据流位置**（文件:行号 或 数据流向描述），不给模糊建议
2. **区分"必须修正"（blocker）和"建议补充"（nice-to-have）**，避免审查意见被等价处理
3. **如果方案本身正确但有一个更优方向，指出差异和理由后按正确方向推进**——不等确认，除非涉及方向性变更
4. **计划中没有但值得做的补充，标注为"可选扩展"**——给执行者判断是否纳入 scope 的空间

## 第二部分：落地方法论——从"审查意见"到"高质量代码"的推理链

### 执行层面对审查意见的标准处理流程

基于两轮落地的观察，执行者面对天枢的审查意见时，遵循了以下推理链路：

**Step 1: 不直接实现建议，先反推"为什么这有问题"。**
天枢说"加一个共享标志"。执行者反推：pipeline 本身就有 write 点（两处 trackVerification），不需要"加标志"，需要的是"让 pipeline 成为唯一写入者"。结果不是加 flag，是重画了数据流。

**Step 2: 回到工具的行为模型验证信号。**
天枢方案说 dead-end 信号是"edit 连续失败（failureClass: type_error）"。执行者核查后发现 edit_file 工具几乎不会失败——写盘成功但语义错误挂在验证阶段。信号改为"edit → verify fail → edit → verify fail 循环 ≥2 次"。

**Step 3: 用数据追踪校验阈值。**
天枢方案说 intent-anchor 在"会话超过 20 轮"时触发。执行者追踪 `initialUserMessage` 的赋值和重置路径，发现它在 `turn-step-producer` 中每次 run 重置——session 级 turn 计数在连续 run 中永远达不到 20。修正为 run 级 `getRunTurn()`。

**Step 4: 按上下游需求做接线点定位。**
天枢方案说 output-sanitizer 在 tool-pipeline 返回后、addToolResults 之前。执行者发现正确边界在 `tool-execution.ts`：UI 回调在此之前已收到全文（保真），session 只存裁剪版。且必须排在 `classifyFailure` 之后——它需要原始 stack trace。

**Step 5: 寻找方案覆盖的盲区，主动补缺。**
天枢方案提出三个缺口（死路、裁剪、锚点），执行者发现第四个：maxTurns 耗尽时 model 无感知。补了 turn-budget-hook，带 expect 谓词直接对接 holdout lift。

### 工程执行惯例

- **纯函数核心 + 薄接线层**：每个组件都是 closure-based state + 接口方法，零类继承
- **共享依赖显式提取**：`GIT_CLEAR_RE` 从 hook 迁到 `destructive-patterns.ts`，两个消费者从同一源头 import
- **测试先行但务实**：每个组件独立测试文件，RNG 可注入。环境受阻时不弱化测试——测试仍然写，能跑的环境会绿
- **code-as-design-doc**：注释不解释"做了什么"（代码自说明），解释"为什么这样设计"+"审查意见来源"+"数据流决策"
- **delta 驱动增量合并**：efficacy store 的 `mergeAndSave` 要求调用方传递自上次 flush 以来的增量——防重复提交

## 第三部分：协作分工模型——角色 × 星域

### 角色与星域解耦

协作中有三个**角色**：规划（发现盲区、描述问题空间、出方案骨架）、审查（三层检查、给可操作意见、反审 commits）、执行（信号精炼、数据流追踪、接线落地、主动补盲区）。角色不与星域一一绑定——历史会话中审查方恰好是天枢、执行方恰好是瑶光，但每个星域承接的是**角色组合**，映射如下。

### 四域分工模型

| 星域 | 角色组合 | 定位 |
|------|---------|------|
| **天枢** | 规划 + 审查 + 执行 + 协调 | 默认域，全能。任务性质模糊、跨阶段、或需要全局统筹时的缺省选择 |
| **天权** | 规划 + 审查（重） | 规划审查专精，**交付物是计划**。方案称量、架构审查、出可执行计划文档 |
| **瑶光** | 规划 + 执行（带验证底色） | 规划层 + 执行的完整闭环：调研→计划→执行→验证→文档→提交，复现纪律内建于每一步 |
| **天梁** | 执行（纯） | 推荐执行域。拿成熟计划做翻译式落地，节奏分波、验证过门 |

**天枢（默认全能域）**：既能出方案骨架也能亲手落地——规划、编码、验证、委派皆在能力半径内，委派是全局决策的选择而非身份边界。承接一切未被专域认领的任务；在多域协作中是路由者和最终整合点。

**天权（规划审查域）**：审查的三个检查层次（物理事实验证/边界清晰度/概念完整性，见第一部分）是天权的核心方法。它的产出不止于审查意见——终点是**可执行的计划文档**：精确到文件:行号的引用、blocker 与 nice-to-have 分级、每条改动写清"当前→改后→为何安全"。出计划不出代码。

**瑶光（规划+执行域）**：本文档第二部分的落地方法论（Step 1-5）在历史会话中由瑶光实践。特点是规划与执行同体：先围绕任务调研成形计划（引用到代码物理位置），执行后用自己的复现纪律验自己的交付——绿非证明、失败归属基线（模式 F）、度量消费闭环（模式 G）都是执行的内建环节而非事后审查。适合"计划和落地质量都要硬"的任务。

**天梁（纯执行域）**：计划到手时设计决策已闭环，工作是翻译不是重新设计。分波执行、每波验证过门、测试与源码同交付。适合计划成熟度高、需要稳定节奏批量落地的任务。

### 路由建议

- 出方案/审计划/称架构 → 天权
- 按成熟计划批量落地 → 天梁
- 调研+计划+落地一体、或交付质量存疑需要复现验证 → 瑶光
- 说不清属于哪类、需要跨阶段推进或全局协调 → 天枢（默认）

### 协作原则

1. **审查意见 ≠ 实现指令。** 执行者有权质疑方案的物理可行性，并给出更精确的信号设计。
2. **执行自主权有边界。** 信号精炼、接线点定位、阈值可达性校准是执行层的自主权（只要解决的是同一个缺口），不需要规划方批准；**改变方案方向或目标**的决策才回退请求修订。
3. **规划方的反审（review commits）是闭环。** 审查方案 → 执行者落地 → 规划方审查代码 → 从中学习并改进未来的方案质量。
4. **共享文档作为协作锚点。** 方案文档不是一次性交付物——它记录了"为什么提出这些缺口""当初认为信号应该是什么"，执行者的 diff 对照它形成可追溯的演进链。
5. **执行者在代码中显式标注审查来源和决策理由**，让后续读者可追溯（code-as-design-doc，见第二部分工程惯例）。

## 第四部分：二轮落地中提炼的可复用模式

### 模式 A：单一事实来源（Single Source of Truth）

出现位置：GIT_CLEAR_RE（destructive-patterns.ts）、验证失败状态（pipeline 写/gate 读）。

原则：任何被多个消费者引用的判据/正则/状态，必须显式提取到独立模块。不允许"从 hook 文件导入到 tool-pipeline"——这会创建反向依赖。

### 模式 B：数据流重设计 > 加配置

出现位置：D-gate 的 `noteVerification` 替代"共享标志"。

原则：当方案说"加一个共享标志让 X 和 Y 通信"时，先问"X 有没有现成的写入点？Y 和 X 的关系是否可以反过来？"。通常结果是删除中间层而非增加它。

### 模式 C：信号从工具行为模型推导，不从 prompt 描述推导

出现位置：dead-end 信号从 failureClass → edit→verify 循环。

原则：prompt 描述的是期望行为，工具行为模型描述的是物理事实。如果 prompt 说"edit 会失败"但工具实现中 edit 从来不报 failure，那信号必须改。

### 模式 D：阈值的工程可达性验证

出现位置：intent-anchor 从 session turn → run turn。

原则：方案中任何"超过 N 轮"的阈值，必须先追踪相关字段的赋值、重置、生命周期。不做这一步的阈值是拍脑袋。

### 模式 E：接线点按上下游需求定位

出现位置：output-sanitizer 从 tool-pipeline → tool-execution。

原则：插入裁剪/变换的点，必须先列出它之前和之后的消费者分别需要什么。之前的消费者可能需要原始数据（failure classifier），之后的消费者只需要摘要（session history）。

### 模式 F：共享工作区的失败归属基线

出现位置：全量测试 38 失败排查、loop-factory 4 失败判别、cockpit state.test 的 `getSessionDomain` 缺 mock（三次独立实战）。

原则：本仓库常有并发 agent 会话共改工作区，"我改完后红了"≠"我改红的"。任何验证失败先用 `git stash` / 独立 worktree 在基线上跑**同一用例**，分清失败归属再动手。归属他人的失败只在两种情况下顺手修：它阻塞你自己的新测试（如共享 mock helper），或修复成本一行以内——修了要在交付报告里显式声明"顺手修复预存失败"。绝不用 stash/reset 清场来骗过验证（这是该纪律的堕落形态）。

### 模式 G：度量必须有消费方

出现位置：`getLift()` 实现即闲置（因果账本落地后遗留）、`setStatusSink()` 只有测试在用（dark cockpit）——两者由 lift 消费端专轮补齐。

原则：度量了不消费等于没度量，零消费方 = 死接线——对 advisory/hook/遥测与对 export 同样成立。新度量落地时要么同步规划消费端（哪个决策点吃这个数字），要么在设计文档显式标注"遗留尾巴"并排期。审查计划时把"这个数字谁在读"列为常规检查项。

### 模式 H：新机制出生即可测

出现位置：turn-budget-hook（expect `verify_attempted`）、dead-end-detector（expect `tool_appears`）从第一天进 holdout lift 与跨会话效能信息素。

原则：新 advisory/hook 出生就带 expect 谓词——投出去的每条提醒能核销采纳/忽略，自动接入反事实度量，未来的静音/排序决策有据可依。反面纪律同样重要：无行为签名的机制（intent-anchor 的意图重锚没有可观测的"采纳动作"）诚实地不带 expect，只计送达——发明伪谓词会污染核销数据，比没有度量更糟。

### 模式 I：负反馈回路必须带翻案路径

出现位置：负 lift 静音的 probation 机制（期满放行一次收集新证据，之后 lift 仍 ≤0 才再静音）。

原则：当负反馈（静音/降级/拉黑）的判定输入更新缓慢时（如跨会话先验），裸的负反馈会自锁——被静音的对象失去产生新数据的机会，误判永远无法翻案。任何这类回路必须内置数据刷新口：probation 放行、EWMA 衰减、定期重评之一。设计时问一句：如果这次判定是错的，系统靠什么发现？
