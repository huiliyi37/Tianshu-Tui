# Rivet 3.0 高可靠高可用架构设计

> 日期：2026-05-20
> 方法：Deep Brainstorm (7 scout + 3 轮演化)
> 调研范围：Rivet 代码审计 + 航空航天/核电/医疗 + 游戏引擎 + 数据库引擎 + 终端渲染 + 可观测性
> 核心洞察：不缺系统，缺 sensor 和连接线。recovery-trigger 是大脑但没有眼睛（内存/磁盘 sensor）、没有手（降级执行器）、没有记忆（crash breadcrumb）。

---

## 架构理念

**不新建框架，补已有闭环的缺失环节。**

已有闭环：`PressureMonitor`（感知）→ `recovery-trigger`（决策）→ `fluency-policy`（展示）

缺失环节：
1. **眼睛**：内存 RSS 和磁盘 JSONL 增量没有 sensor
2. **手**：recovery-trigger 只输出 `suggestedActions`，不自动执行降级
3. **记忆**：crash/恢复时没有诊断面包屑
4. **体检**：没有启动时和运行时健康自检
5. **已知 bug**：6 个代码级风险未修复

## 跨领域模式精选（6 个领域 → 15 个可迁移模式）

### 航空航天（Scout 2）

| 模式 | 来源 | 迁移方案 |
|------|------|---------|
| **降级阶梯** | Airbus FBW Normal→Alternate→Direct | recovery-trigger 扩展三级：full（全 tool）→ degraded（禁高风险 tool）→ minimal（只读+文本） |
| **窗口看门狗** | Spacecraft ESA LEON | 每个 tool call 设窗口超时（下限 200ms 防空转，上限 120s 防卡死），独立于 doom loop |
| **面包屑诊断** | Chandra 望远镜 DPA | recovery-trigger 触发时 dump 最后 3 个 tool call + API 状态码 + RSS + turn count 到 `~/.rivet/breadcrumbs/` |
| **状态同步恢复** | Mosh 协议 | SSE 断连重连只同步最新 assistant message offset，不重放 delta |

### 游戏引擎（Scout 4）

| 模式 | 来源 | 迁移方案 |
|------|------|---------|
| **脏标记优化** | Unity dirty flag | TUI 组件（chat/status/tool/summary）标记 dirty，只重渲 dirty 子树 |
| **对象池** | Unity/Godot projectile pool | 预分配 message chunk buffer 和 tool result wrapper，reset 复用 |
| **双缓冲** | Teeworlds front/back buffer | SSE tokens 积累到 back buffer，turn-complete 或 batch tick 时原子 swap |
| **固定节拍+可变渲染** | MonoGame fixed timestep | token 处理按实际速率，TUI 刷新固定 15-20fps，解耦 |
| **轮转快照恢复** | Unreal Recovery Hub | 每 5 turn 或 30s 滚动保存 session 快照（最多 N 个），OOM/SIGKILL 后恢复 |

### 数据库引擎（Scout 5）

| 模式 | 来源 | 迁移方案 |
|------|------|---------|
| **WAL Checkpoint + Truncate** | PostgreSQL | claim-store 定期 snapshot → truncate JSONL，恢复 = load snapshot + replay 增量 |
| **双文件 Base+Incr** | Redis 7.0 Multi-Part AOF | session 持久化拆为 `session.base.json` + `session.incr.jsonl`，compact = merge incr into new base |
| **LFU 时间衰减** | Redis 4.0 | claim fitness 乘 `exp(-λ * age)`，未被访问的 claim 自然衰减 |
| **原子 Temp+Rename** | PostgreSQL/SQLite | 任何批量写：write temp → fsync → rename → fsync dir |

### 终端渲染（Scout 3）

| 模式 | 来源 | 迁移方案 |
|------|------|---------|
| **输出背压保护** | Node.js Writable | SSE 写 stdout 前检查 `write() === false`，暂停消费直到 drain |
| **滚动虚拟化** | react-window | 超 500 行 assistant 回复只渲 viewport，溢出存 ring buffer |

### 可观测性（Scout 6）

| 模式 | 来源 | 迁移方案 |
|------|------|---------|
| **内存趋势回归** | MemWatchdog | 每 60s 采样 heapUsed，线性回归斜率超阈值 → 触发 auto-compact + 告警 |
| **健康自检** | canary pattern | `rivet doctor`：Node 版本 + API key + 网络 + 磁盘 + 依赖完整性 |
| **结构化 crash 报告** | OTLP local | OOM/uncaughtException 时序列化 session 状态 + `--heapsnapshot-near-heap-limit=2` |

## 三轮演化结论

### 灭绝

- **V1 三层预算框架** — 60% 与已有机制重叠，帧预算对终端无意义，Node.js 单线程不能抢占中断

### 存活合并

V2（sensor 补盲）+ V3（降级阶梯+checkpoint）+ V4（watchdog+breadcrumb）合并为统一方案：

**"给 recovery-trigger 长眼睛、长手、长记忆"**

```
新增 sensor ──────→ recovery-trigger ──────→ 降级执行器
(memory RSS,          (已有 4 类触发 +         (新增：自动执行
 JSONL size,           新增 memory/disk)         full→degraded→minimal)
 event loop lag)                                         │
                                                         ↓
crash breadcrumb ← ← ← ← ← ← ← ← ← ← fluency-policy 展示
(~/.rivet/breadcrumbs/)                   (已有 4 级可见性)
```

## 实施路径

### Phase 1（1 周）：修 bug + 补 sensor

**修 6 个已知 bug**（Scout 1）：
- `lwt-guard.ts`：writeSync(fd, pid) 写入同一 fd
- `log-state.ts`：immutable update 替代 push/splice
- `client.ts`：finally 统一 clearTimeout
- `block-stream-writer.ts`：maxBufferSize 硬上限（如 64KB）
- `lwt-guard.ts`：SIGINT emit event 替代 process.exit(0)
- `session-persist.ts`：per-message size cap（如 100KB）

**补 2 个 sensor**：
- Memory sensor：postTurn hook 中 `process.memoryUsage()`，每 60s 采样，线性回归检测趋势
- Disk sensor：session-persist 写入后检查文件大小，超阈值触发 recovery-trigger

**成功标准**：6 个 bug 全部修复 + memory sensor 能检测到模拟的内存泄漏 + disk sensor 能检测到 >50MB JSONL
**退出条件**：任何修复引入新测试失败

### Phase 2（1 周）：降级阶梯 + 持久化升级

**降级执行器**（扩展 recovery-trigger）：
- `full`：全部 tool 可用，正常运行
- `degraded`：禁用 bash write 类 + force push 等高风险 tool，告警用户
- `minimal`：只保留 read_file + 文本回复，建议用户 /compact 或重启

**触发规则**：
- memory RSS > 70% of --max-old-space-size → degraded
- memory RSS > 85% → minimal + auto-compact
- doom_loop_blocked → degraded
- API 连续 5 次 5xx → degraded（circuit breaker half-open）

**持久化升级**（数据库模式）：
- claim-store：checkpoint + truncate（snapshot + 增量 JSONL）
- session-persist：双文件 base+incr（compact = merge incr into new base）
- 原子写：所有批量写用 temp+rename+fsync

**成功标准**：模拟 memory 超阈值时自动降级到 degraded + claim-store checkpoint 缩短恢复时间 >50%
**退出条件**：降级误触发率 >5%

### Phase 3（1 周）：watchdog + breadcrumb + 自检

**窗口看门狗**：
- 每个 tool call：下限 200ms（防空转）+ 上限 120s（防卡死）
- SSE stream：5s 无新 token → 检查连接，30s 无新 token → 断连重连
- Event loop lag 检测：setTimeout 延迟 >2s → 告警

**面包屑诊断**：
- recovery-trigger 每次触发 dump：最后 3 个 tool call 摘要 + API 状态码 + RSS + turn count + event loop lag
- 写入 `~/.rivet/breadcrumbs/{timestamp}.json`，保留最近 20 个
- OOM 时用 `--heapsnapshot-near-heap-limit=2` 自动抓 heap snapshot

**健康自检**：
- `rivet doctor`：Node ≥22 + API key valid + 网络通 + 磁盘 >100MB 可用 + 依赖完整
- 启动时自动运行精简版（只检查致命项），完整版按需

**轮转快照**：
- 每 5 turn 或 30s 保存 session 快照（最多保留 5 个）
- OOM/SIGKILL 后检测 stale session，提示 `--resume`

**成功标准**：watchdog 能检测到模拟卡死 + breadcrumb 记录完整 + rivet doctor 覆盖所有致命检查项
**退出条件**：watchdog 误报率 >10%

## 渲染可靠性专项（基于 Scout 3 发现）

| Ink 6 风险 | 严重度 | 修复方案 |
|-----------|--------|---------|
| 全量历史重渲染 | P1 | React.memo 包裹聊天条目 + rolling window 只渲最后 N 行 |
| clearTerminal 黑闪 | P1 | 控制渲染行数 < stdout.rows 或使用 alternate screen buffer |
| Timer/Listener 泄漏 | P1 | useEffect cleanup 统一 clearTimeout/removeListener + AbortController |
| Yoga layout 瓶颈 | P2 | maxFps 降至 15-20 + 多 token 批量拼接后单次 setState |
| Synchronized Updates 不完整 | P2 | 确认 Ink ≥6.7.0 + 检测终端兼容性 fallback |
| 输出背压 | P2 | stdout.write() 返回 false 时暂停 SSE 消费，等 drain |

## 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 降级误触发（正常操作被判为异常） | 中 | 高 | 降级前要求连续 N 次（非单次）超阈值；用户可 override |
| memory sensor 采样增加 GC 压力 | 低 | 低 | 60s 间隔足够稀疏，单次 memoryUsage() < 1ms |
| checkpoint 写入时 session 并发修改 | 中 | 中 | 用 incremental projection 的 snapshotVersion 做一致性快照 |
| watchdog 在 compact 期间误判卡死 | 中 | 中 | compact 期间暂停 watchdog（或延长 timeout 到 300s） |
| 双文件持久化增加启动复杂度 | 低 | 低 | 回退策略：base 损坏时 fallback 到纯 incr 重建 |
