## 一、两级团队模式

### 经济模型：为什么这个架构成立

```
主控会话（v4-pro）
  ├── 规划、设计、审查 — 高缓存命中率，成本极低
  ├── 不做执行 — 不消耗无效上下文
  └── 缓存持续累积 — 每轮规划的 prefix 越来越长、命中越来越高

天梁 worker（flash）
  ├── 精准执行 — 不需要思考"该不该做"，只需要做
  ├── 成本极低 — flash 定价
  └── 质量不降 — flash 执行能力 >= 深度思考模型（因为不需要思考）
```

**核心洞察**：把"思考"和"执行"分离到不同模型，不是降级，是专业化。
- v4-pro 擅长规划、审查、架构决策 — 让它专心做这些
- flash 擅长精准执行 — 给它清晰的 spec，它比深度思考模型更快更准
- 主控会话的高缓存进一步压低了规划成本

### `/team` — 标准模式

用户已有完善计划文档（或任务描述足够清晰），只需执行。

```
用户输入 + 计划文档（/team 触发）
  │
  ▼
┌──────────────────────────────────────────────┐
│  主控（v4-pro）：任务拆分 + 并行编排              │
│                                               │
│  解析用户计划 → 拆分为 T1-TN 任务组              │
│  判断并行分组：G1{T1-T3}, G2{T4-T8}, ...        │
│  创建 WorkOrder → 派发天梁 worker               │
│                                               │
│  主控继续待命：审查中间结果、处理异常            │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  天梁并行执行（flash）                          │
│                                               │
│  天梁-1 ← T1, T2, T3                          │
│  天梁-2 ← T4, T5, T6, T7, T8                  │
│                                               │
│  按计划精确交付，不多不少                        │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  主控（v4-pro）：审查验收                        │
│                                               │
│  审查所有 commits + 全量测试 + 架构一致性        │
└──────────────────────────────────────────────┘
```

**适用场景**：
- 用户已经写好了完整的计划文档（如 loop-split-v3.md）
- 任务描述足够清晰，不需要多视角规划
- 典型用法：`/team 按 docs/superpowers/plans/xxx.md 执行`

### `/team max` — 能力最大化模式

从零开始的多视角规划 + 执行 + 审查全流程。

```
用户输入任务（/team max 触发）
  │
  ▼
┌──────────────────────────────────────────────┐
│  Phase 1: 多视角规划（并行 worker）             │
│                                               │
│  天权 worker → 依赖分析、任务拆解、执行顺序     │
│  天府 worker → 风险评估、ROI 审计、验证标准     │
│  天璇 worker → 创意探索、定向反证、盲区发现     │
│                                               │
│  主控汇总 → 输出 unified_plan（T1-TN 任务列表） │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  Phase 2: 精准执行（并行天梁 worker）           │
│                                               │
│  天梁-1 ← T1, T2, T3                          │
│  天梁-2 ← T4, T5, T6, T7, T8                  │
│  天梁-N ← ...                                  │
│                                               │
│  天梁 = flash，按计划精确交付                   │
│  不多不少，规划文档怎么写就怎么做               │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  Phase 3: 主控审查                              │
│                                               │
│  审查所有 commits + 全量测试 + 文档收束         │
└──────────────────────────────────────────────┘
```

**适用场景**：
- 新功能设计，没有现成计划
- 复杂重构，需要多视角评估风险
- 探索性任务，方向不明确

### 两级对比

| 维度 | `/team` | `/team max` |
|------|---------|-------------|
| 规划 | 主控直接拆分 | 天权+天府+天璇并行 worker 规划，主控汇总 |
| 输入 | 计划文档 + 用户任务 | 仅用户任务描述 |
| 执行 | 天梁 flash（相同） | 天梁 flash（相同） |
| 审查 | 主控 v4-pro | 主控 v4-pro |
| API 成本 | 极低（主控缓存 + flash 执行） | 低（3 次规划 worker + 主控缓存 + flash 执行） |
| 适用场景 | 有现成计划，需要执行 | 从零开始的设计任务 |
| 对应 loop-split 实战 | Step 6a-6f（天梁按计划执行） | Task 1-5 + Step 6a-6f 全流程 |

### 核心原则（两级通用）

1. **用户主动触发**：通过 `/team` 或 `/team max` 命令，不是自动判断
2. **主控（v4-pro）只做规划和审查**：不执行，保持缓存高命中率，上下文干净
3. **天梁（flash）只做执行**：给清晰的 spec，精准交付，成本极低
4. **规划是关键**：天梁做不好是规划的问题，不是天梁的问题
5. **任务级拆分**：T1-T16 的逻辑单元，不是文件级
6. **质量不降级**：思考与执行分离是专业化，不是降级

## 五、与之前设计的对齐

### 领航星在本次讨论中明确的新约束

1. **用户主动触发**：`/team` 命令，不是天枢自动判断
2. **天枢决定分组并行数**：根据任务复杂度
3. **天梁是 flash**：低成本精准执行，规划文档就是规格
4. **任务级拆分**：T1-T16 的逻辑单元，不是文件级
5. **不做文件级拆分**：现有规划文档怎么出就怎么执行

### 与 2026-06-04 设计的差异

| 维度 | 2026-06-04 设计 | 本次讨论补充 |
|------|----------------|-------------|
| 触发方式 | 主 agent 判断是否需要团队 | 用户 `/team` 主动触发 |
| 拆分粒度 | 未明确（隐含文件→域） | **任务级**（T1-TN 逻辑单元） |
| 天梁模型 | 未指定 | **Flash 模型**（低成本精准执行） |
| 天梁定位 | executor worker | 精准执行者，做不好是规划的问题 |
| 规划方式 | 3 个 planner 并行 | 天枢/天权/天府/天璇 多视角 |

## 八、验收环节设计：基于 Review Squadron 实战

### 实战基线

2026-06-06 的 server 子系统审查验证了多视角审查的价值：

- **三轮审查**：R1 抓 18 个缺陷，R2 抓假修复，R3 抓回归 + 谎报验证
- **审查方法**：主控通读全量 + 3-4 个专精 Inspector 并行（Security/Lifecycle/DataFlow/Silence）
- **发现分布**：2C + 6H + 6M + 4L = 22 个，全部代码级可验证
- **核心结论**：单一 agent 串行实现时"功能正确性"占据全部注意力，安全/并发/失败模式被挤占

### 天权视角代入

天权在 `/team` 验收中的角色 = Review Squadron 的 **Commander**：

| 天权职责 | 对应 Squadron 能力 | 在 loop-split 中的体现 |
|---------|-------------------|----------------------|
| 通读所有变更 diff | Commander 全量审查 | 天府写出 `_runInner` 控制流地图（逐段标注行号、控制流约束） |
| 交叉验证 spec vs 代码 | spec→code 一致性 | 对照 v3 计划的 Task 1-5 逐项验证 |
| 委派专精 Inspector | delegate_batch | 派 Security/Lifecycle/DataFlow/Silence 并行审查 |
| 汇总 + 去重 + 分级 | 聚合策略 | 输出结构化审查报告（C/H/M/L 分级） |

天权的核心能力不是"自己审查所有代码"，而是**编排审查并验证 spec 承诺是否兑现**。

### 天府视角代入

天府在 `/team` 验收中的角色 = Review Squadron 的 **Lifecycle + DataFlow Inspector**：

| 天府职责 | 对应 Inspector 专长 | 在 loop-split 中的体现 |
|---------|-------------------|----------------------|
| 状态机/并发正确性 | Lifecycle Inspector | 控制流地图标注 9× return + 4× continue |
| 数据流完整性 | DataFlow Inspector | 发现 loop-factory.ts 伪提取（耦合未降低） |
| 接口隔离验证 | DataFlow Inspector | P1 问题：37 个 private 移除范围过大 |
| 既有测试覆盖 | Regression 检查 | 验证 34/34 测试通过，无回归 |

天府的核心能力是**追数据流、查边界、守不变量**——这正是 Inspector 的专长。

### 验收工作流设计

```
天梁执行完成
  │
  ▼
┌──────────────────────────────────────────────┐
│  天权（Commander）                              │
│                                               │
│  1. 收集所有天梁 worker 的 diff                 │
│  2. 对照计划文档验证：每个 Task 是否完成         │
│  3. 识别需要专精审查的维度                      │
│  4. 委派 Inspector：                            │
│     - 安全（网络暴露、鉴权）                    │
│     - 生命周期（竞态、状态机）                  │
│     - 数据流（参数传递链、持久化）              │
│     - 静默吞错（空 catch）                     │
│  5. 汇总发现，输出审查报告                      │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  天府（Inspector + 守藏者）                     │
│                                               │
│  重点维度：                                    │
│  - 控制流正确性（return/continue 映射）        │
│  - 接口边界（public/private 暴露面）           │
│  - 既有测试回归                                │
│  - 数据流完整性                                │
│                                               │
│  输出：发现列表 + 验证结果                     │
└──────────────────────────────────────────────┘
  │
  ▼
┌──────────────────────────────────────────────┐
│  主控（v4-pro）闭环                             │
│                                               │
│  - 审查发现 → 需修复? → 派天梁修复 → 再审查    │
│  - 闭环有界（maxRounds=3）                     │
│  - 超过 maxRounds → 升级给用户决策             │
└──────────────────────────────────────────────┘
```

### 审查分级（继承 review-discipline 路由表）

| 档位 | 触发条件 | 审查工作流 | 成本 |
|------|---------|-----------|------|
| **L3 Squadron** | 新子系统 / ≥4 文件 / 跨模块 | 天权指挥 + 4 Inspector 并行 | 高 |
| **L2 单对抗** | 单/双文件修复 / fix 类提交 | 1 个 adversarial_verifier | 低 |
| **L1 nudge** | 微改（常量/文档/格式） | 仅提示词纪律，不派代理 | 零 |

### 关键约束

1. **审查者 ≠ 实现者**（纪律 1）— 天梁执行，天权/天府审查，不可同上下文自我审批
2. **修复后必须复审**（自动闭环）— 修复 spawn 天梁，复审 spawn 天权/天府
3. **"测试全过"须附证据**（纪律 4）— 命令 + 输出，不是自我断言
4. **改 X 必跑覆盖 X 的既有测试**（纪律 3）— 防止 H4 类相邻回归
