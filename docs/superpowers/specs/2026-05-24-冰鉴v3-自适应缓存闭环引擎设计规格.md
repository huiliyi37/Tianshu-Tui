# 冰鉴 v3 — 自适应缓存闭环引擎设计规格

> 日期：2026-05-24
> 前置：冰鉴 v2 完成（双区布局 + 习惯化追踪 + 指纹漂移检测 + Artifact Log）
> 来源：6 scout 并行调研（cache 遥测、多 provider、消息布局、外部研究、生物类比、经济学）
> 核心洞察：遥测数据丰富但没有闭环反馈 — 诊断结果无人消费来做决策

---

## 背景

冰鉴 v2 解决了 prefix cache 命中率问题（从 ~5% 到 70-85%），但系统仍然是"开环"的：

```
[收集 metrics] → [诊断 miss 原因] → [显示给用户] → 结束
```

v3 的目标是闭合这条链路：

```
[收集 metrics] → [诊断] → [决策引擎] → [执行调整] → [验证效果] → [循环]
```

同时，将 cache 优化从 DeepSeek-only 扩展到所有 provider（GLM、Kimi、MiniMax、Mimo）。

---

## 设计原则

来自 6 个领域的跨学科启发：

1. **竞争选择 + 分级持久化**（免疫系统）— 上下文段通过证明复用价值赢得 cache 驻留权
2. **注意力释放是目的**（神经习惯化）— prefix cache 释放模型注意力给新内容
3. **最小化失效范围**（MESI 协议）— 永不修改 Shared 段，隔离 mutation
4. **自调优 recency/frequency**（ARC 算法）— ghost 元数据驱动策略自适应
5. **流量比例强化**（黏菌网络）— 按实际使用比例强化路径，压力下重组
6. **预测性预取**（CPU/CDN）— 从工具调用序列预测下一步需要的上下文

## 模块一：Cache Feedback Loop（闭环反馈）

### 1.1 Ghost Entry Registry

当 compact 或 stale-round 截断/删除一个 tool_result 后，保留其元数据：

```typescript
interface GhostEntry {
  artifactId: string
  tool: string
  target: string
  evictedAtTurn: number
  originalTokens: number
  accessedAfterEviction: number  // 被 read_section 重新访问的次数
}

interface GhostRegistry {
  record(entry: Omit<GhostEntry, 'accessedAfterEviction'>): void
  markAccessed(artifactId: string): void
  getRecentGhostHits(withinTurns: number): GhostEntry[]
  getEvictionEfficiency(): number  // 0-1, 高 = 驱逐的都不需要
}
```

**反馈信号：**
- Ghost hit（被驱逐后 3 turn 内被 read_section 重新访问）→ 驱逐过于激进
- Ghost miss（被驱逐后从未被重新访问）→ 驱逐策略正确

**消费者：** `AdaptiveThresholdController`（见 1.3）

### 1.2 Cache Hit Rate → Compact 策略滑动

当前 `cache-preserving` 策略的阈值是硬编码的。新设计让阈值随 cache hit rate 滑动：

```typescript
interface AdaptiveCompactRatios {
  watch: number
  compact: number
  reactive: number
}

function adaptiveThresholds(
  baseStrategy: CompactStrategy,
  recentHitRate: number,  // getRecentTurnHitRate(5)
): AdaptiveCompactRatios {
  const base = STRATEGY_RATIOS[baseStrategy]

  if (recentHitRate >= 0.85) {
    // Cache 健康 — 延迟 compact 保护 prefix
    return {
      watch: Math.min(base.watch + 0.05, 0.90),
      compact: Math.min(base.compact + 0.03, 0.93),
      reactive: Math.min(base.reactive + 0.02, 0.95),
    }
  }
  if (recentHitRate < 0.3) {
    // Cache 已崩 — compact 不会更差，可以更激进
    return {
      watch: Math.max(base.watch - 0.10, 0.40),
      compact: Math.max(base.compact - 0.08, 0.60),
      reactive: Math.max(base.reactive - 0.05, 0.75),
    }
  }
  return base
}
```

**集成点：** `decideCompactTier()` 调用 `adaptiveThresholds()` 替代硬编码 `STRATEGY_RATIOS`。

### 1.3 Adaptive Threshold Controller

根据 ghost hits 和 cache hit rate 动态调整 artifact intercept 阈值：

```typescript
interface ThresholdState {
  artifactThreshold: number       // 当前成功结果阈值（默认 800）
  artifactErrorThreshold: number  // 当前错误结果阈值（默认 1600）
  stalePreviewChars: number       // stale-round 截断阈值（默认 1200）
}

class AdaptiveThresholdController {
  private ghostRegistry: GhostRegistry
  private state: ThresholdState

  /**
   * 每 turn 结束后调用，根据反馈调整阈值
   */
  adjust(cacheHitRate: number, turnsSinceLastCompact: number): ThresholdState {
    const ghostEfficiency = this.ghostRegistry.getEvictionEfficiency()
    const recentGhostHits = this.ghostRegistry.getRecentGhostHits(3)

    // 经济学规则：cache hit rate 高 → inline 便宜 → 提高阈值
    if (cacheHitRate >= 0.8) {
      this.state.artifactThreshold = Math.min(this.state.artifactThreshold + 100, 2000)
    } else if (cacheHitRate < 0.3) {
      this.state.artifactThreshold = Math.max(this.state.artifactThreshold - 100, 400)
    }

    // Ghost hit 反馈：驱逐的内容被重新请求 → 阈值太低
    if (recentGhostHits.length >= 2) {
      this.state.artifactThreshold = Math.min(this.state.artifactThreshold + 200, 2000)
      this.state.stalePreviewChars = Math.min(this.state.stalePreviewChars + 400, 2400)
    }

    // Ghost efficiency 高 → 可以更激进
    if (ghostEfficiency > 0.9 && this.state.artifactThreshold > 600) {
      this.state.artifactThreshold = Math.max(this.state.artifactThreshold - 50, 400)
    }

    return this.state
  }
}
```

### 1.4 Session Warmth Tracker

模拟 provider 的 cache TTL，识别 cache cold 窗口：

```typescript
type CacheTemperature = 'hot' | 'warm' | 'cold'

class SessionWarmthTracker {
  private lastApiCallTime: number = 0
  private observedTtl: number = 3600_000  // 默认 1hr，可通过观察调整

  predict(): CacheTemperature {
    const elapsed = Date.now() - this.lastApiCallTime
    if (elapsed < 60_000) return 'hot'
    if (elapsed < this.observedTtl) return 'warm'
    return 'cold'
  }

  /**
   * Cache cold 时是做 compact/restructure 的最佳时机
   * — 反正 prefix 要重建，不如趁机优化结构
   */
  shouldOpportunisticCompact(): boolean {
    return this.predict() === 'cold'
  }

  recordApiCall(): void {
    this.lastApiCallTime = Date.now()
  }
}
```

**集成点：** 用户离开后回来时（检测到 cold），在第一次 API call 前触发一次 opportunistic compact。

## 模块二：Cache Behavior Discovery（运行时探测）

### 2.1 设计理念

不依赖静态配置判断 provider 是否有 cache。通过观察正常 API response 中的 cache metrics 来发现：

```typescript
interface DiscoveredCacheBehavior {
  hasCache: boolean
  matchingStrategy: 'exact-prefix' | 'partial' | 'unknown'
  observedMinTokens: number | null
  confidence: number  // 0-1，观察次数越多越高
}

class CacheBehaviorLearner {
  private observations: Array<{
    turn: number
    cacheRead: number
    cacheCreation: number
    prefixChanged: boolean  // 这次请求的 prefix 是否与上次不同
  }> = []

  observe(snapshot: TurnCacheSnapshot, prefixChanged: boolean): void {
    this.observations.push({
      turn: this.observations.length,
      cacheRead: snapshot.cacheRead,
      cacheCreation: snapshot.cacheCreation,
      prefixChanged,
    })
  }

  infer(): DiscoveredCacheBehavior {
    if (this.observations.length < 3) {
      return { hasCache: false, matchingStrategy: 'unknown', observedMinTokens: null, confidence: 0 }
    }

    const hasAnyCache = this.observations.some(o => o.cacheRead > 0)
    if (!hasAnyCache) {
      return {
        hasCache: false,
        matchingStrategy: 'unknown',
        observedMinTokens: null,
        confidence: Math.min(this.observations.length / 10, 0.9),
      }
    }

    // 检查 prefix 变化后是否 miss
    const afterChange = this.observations.filter(o => o.prefixChanged)
    const exactPrefix = afterChange.length > 0 && afterChange.every(o => o.cacheRead === 0)

    return {
      hasCache: true,
      matchingStrategy: exactPrefix ? 'exact-prefix' : 'partial',
      observedMinTokens: null,  // 需要更多观察来推断
      confidence: Math.min(this.observations.length / 8, 0.95),
    }
  }
}
```

### 2.2 策略自动升级

当 discovery 发现 provider 有 cache 时，自动升级 compact 策略：

```typescript
function resolveCompactStrategy(
  staticProfile: ProviderProfile,
  discovered: DiscoveredCacheBehavior,
): CompactStrategy {
  // 静态配置优先（如果明确配置了 cache）
  if (staticProfile.cacheType !== 'none') {
    return selectStrategy(staticProfile)
  }

  // 运行时发现有 cache → 升级策略
  if (discovered.hasCache && discovered.confidence >= 0.7) {
    if (discovered.matchingStrategy === 'exact-prefix') {
      return 'cache-preserving'
    }
    return 'balanced'
  }

  return 'aggressive'
}
```

**集成点：** `CompactionController` 在每 5 turn 检查一次 `CacheBehaviorLearner.infer()`，如果策略需要升级则切换。

## 模块三：Phase-Aware Artifact Threshold（相位感知阈值）

### 3.1 相位 → 阈值映射

不同任务阶段对 inline 内容的需求不同：

```typescript
const PHASE_THRESHOLDS: Record<string, number> = {
  explore: 400,   // 探索产出大量 grep/read，大部分不会被再次引用
  plan: 1200,     // 规划需要看到更多上下文做决策
  execute: 800,   // 执行阶段平衡（当前默认）
  verify: 1600,   // 验证需要完整错误信息
  deliver: 400,   // 交付主要是确认
}

function getPhaseAwareThreshold(
  phase: string,
  isError: boolean,
  adaptiveState: ThresholdState,
): number {
  const phaseBase = PHASE_THRESHOLDS[phase] ?? adaptiveState.artifactThreshold
  // 取 phase 建议和 adaptive 调整的较大值（保守方向）
  const base = Math.max(phaseBase, adaptiveState.artifactThreshold * 0.8)
  return isError ? base * 2 : base
}
```

### 3.2 相位来源

已有 `phaseTracker`（`src/tui/phase-tracker.ts`）和 `setPhaseHint()`。直接复用：

```typescript
// tool-pipeline.ts 中的 artifactIntercept

  deps.phaseHint ?? 'execute',
  isError,
  deps.adaptiveThresholds,
)
if (content.length <= threshold) return content
```

### 4.2 Cache ROI 计算

```typescript
interface CacheROI {
  savedThisTurn: number           // 本 turn 因 cache hit 节省的成本
  projectedLossIfCompact: number  // compact 破坏 prefix 后未来 N turn 的预期损失
  artifactSavings: number         // artifact intercept 节省的 token × 单价
  recommendation: 'delay-compact' | 'compact-now' | 'neutral'
}

function computeCacheROI(
  costs: ProviderCostModel,
  cacheReadTokens: number,
  estimatedRemainingTurns: number,
  avgTokensPerTurn: number,
  currentHitRate: number,
): CacheROI {
  const savedThisTurn = cacheReadTokens * (costs.inputPerMillion - costs.cachedInputPerMillion) / 1_000_000

  // 如果 compact 破坏 prefix，未来 turn 都会 miss
  const projectedLossIfCompact = estimatedRemainingTurns * avgTokensPerTurn *
    currentHitRate * (costs.inputPerMillion - costs.cachedInputPerMillion) / 1_000_000

  const recommendation = projectedLossIfCompact > savedThisTurn * 2
    ? 'delay-compact' as const
    : 'compact-now' as const

  return { savedThisTurn, projectedLossIfCompact, artifactSavings: 0, recommendation }
}
```

**集成点：** `CompactionController.maybeCompact()` 在决定 compact 前调用 `computeCacheROI()`。如果 `recommendation === 'delay-compact'`，跳过本次 compact（除非已到 reactive/ceiling 级别）。

## 模块五：Volatile Block Versioning（前缀稳定性保证）

### 5.1 问题

当前 habituation promotion 改变 `this.volatileBlock`，导致所有历史 user messages 的 volatile 前缀变化 → prefix cache 全部失效。

### 5.2 解决方案：版本化 volatile block

```typescript
class PromptEngine {
  // 新增：记录每个 user message 被创建时的 volatile 版本
  private volatileAtCreation: Map<number, string> = new Map()
  private userMessageIndices: number[] = []

  buildOaiRequest(oaiMessages: OaiMessage[], toolHistory?: ToolHistoryEntry[]): OaiChatRequest {
    const result: OaiMessage[] = []
    let userIdx = 0

    for (let i = 0; i < oaiMessages.length; i++) {
      const msg = oaiMessages[i]!
      if (msg.role === 'user') {
        if (i === lastUserIdx) {
          // 最新 user message — 使用 FRESH（同 v2）
          result.push({ role: 'user', content: this.cachedFreshBlock })
        } else {
          // 历史 user message — 使用它被创建时的版本
          const version = this.volatileAtCreation.get(userIdx) ?? this.frozenBase
          result.push({ role: 'user', content: version })
        }
        userIdx++
      }
      result.push(msg)
    }
    // ...
  }

  /**
   * 当新 user message 被添加到 session 时调用
   * 快照当前 volatileBlock 作为该 message 的永久版本
   */
  snapshotVolatileForNewUser(): void {
    const idx = this.userMessageIndices.length
    this.volatileAtCreation.set(idx, this.volatileBlock)
    this.userMessageIndices.push(idx)
  }
}
```

**效果：** Habituation promotion 只影响新 turn 的 volatile block，不会回溯修改历史 → prefix 保持字节稳定。

**内存开销：** 每个版本 ~2KB，50 user messages = 100KB，可忽略。

### 5.3 Append-Only Guard（运行时断言）

```typescript
class AppendOnlyGuard {
  private sealedHash: string = ''
  private sealedLength: number = 0

  seal(messages: OaiMessage[], upTo: number): void {
    this.sealedLength = upTo
    this.sealedHash = sha256(stableStringify(messages.slice(0, upTo)))
  }

  verify(messages: OaiMessage[]): boolean {
    if (this.sealedLength === 0) return true
    const current = sha256(stableStringify(messages.slice(0, this.sealedLength)))
    return current === this.sealedHash
  }
}
```

**集成点：** 在 `buildOaiRequest` 开头调用 `verify()`。在 dev/test 模式下 throw，在 prod 模式下 log warning + 记录 drift event。

## 模块六：Opportunistic Compact（机会性压缩）

### 6.1 Cold Window Detection

当用户离开一段时间后回来，cache 已经冷了。这是做 compact 的最佳时机：

```typescript
// 在 AgentLoop.run() 的 turn 开始时
if (this.warmthTracker.shouldOpportunisticCompact()) {
  // Cache 已冷 — 趁机做结构优化
  await this.compactionController.opportunisticCompact({
    // 可以更激进，因为 prefix 反正要重建
    strategy: 'aggressive',
    // 但保留 anchor messages
    preserveAnchors: true,
  })
  // 重建 frozen base（如果 volatile 有变化）
  this.config.promptEngine.rebuildFrozenBase()
}
```

### 6.2 Flow-Score Selective Compact

压力下不是按时间顺序删除 round，而是按"流量分数"选择性删除：

```typescript
interface RoundFlowScore {
  roundIndex: number
  score: number  // 0-1，高 = 该 round 的 artifact 被后续引用多
}

function computeFlowScores(
  rounds: MessageRound[],
  ghostRegistry: GhostRegistry,
): RoundFlowScore[] {
  return rounds.map((round, idx) => {
    const artifactIds = extractArtifactIds(round)
    const totalAccesses = artifactIds.reduce((sum, id) =>
      sum + (ghostRegistry.getAccessCount(id) ?? 0), 0)
    return { roundIndex: idx, score: Math.min(totalAccesses / 3, 1) }
  })
}

// 在 microCompactOai 的 round-dropping phase 中：
// 优先删除 flow score 最低的 round（而非最老的）
```

## 非目标

1. **不做 ML-based 预测** — 用简单规则和观察，可解释性优先
2. **不做额外的探测请求** — 只观察正常使用中的 response
3. **不做 attention heatmap** — 解析模型 reasoning 太脆弱
4. **不做 prefix alignment padding** — DeepSeek cache-prefix unit 粒度未公开
5. **不修改 API 请求格式** — 除了 Anthropic 的 cache_control，不添加 provider-specific 参数

---

## 验收标准

1. **闭环验证：** cache hit rate 下降时，系统在 3 turn 内自动调整策略
2. **Ghost 有效性：** ghost hit rate < 10%（说明驱逐策略正确）
3. **多 provider：** 对有透明 cache 的 provider（如 Mimo），5 turn 内自动发现并升级策略
4. **经济学：** 对 DeepSeek，compact 决策考虑 ROI，不在 cache 健康时做不必要的 compact
5. **稳定性：** volatile versioning 消除 habituation promotion 的 cache 破坏
6. **向后兼容：** 所有现有测试通过，无行为回归
