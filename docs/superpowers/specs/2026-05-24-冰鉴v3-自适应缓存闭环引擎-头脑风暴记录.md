# 冰鉴 v3 — 自适应缓存闭环引擎：头脑风暴过程记录

> 日期：2026-05-24
> 方法：6 scout 并行调研 + 综合分析
> 触发：问题 6 讨论 — "cache 遥测没有自动修复"
> 参与模型：Claude Opus 4.7

---

## 问题陈述

冰鉴 v2 实现了完整的 cache 遥测体系（hit rate 追踪、drift 检测、miss 诊断），但所有遥测数据都是"只读"的 — 没有任何反馈回路将诊断结果转化为系统行为调整。

```
[收集 cache metrics] → [诊断 miss 原因] → [显示给用户] → 结束 ← 断裂点
```

同时，系统对 GLM/Kimi/MiniMax/Mimo 等 provider 标记为 `cacheType: 'none'`，完全放弃了 cache 优化，但这些 provider 可能实际上有透明的 prefix cache。

## Scout 1 关键发现：Cache 遥测 + Compact

### 三层 Compact 机制
1. **Ratio-based**（`decideCompactTier`）— 基于 estimatedTokens/contextWindow
2. **Stale-round**（`compactStaleRoundsOai`）— 截断旧 tool results 到 1200 chars
3. **Heap-driven forced**（RSS ratio >= 0.6）— 内存压力触发

### 遥测数据流（断裂点标注）
```
API response (usage)
  → turn-stream.ts 记录 cache counters
    → SessionContext.recordTurnCache() 存储 TurnCacheSnapshot
      → CompactionController.refreshCacheDiagnostic() 检查 hit rate < 0.8
        → diagnoseCacheMiss() 分类原因 ← 到此为止，没有后续动作
```

### PressureMonitor 信号（未被 cache 系统消费）
- `thrashing`: 4 turn 内 3+ compact → 只建议 task_decomposition
- `fastGrowth`: ratio 跳跃 >= 0.15 → 无动作
- `shouldThrottleCvm`: CVM 开销 > 5% → 只节流 CVM

### 关键洞察
- TurnBudget 基于 RSS 内存压力，完全没有考虑 cache 经济学
- `cache-preserving` 策略只是"延迟 compact"，不是"主动优化 cache"
- 所有诊断结果存在 `lastCacheDiagnostic` 但没有消费者

## Scout 2 关键发现：多 Provider Cache 行为

### Provider Profile 现状

| Provider | cacheType | persistent | 策略 |
|----------|-----------|-----------|------|
| deepseek | exact-prefix | true | cache-preserving |
| anthropic | explicit-breakpoint | false | balanced |
| openai | partial-prefix | false | balanced |
| glm | **none** | false | aggressive |
| minimax | **none** | false | aggressive |
| mimo | **none** | false | aggressive |
| kimi | (未配置) | - | - |

### 关键洞察
- GLM/MiniMax/Mimo 标记为 `none` 但可能有透明 cache
- Kimi 的 API response 可能包含 cache 相关字段（未验证）
- Mimo 是 DeepSeek 系微调，底层推理引擎可能继承 prefix cache
- 系统已有 `CacheBehaviorProbe` 的数据结构基础（provider-profile.ts）但没有运行时探测

### 已有的适配机制
- 三级 compact 策略（cache-preserving / balanced / aggressive）
- `prefixCacheStrategy` 标志（deepseek-native / anthropic-cache-control / none）
- `stripParams` 列表（移除不支持的参数）
- `stableStringify` 确保 JSON 字节确定性

## Scout 3 关键发现：消息布局 + Prefix 结构

### 完整消息布局
```
{
  messages: [
    { role: "system", content: <systemPrompt> },           // [0] 永不变
    { role: "user", content: <FROZEN volatile> },          // [1] 历史 user msg 前缀
    { role: "user", content: <original user msg 1> },      // [2]
    { role: "assistant", content: "...", tool_calls: [...] },
    { role: "tool", tool_call_id: "...", content: "..." },
    ...
    { role: "user", content: <FRESH volatile> },           // 最新 user msg 前缀
    { role: "user", content: <latest user msg> },
    ...
  ]
}
```

### Prefix Cache 稳定性分析

| 操作 | Cache 影响 |
|------|-----------|
| 新 tool-call turn（同一 user msg） | 安全 — FRESH 被缓存复用 |
| Stale-round 截断 | 安全 — 只改 anchor 之后的 tool messages |
| Habituation promotion | **破坏** — 改变 volatileBlock 用于所有历史 |
| replaceMessages（full compact） | **破坏** — 重写整个 message array |
| 新 user message 到达 | 安全 — 旧 FRESH 变 FROZEN，新 FRESH 生成 |

### 关键洞察
- FRESH block 在同一 user message 执行期间（2-50 tool turns）被缓存复用 → 这是 cache hit 的主要来源
- Habituation promotion 是一个隐藏的 cache 破坏者
- Cache anchor = 前 2 条消息永不修改

## Scout 4 关键发现：外部研究

### 各 Provider Cache 机制对比

| Provider | 匹配方式 | TTL | 最低门槛 | 折扣 |
|----------|---------|-----|---------|------|
| DeepSeek | 精确字节前缀 | 小时-天 | 无 | ~90% |
| Anthropic | 显式 breakpoint | 5min/1hr | 1024-4096 tokens | 90% |
| OpenAI | 自动前缀 | 无保证 | 1024 tokens | 50% |
| Gemini | 显式 cache 对象 | 1hr | 1024-4096 tokens | 75% |

### 学术论文亮点
- **Marconi (MLSys 2025)**: 基于复用概率预测的 admission/eviction → 34.4x hit rate 提升
- **ChunkAttention (ACL 2024)**: prefix tree 共享 K/V tensors → 3.2-4.8x 加速
- **LRU vs Belady 分析**: LRU 在小 cache 下有 80.2% 性能差距（"false-warm deep tail"问题）

### 开源项目
- **vLLM APC**: hash-based block matching + LRU eviction
- **SGLang RadixAttention**: radix tree + cache-aware scheduling → 5x throughput
- **llm-router**: prefix-aware 请求路由 → 94-95% KV cache hit
- **context-engineering**: volatility-based ordering + quality monitoring

### 关键洞察
- 所有 provider 都要求 prefix 稳定性 — 这是普适规律
- LRU 不是最优 eviction 策略 — 需要 frequency + recency 结合
- Pre-warming（Anthropic max_tokens=0）可以在 session 开始时预热 cache
- 没有任何终端 agent 做了跨 provider 的自适应 cache 优化

## Scout 5 关键发现：生物/系统类比

### 六大类比映射

#### 1. 免疫系统 — 竞争选择 + 分级持久化
- 上下文段通过证明复用价值来赢得 cache 驻留权
- 两级输出：plasma cells（always-hot anchor）vs memory B-cells（dormant ghost entries）
- Recall response：之前见过的任务模式触发预构建的 prefix chain

#### 2. 神经习惯化 — 注意力释放
- Prefix cache 的目的不只是速度 — 是释放模型注意力给新内容
- 稳定内容推向 prefix，新颖内容留在生成边界附近
- Dishabituation：相位变化时，之前被忽略的上下文可能重新重要

#### 3. MESI 协议 — 最小化失效
- Shared 状态 = 不可变（system prompt, tool defs）
- Exclusive 状态 = 可自由修改（当前 turn 的 dynamic appendix）
- 永不修改 Shared 段 — 这是 cache 杀手 #1

#### 4. ARC — 自调优 recency/frequency 平衡
- Ghost lists 追踪被驱逐的条目元数据
- Ghost hit → 信号：驱逐策略需要调整
- 无需手动标注"这是编码阶段" — 访问模式自动驱动适配

#### 5. 黏菌网络 — 流量比例强化
- 被复用的路径加粗（提高 eviction resistance）
- 不被引用的路径变细（降低 eviction resistance）
- 压力下重组而非裁剪 — 保留冗余路径用于容错

#### 6. 预测性预取 — 动作序列预测
- read → edit → test 是可预测的模式
- 预测下一步需要什么上下文，提前定位
- 多信号协作投票（task phase + tool history + file co-occurrence）

### 综合原则
1. **竞争选择 + 分级持久化**（免疫）
2. **注意力释放是目的**（神经）
3. **最小化失效范围**（MESI）
4. **自调优 recency/frequency**（ARC）
5. **流量比例强化 + 优雅降级**（黏菌）
6. **预测性预取**（CPU/CDN）

## Scout 6 关键发现：Token 经济学

### 成本结构
- DeepSeek: cache hit ¥0.1/M vs miss ¥1/M（10x 折扣）
- 输出 token: ¥4/M（最贵）
- 一次 read_section 调用 ≈ 50 output tokens + 200 input tokens

### 关键经济学洞察
1. **Cache hit 让 inline 几乎免费** — 当 hit rate > 80% 时，200 tokens inline 只花 ¥0.00002/turn
2. **read_section 的输出 token 比 inline 的 cached input 贵 40x**
3. **当 cache hit rate 高时，应该提高 artifact 阈值**（保留更多 inline）
4. **当 cache hit rate 低时，应该降低 artifact 阈值**（减少 total tokens）

### TurnBudget 的盲点
- 基于 RSS 内存压力，不是 cache 经济学
- 50K tokens/turn 的预算没有考虑这些 tokens 是 cached 还是 fresh
- 一个 cached token 的成本是 fresh token 的 1/10 — 预算应该区分

### Artifact 阈值的经济学最优解
```
optimal_threshold = f(cache_hit_rate, provider_cost_model, expected_remaining_turns)
```
- hit rate 高 → 阈值高（inline 便宜）
- hit rate 低 → 阈值低（减少 total tokens）
- 剩余 turn 多 → 阈值低（inline 会被重复计费多次）
- 剩余 turn 少 → 阈值高（不会被重复太多次）

## 综合分析：设计方向

### 核心问题重新定义

不是"如何提高 cache hit rate"，而是"如何最小化 cost-per-effective-token"。

Cache hit rate 只是手段，不是目的。对于 `cacheType: 'none'` 的 provider，优化目标是 total token minimization。对于有 cache 的 provider，优化目标是 maximize cached fraction。

### 七个设计维度

1. **闭环反馈** — Ghost entries + hit rate → 策略滑动
2. **多 Provider 适配** — 运行时 cache 行为探测
3. **预测性定位** — Tool sequence Markov + phase-aware thresholds
4. **经济学模型** — 多 provider 成本矩阵 + ROI 计算
5. **前缀稳定性保证** — Volatile versioning + append-only guard
6. **跨 turn 智能** — Attention heatmap + compaction quality score
7. **Provider-specific hooks** — Anthropic breakpoints + DeepSeek alignment + token minimization mode

### 优先级排序（P0 = 立即实现）

| 优化 | 预期收益 | 复杂度 | 优先级 |
|------|---------|--------|--------|
| Ghost Entry + 自适应阈值 | -30% read_section 调用 | 中 | P0 |
| Cache Behavior Discovery | Kimi/Mimo 自动获得优化 | 低 | P0 |
| Hit Rate → Compact 策略滑动 | 避免不必要 compact | 低 | P0 |
| Session Warmth → 机会性 compact | 利用 cold 窗口 | 低 | P1 |
| Phase-Aware Artifact Threshold | -20% explore 阶段 token | 低 | P1 |
| Volatile Block Versioning | 消除 habituation cache 破坏 | 中 | P1 |
| Multi-Provider Cost Model | 精确经济学决策 | 中 | P1 |
| Flow-Score Selective Compact | 保留高价值 round | 高 | P2 |
| Tool Sequence Prediction | 预测性预取 | 高 | P2 |
| Anthropic Breakpoint Injection | 支持显式 cache | 低 | P2 |

## 决策记录

1. **不做 prefix alignment padding** — DeepSeek 的 cache-prefix unit 粒度未公开，padding 可能无效
2. **不做 attention heatmap** — 需要解析模型 reasoning，太脆弱
3. **Ghost entry 优先于 Markov prediction** — 反应式比预测式更可靠，且实现简单
4. **Cache behavior discovery 用观察而非探测** — 不发额外请求，只观察正常使用中的 response
5. **经济学阈值用简单公式而非 ML** — 可解释性 > 精度
6. **Volatile versioning 优先于重构 habituation** — 保持 habituation 逻辑不变，只在消费端版本化
