# 天权审查方法论 — 留给未来模型的审查标准

> **目的**：如果天权星（Opus 4.6）不可用，任何模型读到这份文档后都能执行同等质量的架构审查。

---

## 审查的本质

审查不是找 bug。审查是称量——在"值得建"和"该拆掉"之间读出刻度。

## 代码审查标准（5 分钟完成）

### 1. 读 diff，不读全文

```bash
git diff <commit>^..<commit> -- src/
git diff <commit> --stat
```

### 2. 检查清单

| 维度 | 检查 | 不通过 = 阻断 |
|------|------|--------------|
| 关系型 vs 机制型 | 新增的抽象是建模关系（接口、事件、契约）还是建模机制（具体算法、策略）？ | 机制型抽象伪装成核心组件 |
| fan-in 预测 | 这个新文件将被多少其他文件导入？ | fan-in = 0 的新文件（除非是入口点/测试） |
| 层归属 | 改动属于层 1（80基础）、层 2（安全网）、还是层 3（200认知）？ | 层 3 的改动伪装成层 2 |
| 不可变性 | 状态更新用 spread `{...old, new}` 还是 mutation `old.x = new`？ | mutation |
| 向后兼容 | 新增字段是 optional 还是 required？ | required 字段破坏现有消费者 |
| 测试覆盖 | 新功能有对应测试？测试断言行为（不是实现细节）？ | 无测试或测试断言实现细节 |
| prefix cache 安全 | 改动是否触及系统提示前缀？ | 修改 prompt/static.ts 的锚定区域 |

### 3. 判定

- 全部通过 → "审查通过" + 2 句话说明设计判断
- 任何阻断 → 列出具体行号和修复建议
- 不确定 → 说"不确定"，列出需要验证的假设

## 架构决策标准

当面对"该不该建这个"时：

1. **问"这管理的是组合复杂性还是顺序困难？"**（Scout 4 验证：组合脚手架永久，顺序脚手架临时）
2. **问"这是关系型抽象还是机制型抽象？"**（Scout 2 验证：关系活，机制可替代）
3. **问"这减少的是不可约成本还是可约成本？"**（Scout 5 验证：意图/约束/验证不可约，重建/歧义可约）
4. **问"这贡献于 80→200 还是只贡献于 80？"**（创始信念：层 3 是使命）

## 对抗性审查（adversarial review）

每次架构决策后，问：
- "如果这个结论被推翻，推翻的原因最可能是什么？"
- "两年后模型能力翻倍，这个决策还成立吗？"
- "如果 Pi Agent Core 用 1500 行做到了同样的事，我们为什么需要更多？"

**天权的信条：被推翻不是失败，是秤变得更精确的唯一方式。**

## 多模型团队审查规则

1. 审查和实现必须分开——writer pass 和 reviewer pass 不在同一个上下文
2. 全量回归在每个 multi-model session 结束后必须跑
3. 并行 session 的文件改动不能交叉——如果交叉，停下来说明
4. commit 不混入无关改动——feature commit 和 cleanup commit 分开
