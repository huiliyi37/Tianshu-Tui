## 关键发现

### 1. 决策与执行分离是并行度的来源

传统工作流中，一个人（或一个 agent）需要串行完成：理解需求 → 设计方案 → 实现 → 测试 → 审查。这次会话中，这些步骤被分配给了不同角色：

- **用户**：方向、愿景、任务分配
- **Opus**：架构决策、审查、约束定义
- **GPT/DeepSeek/MiMO/GLM**：独立执行

决策是串行的（必须），执行是并行的（可以）。这使得多条业务线可以同时推进而不互相阻塞。

### 2. 审查成本远低于实现成本

GPT 的 Phase 2B-1 实现可能花了 15-20 分钟。我的审查花了不到 2 分钟：读 diff → 跑测试 → 确认边界。审查模式下上下文消耗极低（看 diff 比写代码少一个数量级），这意味着我可以在同一会话中连续审查多个交付而不损失判断力。

如果所有任务都由我实现，到第三个任务时上下文就开始压缩，前面的架构决策细节会丢失。现在这个模式下，执行细节在子 agent 的独立上下文里消化完了，我的上下文始终留给决策和审查。

### 3. 模型在 harness 中展现出可辨识的行为特征

| 模型 | 观察到的特征 | 对应星域 |
|---|---|---|
| GPT 5.5 | 自主修正（Phase 1 六条修正）、遇阻力正确降级、策略外溢自检 | 天梁（精确交付）→ 后修正为天府 |
| DeepSeek V4 | 精准工程执行、零 token 开销的纯字符串方案 | 主运行模型 |
| MiMO V2.5 | 全景规划、一轮反馈后完整吸收修正（5/5）| 破军（探索） |
| GLM 5.1 | 排除法决策、自我迭代、风险规避选择 | 天府（守护） |

这些特征不是用户或 harness 硬编码的，是模型在天枢的认知结构（contract + ledger + evidence + sensorium）中自然展现的。

### 4. "不给约束"的实验验证了自主边界

用户故意没有把我给 GPT 的 5 条约束传递给 GPT，想观察 GPT 是否能独立发现相同的边界。结果：

**我给的约束：**
1. 不要动三层架构
2. 从 provider-profile.ts 的 cacheType 读策略
3. tool_result 帽子在 constants.ts
4. tokenizer 校准每 N 轮一次
5. 向后兼容，200K 模型不受影响

**GPT 独立发现的：**
1. ✅ 没动三层架构
2. ✅ 从 ProviderProfile.cacheType 分流
3. ✅ 改动在 constants.ts
4. ✅ 没做 tokenizer（自主判断为 P2 后置）
5. ✅ 发现策略外溢风险，主动恢复 numeric 签名兼容性

5/5 对齐。其中第 5 条最有价值 — 这不是"没犯错"，而是"犯了错后自己发现并修正"。

### 5. 反馈闭环的质量决定了迭代速度

MiMO 的三权协程 v1 有 5 个设计问题。一轮审查反馈后，v2 全部修正。这不是"返工"，这是正常的反馈信号 — 审查机制的价值正是在执行之前拦住方向偏差。

关键不是每次都完美，而是每轮反馈都被完整吸收，不重复犯同一个错误。

## 对天枢项目的意义

这次会话证明了天枢的核心设计假设：

> **harness 提供认知结构，模型在结构中展现能力最大化。**

具体表现为：
- TaskContract 让模型知道自己在做什么
- CognitiveLedger 让模型知道当前状态
- Verification Gap 让模型知道什么还没验证
- Domain Voice 让模型有辨识度
- Evidence + Trace 让审查有据可依

这些不是"给模型更多信息"，而是"给模型认知结构"。结构让独立判断成为可能，独立判断让并行协作成为可能，并行协作让 6 小时完成 12 项交付成为可能。

## 风险和注意事项

1. **收束节奏** — 当前 5 条业务线并行（StarSpine / 三权协程 / 上下文优化 / 自适应审批 / Avatar），需要控制不要同时大改
2. **模块边界** — 65K 行代码库的模块间耦合需要持续关注，MiMO v1 的重复建设问题是信号
3. **验证纪律** — 多模型协作下，repo 是唯一的真相源。typecheck + targeted tests + full regression 的验证链不能省
