# 多会话并行开发背景说明

## 1. 摘要

天枢面对的生产力现实不是单会话顺序执行，而是人类同时调度多个 AI 会话并行推进真实工程。长程任务中，一个主控模型即便能协助子代理，也可能运行一到两个小时；开发者不可能等待该任务完全结束后才开始下一个任务。

因此，多会话并行不是可选优化，而是当前 AI 辅助开发的生产力基线。天枢需要适配这个现实：人类负责调度，agent 服从边界，系统提供归属、验证、交付和风险控制。

## 2. 现实背景

- 单会话长程任务可能持续一到两个小时。
- 开发者等待长任务结束再下发下一任务，会造成严重生产力浪费。
- Claude Code、天枢或其他 coding agent 都会被用于多会话并行工作流。
- 人类已经在承担任务拆分、冲突判断、审查和合并节奏控制。
- 未提交改动在这种工作流中不是异常状态，而是多个会话共同推进工程现场的正常现象。

## 3. 当前人工调度模式

过去主要由开发者与 Claude Opus 一起审查、拆任务、分配会话和发现风险。这个模式有效，因为 Opus 可以作为高质量审查者，帮助判断任务是否冲突、文档是否充分、实现是否越界。

但这个模式存在明显约束：Opus 不会一直在线。当天枢自身能力尚未完全建成时，开发者仍然要承担大量调度与审查成本；一旦审查者离线，多会话现场就更依赖清晰的任务边界、可追踪的文件归属和可审计的交付记录。

## 4. 单会话假设为什么不成立

单会话假设认为一个主控模型可以串行接收任务、规划、调用子代理、执行、验证、提交，然后再处理下一个任务。这个假设在真实生产力环境里不成立。

原因包括：

- 单会话无法覆盖多个独立任务的等待时间。
- 单会话主控可能形成新的排队瓶颈。
- 长程任务执行期间，开发者仍然会产生新的判断、新的任务和新的审查需求。
- agent 容易把当前上下文内的失败误认为全局必须修复的问题。
- 共享工作区中的 dirty 文件可能属于其他会话，不应被视为需要清理的噪音。

## 5. 多会话并行的必要性

多会话并行不是为了让 AI 自主接管项目，而是为了让人类在安全边界内放大自己的调度能力。

人类负责决定：

- 哪些任务可以并行。
- 哪些文件或目录不能碰。
- 哪些验证失败属于历史问题。
- 哪些 diff 需要合并审查。
- 哪些阶段需要收束，哪些阶段可以继续探索。

agent 必须接受这个调度现实。它不应该要求开发者为了 agent 的安全性改成串行等待，也不应该因为自己无法区分归属就尝试清理整个工作树。

## 6. 对天枢的要求

天枢需要逐步承担工程控制层职责：

- 记录任务归属，区分本会话文件与外部会话文件。
- 识别外部改动，避免把未提交内容误还原到 HEAD。
- 归因验证失败，区分本任务失败、历史失败、外部会话失败、环境失败和命令错误。
- 拦截越权还原、删除 untracked 文件、全局 checkout、全局 reset 等高风险操作。
- 暴露 agent 认知风险，让人类看到当前是否存在任务漂移、上下文压力或验证不足。
- 在交付时给出可审查证据，而不是只给出“已完成”的结论。

## 7. 过渡期原则

在天枢能力没有建完全之前，多会话并行仍然是必要模式，但必须依靠更明确的人工规则支撑：

- 不要求所有会话串行等待。
- 不把 shared worktree 的 dirty 状态当成错误。
- 用户分配的任务边界优先于 agent 的自我判断。
- 不确定文件归属时先询问，不自行还原。
- 文档、计划和交接记录必须足够清晰，让 Opus 不在线时也能继续审查和推进。
