# 缓存命中率追竞品全景：四维度分析与行动优先级

> 2026-06-19 | 基于会话 `fe39a8ee`（DeepSeek-V4-Pro，4 轮 27 请求）的 ground-truth 数据
> 目标：缩短与竞品（Claude Code 99%+ 缓存命中）的差距
> 关联文档：`2026-06-19-轮间首请求-cacheCreate-12K-根因分析与优化方向.md`、`2026-06-19-轮间首请求-cacheCreate-增量附录优化设计.md`、`2026-06-17-claude-code-agent-tool-mechanism-analysis.md`

## 现状基线

| 指标 | 我们的值 (fe39a8ee) | 竞品参考 (Claude Code) |
|------|---------------------|----------------------|
| 轮内命中率 | 97-99.9% | ~99%+ |
| 轮间首请求命中率 | 73-91% | — |
| 整体会话命中率 | 94.8% (cacheRead/totalInput) | 99%+ |
| 费用节省（vs 无缓存） | 85.3% | 更高 |

轮内已经接近竞品。差距集中在**轮间首请求的 12K cacheCreate**和**tool result 撑大的 input 基数**。

## 维度 1：轮间首请求的 cacheCreate（appendix 重建）

**根因**：每次新用户消息到来时，`buildDynamicAppendix`（`volatile.ts:302`）全量重建 `<context-update>` 块，体积 ~12K token（逼近 `appendixMaxChars` 上限 48K chars）。这是轮间首请求 cacheCreate 的主要来源。

**数据**：cache-log 显示整个会话零次 `volatileSwapped`——12K 纯粹是 dynamic appendix 重建，不涉及 frozen base swap。

**已有方案**：增量附录（`2026-06-19-轮间首请求-cacheCreate-增量附录优化设计.md`），预期收益 12K→3-5K。

**天花板**：即使增量附录成功，仍有物理下限——新用户消息本身（几十到几百 token）+ 必须变化的 progress/tool-history 子块。预期收益 3-5pp。

## 维度 2：system/user 消息分离（温跃层可能性）

**现状**：`engine.ts` 的 trailer mode 把 `volatileBlock + consolidated + userContent + appendix` 全部合并进最后一条 user message。DeepSeek exact-prefix 从消息数组开头 byte-for-byte 匹配。

**竞品做法**：Anthropic 用四个显式 `cache_control` breakpoint（`anthropic-client.ts:161-227`）——tools、system、first-user、rolling-assistant 各自独立缓存。一个边界变化不影响其他边界。我们的 DeepSeek exact-prefix 没有 breakpoint 能力，但可以通过**消息层分离**近似这个效果。

**可能性**：把 volatileBlock 的稳定部分（project-instructions、working-set、session-memory）从 user-message trailer 移到 system message。这些字节就不会被 user message 的变化影响。但约束是：DeepSeek exact-prefix 把 system 和 user 当作连续字节流——system message 变化同样破坏前缀。不过 system message 是 session 常量（一旦设置不变），天然安全。

**风险**：如果 volatileBlock 中任何字段中途变化（如 sessionMemoryBlock 更新），整个前缀缓存从 byte 0 开始失效。当前 trailer mode 下这种变化只影响最后一条 user message。

**预期收益**：2-3pp（减少 trailer 中稳定部分的重复 cacheCreate）。风险高于维度 1 和 4。

## 维度 3：reasoning_content 回显

**现状**：DeepSeek 要求 tool-call turns 回显 assistant 的 `reasoning_content`。这些推理内容在 tool-dense 会话中**线性累积**——27 个请求的会话中，assistant 消息占 22K chars（~5.5K token），其中大部分是 reasoning。

**当前处理**：`requestTimeCollapse`（`engine.ts` T7）在 50% 窗口填充率时 strip 旧 reasoning_content。但 strip 本身改写历史消息字节——破坏 exact-prefix。设计上用 watermark 边界保持稳定，只在 50K-token step 跨越时触发一次。

**竞品做法**：Claude Code 用 `ContentReplacementState` 保证同一 tool_use_id 的字节跨 turn 不变——一旦模型看到某个内容，永远看到同样的字节。配合 server-side `cache_edits` 删除旧 tool_result 缓存条目，本地 history 完全不改。

**我们的约束**：DeepSeek 不支持 `cache_edits`。reasoning strip 只能在 request copy 上做（当前已是如此），不能改 session history。watermark 机制已经是最优解。

**预期收益**：有限——当前 watermark 机制已经把 strip 的 cache 破坏控制在最小频率。进一步优化空间不大。

## 维度 4：tool result 体积（最大杠杆）

**数据（fe39a8ee 会话）**：

```
tool messages:    64 msgs, 163,328 chars (40,832 tok)  — 88.0% 消息内容
assistant:        27 msgs,  21,952 chars ( 5,488 tok)  — 11.8%
user:              5 msgs,     257 chars (    64 tok)  —  0.1%
```

Tool result 占消息内容的 **88%**。在最后一次 API 请求中（input=127,374 tokens），tool result 占 **~32%**（40,832 tokens）。会话越长，这个比例越高。

**Top 15 tool result 体积分布**：

| # | chars | 内容 |
|---|-------|------|
| 1 | 29,507 | 完整计划文档（council-core 实现计划） |
| 2 | 13,381 | 完整测试文件 |
| 3 | 9,901 | 完整源码文件（worker-result extraction） |
| 4 | 8,781 | 完整设计文档（I1 业务流） |
| 5 | 7,847 | 完整源码文件（zod schema） |
| 6-15 | 3,667-7,769 | 更多完整文件读取 |

**关键发现**：最大的 5 条 tool result 全是**完整文件读取**（read_file 返回全量内容）。这些内容在后续每个 API 请求里都被重发——虽然命中缓存（不产生 cacheCreate），但它们是 input tokens 的主要构成，直接抬高了计费基数。

**已有但未充分利用的机制**：
- `DISK_BUDGET_CHARS = 50,000`（`engine.ts:477`）——tool result 截断阈值。但 top 15 中最大才 29.5K，远没到截断线。这个阈值太高了。
- `rawPath` / artifact 持久化——已有机制但 top 15 中没有一个走了 artifact 拦截。
- `observation masking`（`engine.ts:452`）——10 轮以上旧 tool result 被替换为占位符。但只对 10 轮以上的旧消息生效。

**竞品做法**：
- Claude Code：tool result 单 turn 聚合超 200K 字符→落盘 preview（`toolResultStorage.ts`）。旧 result 用 server-side `cache_edits` 删除，本地不改。
- aider：只发 diff hunk，不重发完整文件。
- Manus：大块外置引用，appendix 留指针。

**优化方向**：

1. **降低 artifact 拦截阈值**：从 50K 降到 8-10K。超过 8K 的 read_file 结果落盘为 artifact，消息里只保留 preview + 路径引用。top 15 中有 7 条会触发拦截，每条节省 3-20K chars。

2. **提前 observation masking**：从 10 轮降到 5 轮。旧 tool result 更早被折叠。

3. **read_file 默认带 limit**：对 >2000 行的文件，默认只返回导航视图（首页 + grep 定位），而非全量。工具描述里已有 `offset/limit` 参数和 "Files > ~2000 lines: returned as PARTIAL view" 的说明，但模型仍倾向全量读取。

**预期收益**：最高。如果把 tool result 平均体积从 ~2.5K 降到 ~1.5K chars，input 基数减少 ~40%。即使命中率不变，cacheRead 的计费基数也降低 40%——直接省钱。同时减少了 observation masking 和 collapse 的触发压力。

## 优先级排序

| 优先级 | 维度 | 收益预期 | 改动量 | 风险 |
|--------|------|----------|--------|------|
| P0 | 维度 4：tool result 体积 | 最大（input 基数 -40%） | 中（阈值调整 + artifact 拦截扩展） | 低 |
| P1 | 维度 1：增量附录 | 中（轮间 cacheCreate 12K→3-5K） | 高（buildDynamicAppendix 重构） | 中 |
| P2 | 维度 2：system/user 分离 | 小（2-3pp） | 中（engine.ts 结构调整） | 中高 |
| P3 | 维度 3：reasoning 回显 | 极小 | — | — |

**建议路径**：先做 P0（tool result 体积），因为投入产出比最高——阈值调整是几行代码的改动，但影响每个请求的 input 基数。P1（增量附录）作为第二步，处理轮间首请求的 cacheCreate。P2/P3 暂缓。
