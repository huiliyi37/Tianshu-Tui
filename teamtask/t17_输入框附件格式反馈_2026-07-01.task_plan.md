# Task Plan: 桌面端输入框附件格式反馈

## Goal

为桌面端 Composer 输入框的附件上传（选择/拖拽/粘贴）增加明确的不支持格式反馈，例如用户选择压缩包时，立即提示「压缩包暂不支持，请解压后上传文件或图片」，避免静默失败带来的挫败感。

## Current Phase

Phase 5

## Phases

### Phase 1: Requirements & Discovery
- [x] 明确用户场景：选择文件、拖拽文件、粘贴文件三种入口
- [x] 定位代码：`desktop/src/components/Composer.tsx`
- [x] 梳理当前行为：
  - 仅支持图片（PNG/JPEG/WebP/GIF/BMP），SVG 被排除
  - 文件选择器通过 `accept="image/png,image/jpeg,image/webp,image/gif"` 过滤
  - `addFiles` 对不支持的文件会设置 `imageError`，但文案较笼统
  - 拖拽非图片文件会被当作 textFiles 内联到输入框，无"不支持"反馈
  - 粘贴非图片文件被静默忽略
- **Status:** complete

### Phase 2: Design & Interaction
- [x] 定义支持/不支持的行为边界
  - 图片：始终作为 vision attachment 上传
  - 文本文件（.txt/.md/.json/.ts/.js 等）：可作为文本内联（保留现有行为）
  - 压缩包（.zip/.rar/.7z/.tar.gz 等）：明确提示不支持
  - 二进制文件（.exe/.dmg/.pdf/.docx 等）：明确提示不支持或建议换方式
- [x] 设计反馈文案（中文优先）
  - 单文件不支持：`xxx.zip 是压缩包，暂不支持，请解压后上传文件或图片`
  - 多文件混合不支持：`xxx.zip 等 N 个文件暂不支持（压缩包请解压后上传）`
- [x] 选择展示方式
  - 选择/拖拽：使用现有的 `composer-error` inline 错误条
  - 粘贴：使用 `toast.error`（粘贴触发位置不确定）
- **Status:** complete

## Key Questions

1. 文本文件是否继续内联？→ 是，保留现有行为，但文案提示可更清晰。
2. 反馈用 inline error 还是 toast？→ 选择/拖拽用 inline error，粘贴用 toast。
3. 是否需要支持更多格式？→ 本次只加「不支持反馈」，不扩展支持的格式。
4. 压缩包是否要提示解压？→ 是，明确告诉用户"请解压后上传"。

## Decisions Made

| Decision | Rationale |
|----------|-----------|
| 不扩展支持格式，只做反馈 | 用户明确需求是"给一个反馈"，不是"支持压缩包" |
| 拖拽的压缩包不再内联 | 当前内联二进制内容是乱码，体验更差 |
| 文本文件继续内联 | 已有成熟行为，用户可接受 |
| 按扩展名兜底判断 | Windows 剪贴板/拖拽常见 MIME 为空，必须兼容 |
| 错误文案区分"压缩包"与"其他不支持文件" | 压缩包是最常见误操作，需给出可操作建议 |
